## Как проверено

`tools/research/post-draft-history-gaps.mjs` использует `CaptureSchema`, `prepareV1PerMapFeatureHistory` и `createV1FeatureBuilder`. Никакого собственного упрощённого подсчёта raw source rows вместо eligibility. После расчёта отдельный recount по `usedMatchIds` проверяет каждого игрока: только совпадающие verified player/account IDs, `started_at < cutoff`, `completed_at < cutoff`, target исключён. Количество обязано совпасть с builder N.

A/B выбираются сравнением bigint team IDs, native sides остаются отдельными. История следует за аккаунтом через организации. У результата каждой целевой карты должен остаться только прежний `INSUFFICIENT_PLAYER_HISTORY`; появление identity conflict, иной причины, ready вместо unavailable или несовпадение source SHA останавливает аудит. Current verified identity не подменяет historical lineup known-at: все карты остаются `actual_lineup_reconstructed` / event-time-assumed.

В реальном replay обнаружились два формата ключа одной серии: dataset tuple `["opendota","1138399"]` и feature-history `opendota:1138399`. Добавлена точная нормализация проверенного namespace с сохранением обоих ключей; никаких объединений по названию или потери bigint precision. До исправления аудит остановился, результата не записал. Исходные файлы не правились.

CLI сверяет dataset/capture SHA и fingerprint, frozen code hashes; файл результата создаётся только новым. `verify` повторяет аудит без сети/БД и сравнивает результат. Код не читает токены, не создаёт jobs и не выдаёт вероятности.

```powershell
node tools/research/post-draft-history-gaps.mjs verify .tools/s304-eval-r1 .tools/s304-dataset-final.json .tools/s304-dataset-capture-final.json .tools/s304-history-gaps-r1.json
```

## Ограниченный план пополнения

Следующий шаг начинается с **discovery**, без импорта деталей или обучения. [Конкретное предложение запросов](evidence/s3-04-history-discovery-proposal.json) пока draft, не зарегистрировано и не выполнено.

1. Первая группа —20из34аккаунтов, порядок: самый ранний проблемный cutoff, затем numeric account ID.14остаются явно отложенными. Выбор не зависит от победителей, величины prediction error или текущих ников.
2. Существующий `OpenDotaPlayerHistoryClient.discover` допускает до5аккаунтов с одним cutoff в запросе. Совпадающие cutoff объединены: **9логических запросов, максимум18HTTP-попыток вместе с retries**, до200account-map rows. Это лимит нашего первого сбора, не заявление об API-квоте. Общий persistent quota guard/Retry-After имеет приоритет.
3. Каждый запрос ищет до10недавних pro-кандидатов на аккаунт в730днях перед **первым** проблемным cutoff. Существующий adapter поддерживает это окно; оно не покрывает весь warmup от01.01.2024. Более ранняя история остаётся неизвестной, а не отсутствующей. Последующие страницы/старые окна потребуют сохранённого плана продолжения. При заполненной странице фиксируется возможная неполнота.
4. Использовать существующую валидацию fixed Explorer query/rows; сохранить все возвращённые строки и provenance до отбора. `professional/premium` — discovery filter, не утверждение Tier1 или готовности импортированной карты. Для пригодности затем нужны независимые pro/outcome/identity/series checks.
5. Dedup по numeric match ID между всеми аккаунтами. Прежде чем получать detail, проверить существующий verified локальный source/cache. Общая discovered карта должна запрашиваться один раз. Не брать total hero aggregates/public matches вместо pro-history.
6. Первый discovery проход: **0detail/profile/league/hero catalogue запросов,0business writes**, никаких auto-import/auto-enrichment/queue jobs. Обобщённый proposal аудитора резервирует потолок100detail attempts для возможной следующей фазы, но текущий конкретный draft их не выполняет. Отдельный этап деталей возможен только после оценки discovery и фиксации собственного бюджета; больше данных не означает автоматически больше пригодных карт.
7. После возможного пополнения нужна новая dataset revision и повтор eligibility, включая всю серию. R1 остаётся неизменным. Не снижать минимум5, не добавлять публичные матчи или непроверенные cross-account merges. Рост coverage не устраняет прежний отрицательный metric signal сам по себе и не активирует post-draft модель.

Первые20аккаунтов встречаются среди25из39целевых карт, но это не обещание восстановить25карт: часть игроков той же карты отложена, remote availability неизвестна, новые карты тоже могут не пройти проверку. Эти34аккаунта получены из исследовательского pro-корпуса, не объявлены Tier1-участниками. Расширение истории допустимо для исследования; будущая оценка R2 обязана иметь отдельно проверенный Tier1 event-edition scope.
