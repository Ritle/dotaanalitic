## Поведение

«Следующая страница» читает серверный кэш выбранной страницы. При первом открытии незагруженной страницы выполняется явное обновление источника. Повторный переход использует кэш; устаревшие данные помечаются и обновляются отдельной кнопкой. Возврат на предыдущую страницу доступен и после пустого ответа. Номера ограничены 1–50, размер страницы — 20; это предел приложения, а не утверждение полноты календаря. Неполная/пустая страница отключает переход вперёд; она могла измениться после времени получения. Автоматического обхода страниц, опроса API или загрузки всех встреч нет.

Фильтр турнира действует на текущую страницу. Смена страницы сбрасывает фильтр, выбранную встречу, подтверждение и несохранённую форму. Переходы и повторное обновление заблокированы на время запроса. Списки страниц могут сдвигаться, когда провайдер добавляет или переносит встречи; они не объединяются в якобы полный снимок.

PandaScore документирует `page`/`per_page` для навигации: [официальная документация](https://developers.pandascore.co/docs/getting-started). Все запросы выполняются сервером с общей постоянной квотой, обработкой Retry-After и существующими ограничениями попыток/тайм-аута/размера. Каждый успешный запрос сохраняет endpoint, фактическое fetchedAt, knownAt=null и SHA источника. Обновление одной страницы не переписывает другую.

## Совместимость

`GET /api/v1/upcoming?page=N` только читает кэш; `POST /api/v1/upcoming/refresh?page=N` с owner/CSRF обновляет выбранную страницу. Отсутствующий page означает 1; остальные query/body поля отклоняются, номера должны быть каноническими целыми строками. Первая страница сохраняет прежний JSON, таблицы и immutable source history. Применяется только новая миграция 047 с отдельными `upcoming_page_cache` и `upcoming_page_observations` для страниц 2–50. Старые SQL не меняются.

Составы разрешены только для турниров из валидированных сохранённых страниц. Контекст каталога ищет конкретную встречу в сохранённых страницах без внешнего запроса; если ID повторяется, выбирается наблюдение с наиболее свежим fetchedAt. Отсутствие встречи на более новой другой странице не трактуется как отмена. Повреждённые записи, чужой endpoint, будущий fetchedAt, повторяющиеся ID и отражённый токен не используются.

Замороженные контракты и executor V1 принимают только исторически закреплённый источник первой страницы. На дополнительных страницах доступны составы и сравнение; блок назначения прогноза заменён явным пояснением. Эти наблюдения не выдаются за источник первой страницы и не попадают в её журнал. Поддержка прогнозных назначений новых страниц требует отдельной версии контракта; этот срез не оценивает и не активирует модель.
