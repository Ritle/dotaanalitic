# S1-11 — поиск записей для состава предстоящей встречи

## Поведение

В форме `/upcoming` вместо копирования ID в отдельной вкладке можно найти организацию или игрока по имени/ID локального справочника. Введите запрос, нажмите **«Найти»** или Enter, затем явно выберите результат. В списке и выбранном значении видны имя и строковый canonical ID: одинаковые никнеймы не выбираются автоматически. После выбора десяти разных игроков и двух организаций подтвердите состав и создайте обычный manual scenario.

`CatalogPicker.vue` использует существующий owner-only catalogue API, Zod payload и Vue Query server cache. Новых endpoints, provider calls, SQL, библиотек и записей identity нет. Поиск возвращает первые10 совпадений; при hasMore предложено уточнить запрос. Пустая выдача, загрузка, ошибка/повтор, сброс и Escape имеют явные состояния. Enter в поиске не отправляет родительскую форму. Результаты доступны обычными клавиатурными кнопками; inputs имеют уникальные labels.

Редактирование выбранного имени немедленно снимает прежний ID и подтверждение состава. Введённый запрос при этом сохраняется. Сам текст в поле не является выбранным ID. При смене встречи форма пересоздаётся, старые записи не переносятся. Выбранная в другой позиции запись недоступна повторно; существующая ScenarioInputSchema и server checks сохраняют final duplicate/unknown guards. Выбор роли/замены остаётся ручным.

Поиск имени помогает владельцу выбрать **локальный canonical record**. Он не создаёт PandaScore→Steam связь, не подтверждает участие в карте и не импортирует отсутствующего игрока. Пустая выдача означает отсутствие совпадения в локальном каталоге; нельзя заполнить её вымышленным игроком или source ID. Expected roster PandaScore по-прежнему отображается отдельным ориентиром, без автоматического baseline/role assignment. Сохранение использует прежний POST `/scenarios`; сохранённый состав содержит только выбранные canonical IDs.

## Проверки

Расширен реальный PostgreSQL/Chromium сценарий: поиск и явный выбор12 записей, два игрока с одинаковым именем и разными bigint IDs, сохранение ровно выбранной десятки, неподтверждённая форма, пустой поиск, synthetic503/retry, запрет повторного игрока, сброс, Escape и отсутствие случайного POST при Enter. E2E uses disposable synthetic DB, provider stub и явно синтетические имена; production fallback fixtures нет.

Первый прогон выявил сброс нового запроса при редактировании выбранного игрока: prop watcher реагировал на уже очищенный ID. Существующий failing E2E исправлен условием проверки текущего выбора; текст нового поиска теперь сохраняется. Заодно source-failure test получил собственный cache setup и reset provider failure flag, чтобы не зависеть от предыдущего test/worker. PASS: frozen install/typecheck,422 unit, root build и full17 Chromium E2E (3 upcoming cases). Verifier19/golden, docs/diff прошли. Отдельные PG/API, Node fixtures и SQL baseline не затронуты и в этом UI-only срезе не повторялись; браузерные проверки используют настоящий backend/PostgreSQL в disposable DB. [Подробности](PROGRESS.md).

Desktop/360px PNGs расширенной формы просмотрены в ignored `apps/web/test-results/upcoming-picker-{desktop,mobile}.png`; горизонтальный overflow после выбора12 записей отдельно проверяется. Сервер/API/schema/SQL001–019/dependencies/lockfile/evidence captures не менялись. Сетевых запросов к PandaScore/OpenDota в этом срезе нет. Рабочая БД не наполнялась синтетикой.
