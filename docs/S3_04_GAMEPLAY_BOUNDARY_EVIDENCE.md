# S3-04 — проверка границы драфта и игрового процесса

14 ноября 2026. Срез `post-draft-validation-readiness/gameplay-boundary-evidence`.

**Аудит выполнен; точная UTC-граница не подтверждена.** Доступные ответы не позволяют автоматически признать SQL061-расчёт сделанным до начала игрового процесса. Это ограничение строгого prospective cohort, а не поломка сохранения драфта или действующей V1. Старые снимки, математические модели и критерии проверки не изменены.

## Что проверено на реальных данных

Выполнены3 GET OpenDota и1 GraphQL STRATZ, все HTTP200; retries0, общий durable учёт квот. В канонические факты и прогнозы ничего не записывалось. Установки sentry также встречаются при отрицательном времени. Следовательно, по этой выборке ноль таймера **не означает отсутствие предшествующих действий на карте**. Для строгой проверки «до игрового процесса» следует отдельно удостоверять начало управления героями, а не молча принимать за него0:00. Это исследовательское уточнение смысла границы; frozen independent policy и evaluator в этом срезе не переписаны.

STRATZ `startDateTime` совпал с OpenDota `start_time` на3/3 картах. `endDateTime − startDateTime − durationSeconds = 0` на3/3; при этом OpenDota вернул ненулевые pause records. Это наблюдаемое равенство, **не доказательство независимых wall-clock отметок** и не установленная формула STRATZ. В fresh introspection у start/end отсутствуют описания фаз; в проверенных `MatchStatsPickBanType` и `MatchPlaybackDataType` нет явных полей UTC-границы драфта/управления. Не утверждается отсутствие такой возможности во всех API/тарифах провайдера.

PandaScore в этой задаче не запрашивался. [Прежний source pilot](S3_04_DRAFT_TARGET_SOURCE_PILOT.md) сохранил game-detail403 и разные длительности begin/end/length; generic `begin_at` встречи не заменяет начало игровой фазы карты. Покупка доступа или повтор того же запроса без новой информации не гарантируют нужную семантику.

## Проверка первоисточников

Сохранены семь публичных ответов GitHub с SHA и fetchedAt; код закреплён по ревизиям, не по изменяемому master. Опубликованная ревизия не удостоверяет точный deployment SHA парсера, сформировавшего каждый API-ответ; это дополнительное свидетельство устройства часов, а не замена измерения фактической границы.

- [OpenDota parser, ревизия67945be](https://github.com/odota/parser/blob/67945be040de92d0ba9cdedc77434886d4f736be/src/main/java/opendota/Parse.java): значения времени событий приводятся к внутреннему game zero; код учитывает pause ticks отдельно, а сбор draft timings зависит от стадии выбора. Он не предоставляет в этом выводе проверенное преобразование относительных времён в UTC первой возможности управлять героями. Наличие кода draft timings также не обещает непустые данные каждой карты — наш результат0/3.
- [OpenDota ParsedFetcher, ревизияdf9c93e](https://github.com/odota/core/blob/df9c93e280ac9a5f7c354737a1dab81049b1ddbf/svc/fetcher/ParsedFetcher.ts): start/duration передаются отдельно от replay-данных, а значение endedAt для insert вычисляется из их суммы. Это ещё один пример того, почему арифметически полученный конец не является независимым UTC-свидетельством.
- [OpenDota MatchResponse той же ревизии](https://github.com/odota/core/blob/df9c93e280ac9a5f7c354737a1dab81049b1ddbf/svc/api/responses/MatchResponse.ts) описывает pause entries, но не удостоверяет нужную фазу у исследуемых clock fields. Fresh STRATZ schema и реальные ответы сохранены локально с отдельными SHA.

Документация Valve Developer Community вернула403 через web-инструмент; ограничения не обходились. `docs.stratz.com` этим инструментом недоступен. Выводы основаны на фактически полученных ответах/коде, а не на предположениях о содержимом недоступных страниц.

## Контракт временной пригодности

Ручной ввод пиков остаётся допустимым: прежний protocol разрешает `owner_asserted_asof` для выбранных пятёрок и окончательных10героев. Отсутствие отдельного API timestamp конца драфта не вводит новое требование официально подтверждать ручной выбор. Недостающее свидетельство этого аудита — пригодная граница начала игрового процесса для проверки времени уже сохранённого расчёта.

Не применять автоматически `start_time`, `start_time + 90`, `start_time − 90`, `end − duration` или время получения API как verified gameplay start. `pre_game_duration` само по себе не задаёт абсолютный UTC-якорь; паузы/задержки и различные фазы нельзя спрятать фиксированной поправкой.

Для будущего доверенного adapter нужны native map ID, определение конкретного фазового события, проверенная связь его часов с UTC, разрешение и границы ошибки, provenance события и отдельно event/known/fetched clocks. При интервальной точности SQL061 commit receipt должен быть **строго раньше нижней границы** начала игрового процесса; пересечение интервалов — неизвестно, а не «вовремя». Окончательные10героев и их привязки к игрокам должны быть заморожены ранее cutoff. Receipt доказывает завершение записи, но не фазу Dota.

Поздний replay/ответ может проверять фактическое событие, если его семантика и часы действительно удостоверены. Он не может задним числом создать отсутствовавшие входы, драфт или доказательство их доступности. Одного ручного выбора победителя, таймера трансляции с неизвестной задержкой или server timestamp недостаточно для строгого cohort.

Сейчас `verifiedGameplayStarts:0`, `verifiedDraftEnds:0`, `collectionAllowed:false`, `primaryEligible:false`, `deployable:false`. Это вывод для небольшой фиксированной выборки и доступных полей, а не утверждение, что решить задачу принципиально невозможно.

## Реализация и воспроизведение

- `tools/audits/gameplay-boundary-collect.mjs`: ограниченный однократный collector; exclusive каталог попытки, именованный OpenDota client, durable quotas, без повторов и бизнес-записей.
- `gameplay-boundary-core.mjs`: чистая сводка с nullable неизвестными данными; никакие clock coincidences не дают автоматического допуска.
- `gameplay-boundary-report.mjs`: SHA/code/source verification и exclusive offline report/replay. Сырые ответы находятся только в игнорируемой `.tools`.
- `tests/node/gameplay-boundary.test.mjs`: синтетические проверки отсутствующих/пустых данных, неоднозначных часов, отрицательных событий, конфликтов ID/GraphQL и неизменности входов.

Отчёт `.tools/s304-gameplay-boundary-r1/analysis.json`, SHA `175c446a0e513245d9afe37fc7fdc65bc4d4f1dc0d7e4f93068da0cf45f5de1b`. Для replay новые HTTP не нужны:

```powershell
node tools/audits/gameplay-boundary-report.mjs verify 175c446a0e513245d9afe37fc7fdc65bc4d4f1dc0d7e4f93068da0cf45f5de1b
```

Не удалять каталог ради повторного collector. Проверку другого источника проводить по отдельному ограниченному плану только при новых полях/описании фаз; расширение случайной выборки само по себе не объяснит семантику.
