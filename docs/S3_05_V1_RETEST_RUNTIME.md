# S3-05/S3-06 — активация и расчёт проверенной модели V1

Формат зарегистрированного retest подключён к общему статусу модели и двум существующим путям расчёта: обычному и назначению первой карты со страниц расписания. Рабочая модель `35aa1dd3-e00c-4dcf-95fa-fbd3b74dba3b` остаётся **неактивной**. Активация в рабочей БД и проверка будущей встречи через интерфейс — следующий отдельный срез.

Основание модели остаётся `conditional_retrospective_unexposed_series`: историческая проверка при восстановленных пятёрках. [Оценка на 664 картах / 332 сериях](S3_03_V1_RETEST_EVALUATION.md) и предыдущий FAIL сохранены. Этот срез не создаёт новую независимую оценку и не доказывает prospective точность.

## Активация и откат

`RetestActivationRegistry` принимает строгий versioned request: UUID запроса, действие `promote` / `rollback` / `deactivate`, ID модели, ожидаемую текущую модель, причину и три digest исходного evidence. Повтор того же запроса возвращает прежнее событие; изменение содержимого при том же UUID отклоняется. Смена активной модели требует совпадения ожидаемого состояния.

При promotion/rollback заново проверяются все сохранённые доказательства, capsule и полный отчёт. Код считывается до и после воспроизведения, затем ещё раз под общей блокировкой реестра. Изменение кода прерывает переход. Событие и активность модели меняются в одной транзакции. Rollback разрешён только к модели с прежним событием активации и заново проверенными доказательствами. Деактивация доступна без воспроизведения backtest, в том числе после изменения кода.

SQL051 добавляет поля retest в общий журнал активации и отдельные проверки связности. Прямое изменение `is_active` без соответствующего события отклоняется; остальные метаданные и исходные доказательства неизменяемы. У старого формата сохраняются прежние проверки. Для перехода между форматами сначала требуется деактивировать текущую модель её штатным механизмом.

## Расчёт и совместимость

`PredictionModelRegistry` выбирает формат на сервере. Клиент не передаёт собственные параметры Elo или доказательство `passed`. Статус API остаётся прежним: наличие подходящей активной модели ещё не гарантирует пригодность конкретной встречи.

При каждом расчёте проверяются неизменяемые метаданные, последнее событие активации и точный профиль текущего кода. Полный backtest не выполняется на HTTP-запросе. Общая блокировка удерживается до сохранения снимка, поэтому деактивация не может обогнать выдачу результата. При изменении кода возвращается `unavailable` / `ACTIVE_MODEL_EVIDENCE_INVALID`, вероятность `null`.

Числовой расчёт использует прежние `buildV1Features` и `eloLink`: 1500/K32/scale400, минимум пять более ранних завершённых pro-карт на игрока, десять разных подтверждённых идентичностей. Сохранены проверки времени, исходных данных, состава, целевого турнира, первой карты и запрет подмены серии одной картой. В снимке фиксируются conditional basis, protocol/report/freeze/candidate/runtime fingerprints и событие активации. Повтор сохранённого запроса после деактивации читает прежний снимок, новый запрос получает `unavailable`.

Исходный freeze не переписывается. Кроме точных добавлений export разрешены ровно два изменения orchestration-модулей по парам исходного/нового SHA в `scripts/lib/v1-retest-runtime-compatibility.json`. Числовой kernel, scorer, quality policy и остальные frozen files сохраняются. Новый профиль admission дополнительно связывает текущие scripts, verifier, ingestion и runtime; произвольное добавление кода в разрешённый файл не проходит проверку.

## Команды владельца

После сборки и миграции:

```powershell
node --env-file-if-exists=.env scripts/retest-model.mjs readiness
node --env-file-if-exists=.env scripts/retest-model.mjs events
node --env-file-if-exists=.env scripts/retest-model.mjs transition .tools/retest-activation-request.json
```

Последняя команда меняет реестр; её не нужно запускать для просмотра готовности. Пример содержимого запроса для зарегистрированной модели (новый `requestId` задаётся при подготовке конкретного перехода):

```json
{
  "requestId": "<новый UUID>",
  "action": "promote",
  "modelId": "35aa1dd3-e00c-4dcf-95fa-fbd3b74dba3b",
  "expectedCurrentId": null,
  "reason": "Явная активация проверенной conditional V1 для личного использования",
  "evidence": {
    "protocolFingerprint": "0d1518cc6446685ddabb4afb880fae72821e93c4aa8444ab1cdb834d853168a9",
    "freezeSha256": "61a718f762d24c9fa98dca1b928797adab411a097d4b6eef04782de5ca7992ab",
    "reportSha256": "8227233077617c91335cc2b53c634cbaebe69bd180a0665d4c336809af3ee790"
  }
}
```

При деактивации `modelId` и `evidence` равны `null`, `expectedCurrentId` — ID активной модели. Для rollback требуется ID ранее активированной модели и её собственные digest. Старый `v1-registry.mjs` обслуживает старый формат; для retest используется новый CLI.

## Проверки и ограничения

Подробные результаты и digest локальных журналов записаны в [evidence](evidence/s3-05-v1-retest-runtime.json). Проверки охватывают повтор/CAS, конкурирующую активацию, rollback, failed challenger, прямой SQL-обход, подделку snapshot, изменение runtime, недостаток истории, неподтверждённые аккаунты и cutoff. Для гонки изменения кода во время replay сначала воспроизведён RED, затем GREEN. Синтетические fixtures применяются только в тестовых БД и не объявляются успешной проверкой реальной модели.

Custom backup рабочей БД реально восстановлен в отдельную БД. В копии активирована настоящая зарегистрированная модель после полного replay. Оба пути расчёта проверены на реальной истории: 2158 подходящих карт, минимум 20 на выбранного игрока; арифметика совпала точно. Сценарий и tournament scope были явно гипотетическими тестовыми объектами. Это не прогноз будущей встречи и не наблюдение live performance. Проверены неизменность повторного результата, деактивация и отказ нового расчёта; копия удалена. После исправления гонки compiled activation/readiness/deactivation повторно прошли на новой восстановленной копии, которая также удалена.

Frozen offline install, typecheck и финальная сборка — PASS; 899 unit/CLI, 240 Node и 60 уникальных PG/API проверок — PASS. В первой PG/API регрессии два теста readiness подменяли старый класс реестра; после исправления spies все четыре теста файла прошли без изменения тайм-аутов. SQL051 применён к рабочей БД после backup/restore-проверки; все прежние строки 84 таблиц, 2232 карты и 14 полных queue rows сохранены, activeModels=0. Из 9703 защищённых файлов 9699 неизменны, оставшиеся четыре — перечисленные выше current barrel/dispatch modules; frozen copies и первые результаты оценок сохранены. Полный PostgreSQL/browser/Python/Docker/Linux набор в этом срезе не повторялся; охват отдельных PG/API файлов указан в evidence. Переносимость на Linux не подтверждена: исходный freeze связан с Windows и Node 22.15.0. Существующее предупреждение Vite о размере chunk остаётся. API/Web/general worker не запускаются; внешних запросов к провайдерам нет.
