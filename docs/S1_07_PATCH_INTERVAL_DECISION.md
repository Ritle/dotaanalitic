# S1-07 — достаточность patch evidence и граница будущего прогноза

Дата review: 2026-11-01. **Решение по существующим данным принято: promotion запрещён.** Ниже отдельно описано предложение изменения контракта; оно не реализовано и не меняет нормативные требования. S1-07 остаётся открытой. Новых HTTP-запросов, записей в БД, моделей и миграций в этом срезе нет.

## Вывод для разработки

По сохранённым источникам нельзя заполнить `released_at`, `coverage_until`, `known_at` для 16 недавних карт. Однако искать точную секунду релиза бесконечно тоже не требуется: доказанный интервал действия версии мог бы установить версию карты вдали от перехода. Для этого нужны доказательства границ, которых сейчас нет, и отдельный контракт, умеющий сохранять неопределённость.

Выявлено независимое ограничение: **действующий resolver не способен подтвердить патч будущей карты на источниках, полученных до расчёта**. Оно останется даже после получения идеального исторического release evidence. Следующий шаг — разделить наблюдаемую сейчас версию и фактическую версию карты, не выдавая предположение о будущем за исторический факт.

## Достаточные факты для действующего контракта

| Поле | Что reviewer должен установить | Чего недостаточно |
|---|---|---|
| `releasedAt` | Момент начала действия конкретной версии, источник явно описывает effective deployment; область применимости включает карту/турнир | Название новости, дата feed, provider index, произвольный запас в 24/48 часов |
| `coverageUntil` | Конечный горизонт подтверждённого действия/полной истории версий с учётом переходов и исключений турнира | «В списке нет следующего патча», момент нашего fetch сам по себе |
| `knownAt` | Подтверждённое время доступности именно используемого утверждения и его scope | Дата статьи как доказательство позднее дополненного JSON, дата ретроимпорта |
| Связь карты и версии | Применимость release history к данной карте либо первичный map/build факт с проверенной связью build→patch | Время старта плюс неполный каталог; nickname/организация/исход карты |

У составного proof все необходимые утверждения должны быть доступны к cutoff. Нельзя взять ранний knownAt объявления и прикрепить к нему позднее установленное coverage. Поздний fetch допустим для ретропроверки только с независимым доказательством ранней доступности соответствующего содержания.

Фактическая версия из завершённой карты может улучшить описательную историю, но не доказывает, что эту версию знали до старта. Hero availability/impact и коэффициенты переноса требуют своих доказательств и оценки; подтверждение patch label не закрывает их автоматически.

## Воспроизведённое противоречие для будущей игры

Контракт [PatchReleaseEvidenceSchema](../packages/contracts/src/game-context.ts) и [SQL011](../packages/db/migrations/011_game_context_registry.sql) требуют `coverageUntil <= fetchedAt`. [resolvePatchAt](../packages/db/src/game-context.ts) требует `mapTime < coverageUntil`. При настоящем расчёте до старта источник может быть получен только к cutoff:

```text
coverageUntil <= fetchedAt <= cutoffAt <= mapTime
resolver requires: mapTime < coverageUntil
```

Оба условия одновременно невыполнимы. Это относится и к mapTime=cutoffAt при coverageUntil=cutoffAt из-за открытой правой границы. Retrospective fetch после карты может пройти эту геометрическую проверку; это не делает поздний fetch допустимым источником онлайн-прогноза.

Проверка выполнена прямым вызовом существующего compiled resolver, на явно синтетическом объекте, без DB: accepted patchId=1, releasedAt/knownAt/eventAt=2026-10-01T00:00:00.000Z; fetchedAt=coverageUntil=cutoffAt=2026-11-01T20:00:00.000Z.

| mapTime | Фактический результат |
|---|---|
| 2026-11-02T19:00:00.000Z | value=null, PATCH_COVERAGE_GAP |
| 2026-11-01T20:00:00.000Z | value=null, PATCH_COVERAGE_GAP |
| 2026-11-01T19:59:59.000Z | value=1, reason=null |

Это проверка логики, не live patch evidence и не оценка модели. Удалить только SQL CHECK или увеличить coverage до бесконечности — недостаточное исправление: так утверждение о будущем станет ложным подтверждённым фактом.

## Предложение: два независимых вида сведений

**Не реализовано.** На следующем шаге подготовить узкое изменение нормативного контракта и acceptance cases:

1. `effective_patch_at_map`: подтверждённая фактическая версия карты/интервала, источник и его реальная доступность. Применение к историческим признакам всё равно проверяет knownAt. Предположения не проходят этот канал.
2. `patch_observed_at_cutoff`: версия, подтверждённая источником к моменту расчёта, с observed/event/known/fetched, scope и revision. Само наличие последней новости не подтверждает активную версию. Допущение «карта будет сыграна на этой версии» хранится отдельно как условие сценария, а не как coverage фактического интервала.
3. Если будущая модель использует такое условие, обучение и temporal evaluation должны воспроизводить ровно информацию на cutoff, учитывать переходы/задержки/турнирные исключения и отдельно оценивать этот режим. До реализации и прохождения gates вероятность остаётся unavailable. Плановая дата серии не становится известным временем старта отдельной карты.
4. Наблюдение, полученное сегодня, может поддерживать будущий расчёт в своей области применимости, но не заполняет historical knownAt вчерашней карты. При новом патче/конфликте создаётся новый snapshot; старые predictions неизменны.

Это изменение semantics, а не снятие требования проверенного источника. Автоматизация сбора и обучение в scope этого решения не входят. Действующий resolver и schema остаются прежними.

Минимальная матрица для следующего контракта:

| Ситуация | Обязательный результат |
|---|---|
| Активная версия подтверждена до cutoff, карта ещё впереди | Наблюдённая версия доступна; фактическая версия карты неизвестна; условие сценария явно отдельно |
| Есть только patch notes или coarse code | Active-version proof отсутствует, нет автоматического fallback |
| Единственный proof впервые доступен после cutoff | Исключить из этого as-of snapshot |
| Объявлен будущий переход или есть противоречивые источники | Не продлевать текущую версию через переход; unknown/conflict по соответствующему scope |
| Срок свежести истёк либо время карты перенесено | Повторная оценка доступности; TTL сам по себе не доказывает неизменность версии |
| После карты выяснилась другая версия | Отдельный actual-version факт и аудит drift; исходный prediction snapshot неизменен |
| Historical evidence с точными границами уже принято | Старый resolver/результаты сохранены; cohort будущего сценария не смешивается с ним молча |

## Возможный ограниченный контракт неопределённых границ

Для исторической effective version возможна отдельная доказательная модель: реальный переход R находится в подтверждённом диапазоне `[L,U]`. Для версии P между соседними переходами безопасная внутренняя область имеет вид `[U_P,L_next)`, **только если** доказаны связь границ с deployment, полнота последовательности и применимость к турниру. Интервалы неопределённости на переходе исключаются; при конфликте или пересечении нет выбора последней записи.

- Даты feed/Steam не являются L/U автоматически. Их расхождение не задаёт доверительный интервал; фиксированный отступ в сутки не заменяет доказательство.
- Для последней версии допустим конечный доказанный горизонт H вместо следующего перехода, но H нельзя взять из времени fetch без подтверждения scope. Ожидать выхода следующего патча само по себе не требуется.
- Если U_P >= L_next, безопасного внутреннего интервала нет. При R точно известном L=U его граница включается слева; правая граница исключается.
- Для ретропрогноза evidence о нужной области должно быть доступно к cutoff. Будущий релиз не может задним числом сертифицировать раннее знание текущего coverage.
- Нельзя записать U вместо точного releasedAt в существующую таблицу. Потребуются явный вариант evidence, новая policy/revision и forward-only migration, если вариант будет принят. Исторические SQL001–022 не менять.

**Решение сейчас:** не реализовывать интервальный registry до появления хотя бы одного пригодного источника границ. На имеющихся данных он сохранит тот же результат: 16/16 unknown. Проблему будущего cutoff этот вариант сам по себе не исправляет.

## Что остаётся заблокированным и что работает

Работают расписание, ожидаемые заявки, ручной выбор состава и описательная pro-статистика. Patch-specific raw filters и подтверждённый перенос между патчами требуют canonical evidence. По последнему сохранённому inventory 36 real pro maps дают 0 strict eligible для обоих stages; отсутствует также pre-start lineup/teams context, для post-draft — требуемые hero facts. Устранение patch-ограничения не делает эти карты автоматически пригодными и не заменяет достаточную выборку, backtest или calibration.

Точное влияние упрощения на точность неизвестно: обученной и проверенной модели для сравнения нет. Обещать проценты или фиксированное ухудшение нельзя.
