# S1-18 — сквозная проверка предстоящей встречи

Один browser workflow проходит весь путь через существующие формы и API: owner login → расписание/ожидаемые заявки → ручной canonical выбор10 игроков/ролей/stand-in → сравнение с историческим периодом → сохранение сценария → Draft Lab с10 различными героями → сохранённый описательный отчёт → обновление pro-истории → повторное чтение старой версии и новый расчёт.

Тест использует настоящий PostgreSQL, Fastify, session/CSRF, pg-boss и report readers; transport расписания/истории явно синтетический. Все строки создаются только в disposable DB. Это интеграционная QA, не live coverage, training cohort или доказательство качества прогнозов.

## Проверяемые границы

- Расписание и турнирная заявка не заполняют canonical состав автоматически. До ручного выбора/подтверждения сохранить сценарий нельзя. Provider team/league IDs не становятся canonical IDs.
- В сравнение вручную передаются десять игроков и роли; одна замена не даёт штрафа. В сценарии и после Draft Lab сохраняются те же canonical ID/роли/stand-in flags; expected baseline, A/B→Radiant/Dire и first-pick остаются неизвестными.
- Сравнение с from2024-01-02/cutoff2024-01-03 имеет N1. Сценарий получает свой cutoff при сохранении; исторический cutoff сравнения не переносится. Отчёт с отдельно выбранным from2024-01-01 и cutoff сценария имеет N2. На UI рядом с сохранением добавлено явное пояснение об этих разных периодах.
- Все10 героев выбраны вручную. Доступность остаётся unknown при отсутствии подходящих подтверждений; сохранение hypothetical draft не выдаёт forecast или проверенный draft order.
- Импорт двух дополнительных pro-карт увеличивает глобальный pro-корпус4→6, а target отчёта2→4. История организации N4 остаётся отдельно от exact-five N2; новые неизвестные accounts не склеиваются с выбранными игроками.
- GET старого analysis после перехода на страницу организации/refresh и полной загрузки прежнего URL возвращает весь прежний DTO, resultHash, source/input snapshot и N2. Новый расчёт создаёт version2 с N4 и новым hash при той же scenario revision2; version1 остаётся доступной по своему URL. Создан ровно1 сценарий, training datasets0, prediction status unavailable/model+probability null.

## Найденное и изменения

Новый `apps/web/tests/e2e/upcoming-workflow.spec.ts` сохраняет этот regression path. В `UpcomingScenario.vue` добавлено только пояснение разделения периодов; backend/contracts/SQL/dependencies/lockfile не меняются.

Первый прогон остановился на неверном exact-label селекторе теста: в accessible name поля начала периода входит поясняющий `<small>`. Селектор исправлен на уникальный префикс, добавлены bounded action timeout и ожидание analysis ID в URL.

Второй прогон выявил конфликт составной фикстуры: seedScenarioReports явно вставляет league ID1, но serial остаётся last_value1/is_called=false. Следующая штатная вставка importer-а получает23505/leagues_pkey. Отдельная изолированная диагностика воспроизвела это точное ограничение. В setup только новой disposable DB sequence согласован с max fixture ID перед worker import. Production importer, retry policy и ограничения не ослабляются; миграции001–020 сохраняются.

Итоговые реально исполненные команды и результаты записаны в [PROGRESS](PROGRESS.md) и [PROJECT_STATE](PROJECT_STATE.md). Проверка включает отсутствие pageerror и горизонтального overflow отчёта на360px. Рабочие данные/owner не создаются; S1-07/S3-01/corpus/model gates остаются открытыми.
