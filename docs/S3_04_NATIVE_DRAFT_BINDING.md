# S3-04 — привязка снимка драфта к Dota-карте

Реализован `player-hero-native-target-binding`: владелец может проверить сохранённый снимок драфта по **native Dota match ID**. При совпадении сохраняется отдельная неизменяемая запись. Исходный драфт, аккаунты и история снимка не переписываются. Прогноз после драфта этим действием не включается.

## Использование

1. Откройте сохранённую карту в Draft Lab. Полный драфт должен иметь серверный снимок.
2. В блоке «Снимок драфта» раскройте «Связать снимок с сыгранной картой».
3. Укажите числовой Dota match ID из OpenDota или STRATZ и нажмите «Проверить карту».

Проверяется **завершённая карта из локальной профессиональной истории**. Если её ещё нет, интерфейс предлагает обновить историю и повторить проверку. Новый endpoint не делает HTTP-запросы провайдерам и не запускает импорт автоматически.

После успеха показываются ID, дата проверки и результат сверки; поле ввода скрывается. При повторном открытии читается сохранённая связь, повторно вводить ID и подтверждать пятёрки не нужно. Несохранённые правки блокируют новую проверку старой редакции. Поздний снимок помечается явно.

В этом срезе «известный ID» — уже сохранённая проверенная связь этого снимка. Автоматическое извлечение native ID из расписания PandaScore не реализовано: предыдущий [пилот](S3_04_DRAFT_TARGET_SOURCE_PILOT.md) эту связь не подтвердил. Ручной ID — указание кандидата владельцем, не доказательство совпадения с выбранной встречей расписания.

## Проверка и границы

- Снимок проверяется по SHA; учитываются его собственные decision cutoff и server recordedAt с шестью знаками микросекунд.
- Целевая карта должна иметь положительно установленный pro-статус и пройти существующий `OutcomeVerifier`. Неизвестный/public/conflict исход не принимается.
- Сверяются native ID, время карты в canonical rows и OpenDota receipt, десять разных аккаунтов, героев и корректных слотов; canonical players должны совпасть с source receipt. A/B сопоставляются со сторонами через команды и участников, не через порядок массива.
- Проверяются именно account→hero→side выбранной редакции. Подмена игрока, героя или стороны даёт `unavailable` с причинами.
- В JSON фиксируются data revision, receipt ID/SHA, часы проверки, candidate evidence и SHA всей записи. Старое свидетельство не обновляется при позднем исправлении истории; это датированный аудит проверки, не обещание актуальности источника навсегда.
- Неизвестные map ordinal, provider-series mapping и точная граница gameplay start остаются неизвестными. Наличие native ID **не закрывает** эти условия. Всегда `scheduleMappingVerified:false`, `mapOrdinalVerified:false`, `prestartVerified:false`, `primaryEligible:false`, `deployable:false`.
- Сравнение с provider start строгое: равенство/позднее время не проходят. Даже «раньше provider start» остаётся `before_provider_start_semantics_unverified`.
- История и признаки снимка не дополняются поздним исходом цели. Никакого training/prediction/scoring/активации модели нет. V1 Elo работает отдельно.

Один снимок имеет не более одной успешной связи. Другой ID после успеха даёт409; для другого сценария/исправленного драфта сохраните новую редакцию. Неуспешные попытки сохраняются отдельно, после обновления данных доступна новая проверка. Несколько снимков одной карты не становятся несколькими обучающими примерами; этот срез не строит датасет или статистику точности.

## API и хранение

Owner-only `GET /api/v1/scenarios/:id/draft-captures/:revision/native-binding` возвращает `{binding, latestAttempt}`, оба поля nullable. Нет/чужой снимок —404. Обычный пользователь —403.

Owner+CSRF+Origin `POST` по тому же пути принимает строго `{requestId: UUID, matchId: decimal string}`. ID до PostgreSQL BIGINT передаются строками. Нельзя передать source evidence, timestamp, результат или eligibility. Успешно обработанная проверка возвращает200 с `status: verified|unavailable`; некорректный ввод400, конфликт UUID/уже проверенной карты409.

Одинаковый requestId возвращает тот же результат, в том числе после потери HTTP-ответа и создания новой редакции сценария. Новый requestId с тем же уже проверенным ID также читает прежнюю связь. После `unavailable` повторная оценка обновившихся данных требует нового requestId; UI делает это сам. При сетевой ошибке UI сохраняет исходный UUID для безопасного повтора.

SQL059 добавляет `owner_draft_native_bindings`, append-only trigger, серверный recordedAt, SHA/owner/capture/eligibility guards и unique partial index одной verified-связи. Попытки атомарны в repeatable-read транзакции с блокировкой снимка; serialization/unique races повторяются ограниченно. Предел evidence2MiB, statement timeout30s/lock timeout10s. Исторические SQL001–058 не изменены.

Новые модули изолированы в `apps/api/src/modules/scenarios/draft-native-*`; shared db/contracts barrels, feature builders, старый offline target verifier не менялись. UI — `DraftNativeBinding.vue`, вложенный в `DraftCapture.vue`.
