# S3-04 — составное подтверждение турнира, v2

15 ноября 2026. Реализован отдельный **offline-контракт проверки свидетельств** и файловая CLI. Новый формат больше не требует URL календарной статьи внутри JSON OpenDota. Старые registration v1, SQL063, collector/journal/transport/runtime сохранены без изменений. **Новый отчёт ещё не принимается хранилищем регистрации; регистрация и сбор этим шагом не разрешаются.**

Исходная проблема описана в [live-preflight](S3_04_CONDITIONAL_COLLECTION_LIVE_PREFLIGHT.md): каталог OpenDota содержит ID и название, но не календарную ссылку. Простое удаление проверки ссылки превратило бы регистрацию в сопоставление только по имени, запрещённое политикой независимой выборки.

## Новый контракт

Файлы:

- [conditional-tournament-binding-v2.mjs](../tools/research/conditional-tournament-binding-v2.mjs): строгая схема и детерминированный валидатор.
- [inspect-tournament-bindings-v2.mjs](../tools/research/inspect-tournament-bindings-v2.mjs): чтение файла по ожидаемому SHA, проверка и эксклюзивное создание отчёта без HTTP/БД.
- [Тесты](../tests/node/conditional-tournament-binding-v2.test.mjs): положительные синтетические свидетельства и отрицательные границы.
- [Результаты проверок и SHA](evidence/s3-04-tournament-binding-v2.json).

`conditional-tournament-binding-review-v2` содержит SHA неизменной политики, время подготовки/проверки, nullable reviewer UUID, признак синтетики, сохранённые источники и до двух проверок заранее выбранных выпусков. У каждого источника сохраняются URL, исходное UTF-8 тело, SHA, фактическое время получения, HTTP200 и `knownAt:null`. Время загрузки не превращается в историческое время доступности.

Для каждого выпуска нужны три самостоятельных свидетельства:

1. **Календарь организатора.** Точный URL статьи из политики, дословные выдержки о выпуске и периоде, рассмотренные владельцем даты и консервативная нижняя граница начала. Даты должны совпадать с политикой; граница должна оставаться в будущем на момент проверки и не быть позже начала календарного дня турнира.
2. **Каталог native ID.** Исходный JSON точного endpoint `https://api.opendota.com/api/leagues`, выбранный десятичный ID, единственная запись этого выпуска, статус professional/premium. Этот статус подтверждает только классификацию источника; Tier1 задаётся прежним явно выбранным списком, а не автоматически выводится из tier.
3. **Явная связь от организатора.** Сохранённая страница соответствующего организатора, содержащая рассмотренный владельцем фрагмент с точным выпуском, годом и HTML-ссылкой `https://www.opendota.com/leagues/<ID>` либо `https://opendota.com/leagues/<ID>`. Страница может отличаться от календарной статьи. Номер должен совпадать с записью исходного каталога.

Это первый поддержанный способ составного доказательства. **Наличие таких ссылок на реальных страницах пока не подтверждено.** Другие способы — например, проверенная структурированная связь из дополнительного API — потребуют проверки реального формата источника и отдельного адаптера; произвольные названия полей или пространства ID не угадываются. Совпадение названия, одинаковые участники или флаг «проверено» сами по себе связь не устанавливают.

Даты в текстовых выдержках не извлекаются автоматически: их смысл проверяет владелец. Проверка буквального HTML-фрагмента тоже не является DOM-анализом, подписью удалённого сайта или доказательством подлинности самостоятельно подготовленного файла. Граница доверия явно записана как `owner_reviewed_retained_sources_not_remote_signature`. При подключении к регистрации потребуется аутентификация действующего владельца и проверка происхождения сохранённых источников, а не доверие одному флагу отчёта.

## Отказы и ограничения

Неизвестные поля входа запрещены. Отсутствующий материал даёт `unavailable` с причинами, а не выдуманные сведения. Сломанные SHA, неизвестные ссылки на источники, дублирующиеся ключи JSON, небезопасные числовые ID, повторные ID/выпуски и будущие относительно review часы отклоняют весь вход.

Названия сравниваются без нечёткого поиска; qualifier/Division2 и другой выпуск не проходят. Два одноимённых native ID считаются неоднозначностью. В ссылке проверяется настоящий атрибут `href`, а не `data-href`, URL в `title` или строка текста; дублирующиеся атрибуты отклоняются. Границы названия и года не позволяют принять Season300 за Season30 или12026 за2026. Ссылки с credentials/query/fragment, посторонние host и неизвестное представление payload не принимаются.

Пределы: 12 источников, 16 МиБ на исходное тело, 32 МиБ на весь вход, 30 000 записей каталога, глубина JSON100. Это пределы локальной проверки источников; они **не меняют** 1 МиБ HTTP/64 МиБ журнала существующего сборщика.

Успешная структурная проверка возвращает `reviewed_bindings_only` и `bindingsReady:true`. Это относится только к данному рассмотрению источников. Даже при успехе:

```json
{
  "ownerAuthenticated": false,
  "registrationReady": false,
  "registrationPerformed": false,
  "collectionAllowed": false,
  "realEvaluationAllowed": false,
  "activationAllowed": false,
  "deployable": false
}
```

Синтетические положительные случаи явно маркированы и не являются настоящей регистрацией. Истёкший deadline блокирует общую готовность даже при достаточных отдельных свидетельствах.

## Файловая проверка

```powershell
node tools/research/inspect-tournament-bindings-v2.mjs inspect .tools/review/input.json <SHA256> .tools/review/report.json
```

Нужен существующий подкаталог `.tools`; исходный файл и разрешённый путь результата проверяются через realpath. Команда ничего не загружает, не обращается к БД, не перезаписывает существующий отчёт и не принимает `--register`. Время проверки берётся из текущих часов процесса. Сохраняется компактный отчёт без тел источников; stdout содержит только статус/готовность/SHA. Код0 означает успешное выполнение проверки, включая результат `unavailable`; код1 — неверный вход или невозможность безопасно записать новый отчёт. Ошибка на русском без исходных данных и путей.

- BLAST `20208` остаётся кандидатом, подтверждённый ID в отчёте — null.
- Нужные дословные календарные материалы и ссылка организатора в этот review-пакет не приложены; reviewer UUID также null. Это не утверждение, что календарных статей не существует: их веб-проверка предыдущего шага не подменяет сохранённый исходный документ.
- DreamLeague30 main ID по-прежнему отсутствует в этом каталоге.
- Реальные записи `20144`, `20250`, `20359`, `20511` отклонены как qualifiers/Division2 другого scope. В отличие от положительных unit-тестов, это отрицательная проверка на сохранённых реальных данных.

Отдельные PG/browser/численные Python-проверки не повторялись: код БД, интерфейса и модели не менялся. Первоначальные отказы CLI из-за будущего времени синтетической фикстуры и дополнительные отрицательные случаи href/границ названий исправлены и повторно проверены.
