# S3-07/V1-scheduled-target-lifecycle — отмена и повторное открытие встречи

На странице сохранённого назначения владелец может отметить отмену и повторно открыть встречу PandaScore. Состояние относится к `owner / providerMatchId / map1` и действует для всех сохранённых редакций встречи. Новая дата, новое сопоставление команд или отсутствие в частичном ответе расписания не отменяют ручную отметку автоматически.

## Действия владельца

1. Открыть `/schedule-targets/:targetId`. Блок «Состояние встречи» доступен и до первого расчёта.
2. Указать HTTP(S)-источник, причину и, если известна, дату события в UTC ISO с миллисекундами. Неизвестная дата остаётся пустой. Подтвердить изменение состояния всей встречи.
3. Сохранить отмену. Следующее допустимое действие — повторное открытие; далее действия чередуются. Любая правка формы или изменение текущей редакции снимает подтверждение.
4. Для учёта изменений в статистике создать новый отчёт журнала. Сохранённые отчёты продолжают показывать зафиксированное при их создании состояние.

Отметка является сообщением владельца, а не независимо проверенным фактом провайдера. Сервис не скачивает указанный URL. `eventAt` — заявленное время события или null; `recordedAt` — фактическое серверное время сохранения и доступности отметки. Будущая дата события отвергается. Заднее число не меняет старые отчёты.

## Выдача прогнозов и результаты

- Пока последняя отметка — `cancelled`, новая попытка расчёта сохраняется как `unavailable`, с `TARGET_OWNER_CANCELLED` и null вероятностью. Повтор старого запроса возвращает его исходный снимок.
- `reopened` возвращает обычные проверки источника, начала игры, состава, Tier1 scope, истории и активной модели. Само открытие не выдаёт прогноз и не снимает запрет после известной сыгранной карты.
- Если для встречи когда-либо подтверждалась карта, отмена остаётся в аудите, но не исключает её из статистики. Это действует для всех редакций назначения, до первого outcome refresh и после последующих неподтверждённых исправлений источника.
- Сама сохранённая связь с картой не создаёт scoring outcome: для метрик по-прежнему требуется текущая проверка исхода и допустимый прогноз до старта. При отсутствии отдельной сверки интерфейс показывает, что связь известна, а результат этой попытки ещё требует проверки.
- Счётчик отмен считает уникальные встречи среди отфильтрованных попыток, а не редакции, пересчёты или события. Отмена до первого прогноза видна в истории встречи, но не создаёт строку прогнозного журнала.

## Хранение, API и совместимость

SQL034 добавляет append-only `v1_scheduled_lifecycle` с revision, UUID/hash запроса, event text/SHA, цепочкой предыдущего SHA и серверным временем. UPDATE/DELETE/TRUNCATE запрещены. SQL проверяет владельца и сохранённое назначение, переходы, revision/CAS, время и цепочку. Исторические SQL001–033 не изменяются.

Запись события сериализуется с захватом журнала через owner journal lock, а с выдачей прогноза и сопоставлением карты — через существующий owner schedule-result lock. Проверка текущей отмены есть и в runtime, и независимо в SQL `guard_v1_scheduled_issuance`. Прежняя защита SQL033 от выдачи после подтверждённой сыгранной карты сохранена.

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/v1/schedule-targets/:targetId/lifecycle?beforeRevision=N` | До20 записей, exclusive revision cursor и признак ever-verified связи |
| POST | `/api/v1/schedule-targets/:targetId/lifecycle` | Добавить подтверждённую владельцем отмену/открытие |

POST body: `requestId`, `expectedRevision`, `action`, `eventAt`, `sourceUrl`, `reason`, `confirmedByOwner:true`. Owner и target reference определяются сервером из сессии и пути; outcome/model/recording-clock/redirect fields запрещены. Все маршруты требуют owner/session и no-store; POST защищён Origin/CSRF и лимитом6/min. Admission guard ограничивает параллельные HTTP-записи до ожидания DB-lock.

При потере ответа повторяется тот же UUID/body, включая исходную `expectedRevision`. Даже если встречу уже открыли другим запросом, повтор старой отмены возвращает её первоначальное событие. Конфликт требует перечитать историю и заново подтвердить действие. Клиент не меняет expectedRevision незаметно. История общая для редакций встречи; nonce из другого пути не перенаправляет запись.

Новые отчёты используют `v1-journal-input-v3` / `v1-journal-report-v3`, policy `owner_reported_verified_binding_precedence_v2`. Кроме прежних наблюдений и lifecycle OpenDota фиксируются последние события PandaScore и точный inventory сохранённых связей с картами. SQL требует полный соответствующий inventory; нельзя скрыть связь, удалив её из нового отчёта. Первичный прогноз по карте выбирается глобально до фильтров прежним ядром; формулы метрик не меняются.

V1/V2 inputs/reports читаются и воспроизводятся прежними pure builders. OpenDota lifecycle CLI сохраняет прежний контракт. Frozen E0/E1/V1 artifacts, archived release executor и inference/history kernel остаются прежними. Новая модель не обучается и не активируется.

## Границы и следующий шаг

Автоматическая отмена по неполному расписанию, автоматическая проверка URL, исправление ошибочного cross-provider binding и автоматический пересчёт отчётов не входят в этот срез. Вероятность требует независимого release gate и активной модели; текущий этап проверяет протокол на синтетических fixtures, не точность прогноза.

Следующий точный срез: **S4/V1-acceptance-audit** — сверка реализации утверждённого V1 с требованиями и приёмкой, воспроизводимый локальный запуск и проверка полного owner flow. Будущую независимую оценку модели учитывать отдельным незавершённым gate. Рекомендуемая модель: **GPT-6.1 Sol · High**; при обнаружении противоречий temporal/model gates вернуться к Astra.
