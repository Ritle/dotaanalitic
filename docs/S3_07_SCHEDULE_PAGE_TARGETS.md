# S3-07 — назначение первой карты со страниц расписания

Продолжение сверки ТЗ 6 ноября 2026: закрывается ограничение S1-16, из-за которого встречи страниц 2–50 можно было сравнивать, но нельзя было назначать для предматчевого расчёта. Условия допуска V1, Tier1 scope, выбранные десять аккаунтов, история и независимая оценка модели сохраняются.

## Использование

На любой загруженной странице выбрать встречу и раскрыть «Зафиксировать назначение первой карты». Проверить двух участников, сопоставить локальные команды, указать источник и подтвердить назначение. После сохранения открыть назначение и выбрать сохранённый сценарий для карты 1. Это прогноз одной карты; победитель BO3/BO5 не рассчитывается. При отсутствии активной проверенной модели попытка сохраняется как unavailable с null probability.

«Свежесть расписания» показывает номер страницы источника и обновляет именно её. Переход встречи между страницами не требует переписывать прежнее назначение, если содержание самой встречи совпадает. Смена участников, времени или других полей требует новой проверенной редакции. Отсутствие в позднем частичном ответе не считается отменой и не продлевает срок актуальности.

## Источник и совместимость

Policy `schedule-pages-source-v2` использует последние 200 сохранённых наблюдений. На каждой странице выбирается последнее наблюдение, содержащее встречу; между ними — самое свежее fetchedAt, с детерминированным разрешением равенства по recordedAt/page/id. Поздно записанный старый ответ той же страницы не позволяет откатиться к её прежнему свежему ответу. Полнота календаря не утверждается; при превышении ограниченного поиска возвращается понятная ошибка.

Миграция 048 добавляет объединяющее read-only view и отдельный nullable `page_observation_id` с FK. Ровно одна ссылка источника обязательна: исходная первая страница либо отдельный журнал страниц 2–50. Числовые ID этих журналов могут совпадать; namespace проверяется таблицей и точным endpoint. JSON, SHA, fetched/recorded clocks, knownAt=null и исторические источники не переписываются. Новые записи получают warning `SCHEDULE_PAGES_SOURCE_V2`; новый runtime binding — `v1-schedule-runtime-binding-v2`. Старые форматы читаются прежними readers.

Новые модули `schedule-page-targets/binding/runtime/freshness/service` образуют отдельный адаптер. Исходные зарегистрированные модули, model/history kernel, артефакты, пороги и даты release protocol остаются байт-в-байт прежними. Новый runtime фиксирует фактические code hashes. Проверки SQL распространяются и на старые CLI: они не могут выпустить прогноз по устаревшей первой странице, если новое наблюдение уже находится на другой. Для новых многопостраничных назначений используется HTTP/UI-адаптер; исходная CLI не получает скрытую новую семантику.

Owner/session/CSRF, CAS ревизий, exact UUID/hash retry, блокировка на время публикации, общий предел одновременных расчётов, отмена владельцем, verified-result guards и неизменяемость прогнозов сохранены. Истечение пяти минут проверяется при записи после вычисления; отказ откатывает попытку целиком. Дополнительных provider endpoints, автоматического обхода календаря или polling нет. Миграции 001–047 не меняются.

## Приёмка

Проверяются API/SQL на двух namespaces с совпадающим ID, настоящий endpoint, страницы 2–50, перемещение встречи, более поздний старый ответ, пропуск встречи, изменение участников/начала, отсутствие модели, повтор после изменения источника, owner isolation, SQL forgery и immutable history. Browser-проверка сохраняет назначение страницы 2, открывает его, обновляет только страницу 2 и проверяет 360px. Положительный runtime/gate сценарий использует только synthetic doubles в отдельной тестовой БД и не подтверждает качество реальной модели.

Итоги исполненных проверок и рабочей установки дописываются в PROGRESS после завершения QA. Следующий функциональный срез до окна сбора — рабочие owner-reviewed Tier1 scopes; независимый сбор V1 начинается 20 ноября 03:00 МСК, оценка не ранее 2 декабря 03:00 МСК. Дата сама по себе не разрешает активацию.
