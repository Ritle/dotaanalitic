# S3-04 — сохранение регистрации v2

15 ноября 2026. Добавлен внутренний адаптер сохранения пакета с [составными свидетельствами v2](S3_04_TOURNAMENT_BINDING_V2.md) и forward-only миграция066. Это хранение проверенного плана с отдельной commit-квитанцией. **Реальный план не зарегистрирован, сбор и оценка модели не включены.** Миграция применяется при проверках только в отдельных тестовых БД; рабочая схема не обновляется этим шагом.

## Путь записи

- [conditional-real-registration-v2.mjs](../tools/research/conditional-real-registration-v2.mjs): схема полного пакета, проверка источников, неизменной политики/модели/исключений и фактического исполняемого окружения.
- [conditional-real-registration-v2-store.mjs](../tools/research/conditional-real-registration-v2-store.mjs): внутренние `register(ownerId, packageText, sha)` и `read(ownerId, registrationId)`.
- [066_conditional_registration_v2.sql](../packages/db/migrations/066_conditional_registration_v2.sql): версионная маршрутизация проверок INSERT, проверка v2 в SQL и запрет прежнего сборщика для нового формата.

Новый `conditional-real-registration-package-v2` содержит исходный review v2, а не его диагностический отчёт или флаг `bindingsReady`. Формат источников не преобразуется в фиктивный v1 JSON. `reviewerUserId` должен совпадать с действующим владельцем, а `syntheticOnly:true` отклоняется. Сервер заново проверяет источники на своих часах.

Первая транзакция блокирует строку активного владельца от конкурентного изменения роли, использует общий с v1 advisory lock политики, проверяет пакет, актуальный реестр исключений, хеши исполняемых файлов и реальную Node/Python-среду. SQL повторно проверяет ограничения при INSERT и сам записывает время и ID транзакции. Значения `recorded_at`/`writer_txid` от вызывающего кода не принимаются как достоверные.

Обе пишущие транзакции явно используют `READ COMMITTED`. SQL v2 отклоняет другие режимы: при `REPEATABLE READ` snapshot, открытый до импорта новой карты, мог бы скрыть её даже после захвата блокировки inventory. Этот случай воспроизведён отдельным отрицательным тестом. Чтение уже сохранённого плана использует repeatable-read и не пересчитывает исторические исключения по сегодняшней БД.

Вторая транзакция наблюдает уже сохранённую запись, повторно проверяет владельца, срок, источники, исполняемое окружение и локальные исключения, затем добавляет квитанцию. Запись и квитанция должны иметь разные transaction ID; savepoint не является подтверждением commit. `synchronous_commit=on`, время ожидания блокировок ограничено.

## Совместимость и повторные запросы

Оба формата используют существующие `conditional_real_registrations` и `conditional_real_registration_receipts`. **Один UNIQUE(policy_sha256) защищает оба формата**, в том числе прямые SQL-вставки и repeatable-read транзакции. Две параллельные регистрации v1/v2 не могут получить разные записи для одной политики.

SQL066 сохраняет функции SQL063 и направляет старые INSERT в прежние проверки. Для v2 используются отдельные функции. Неизменяемость UPDATE/DELETE/TRUNCATE продолжает обеспечиваться прежними функциями. Файлы SQL001–065 и старые исполняемые модули не переписываются; новые источники проверяются новым адаптером.

Повтор того же завершённого пакета возвращает тот же результат даже после срока регистрации. Он не создаёт новую квитанцию и не пересобирает сохранённые входы. Изменённый пакет для той же политики отклоняется. Если запись успела зафиксироваться, а квитанция — нет, остаётся `commit_unconfirmed`: повтор может завершить её только пока действуют сроки и не изменились необходимые условия. Если локальные карты/серии пополнились между транзакциями, завершение со старым реестром исключений отклоняется; исходный план не переписывается.

Старый reader отклоняет v2, новый — v1: формат не угадывается и не приводится молча. Совместимость означает сохранение старого пути, а не возможность дать старому consumer новые входы.

## Проверки и границы доверия

Проверяются SHA политики/кандидата, полные исключения базового реестра, бюджеты, временное окно, deadline, происхождение и SHA исходных свидетельств. В SQL отдельно проверяются обязательные поля, raw JSON, числовые ID, уникальность, выпуск/этап, календарь, нижняя граница старта, ссылка организатора, владелец и актуальный локальный inventory. Отсутствующие body/hash не должны проходить через неопределённый результат SQL-сравнения с NULL.

Фактическая проверка файлов и Python/Node-среды выполняется серверным адаптером. SQL не удостоверяет содержимое файловой системы и не получает сетевую подпись организатора. Смысл календарной выдержки и связь ссылки с выпуском остаются частью явной проверки владельцем; хеши сами по себе не доказывают подлинность подготовленного им документа. На стороне источников пока подтверждён только отрицательный реальный пример: имеющихся материалов недостаточно для привязок обоих турниров.

Результат сохраняет `collectionAllowed:false`, `realEvaluationAllowed:false`, `activationAllowed:false`, `deployable:false`. Прямой INSERT журнала прежнего сборщика для регистрации v2 отклоняется SQL с `conditional_v2_collection_not_implemented`. Публичного HTTP или CLI для регистрации здесь нет. API приложения, прогнозы V1 и модель после драфта не менялись.
