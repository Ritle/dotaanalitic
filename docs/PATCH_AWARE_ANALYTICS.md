# Patch-Aware Analytics — требования к версии игры и весам истории

**Статус:** утверждённое требование Personal MVP 2.0. Реализация по задачам S0-01, S1-02, S2-04, S3-02, S3-04. Это проектирование; значения коэффициентов ниже — стартовые гипотезы, не проверенные параметры модели.

## 1. Цель и область действия

Не считать матчи разных эпох Dota 2 равнозначными. Использовать более новую и мета-релевантную историю для оценок героев, пар героев, контрпиков и post-draft модели, сохраняя долгосрочные сигналы силы команд/игроков для pre-match модели.

**Не путать:**
- `display_filter`: явная статистика выбранного патча; только матчи этого патча и *сырые* `wins/games`, без скрытого подмешивания.
- `model_weight`: служебный вес старых матчей при вычислении признаков и/или обучении; может включать несколько патчей. Выводить это как **скорректированную оценку**, рядом показывать N, эффективное N, долю актуального патча и использованное временное окно.
- `training_sample_weight`: при необходимости отдельные веса наблюдений в функции потерь; нельзя механически переносить веса метрик и ожидать улучшения. Проверять на holdout.

## 2. Metadata и временная истинность

`patches` хранит `label`, точный UTC `released_at` (если подтверждён), `patch_type` (`major|minor|hotfix|unknown`), источник, `release_source_url`, `source_revision`, `metadata_updated_at`. Таблица `patch_hero_impacts` хранит *подтверждённые* изменения героя по конкретному патчу с `impact_level` (`minor|moderate|major|rework`), ссылкой на источник и примечанием.

Определять `matches.patch_id` по моменту `matches.started_at` и подтверждённой истории начала действия обновления: последний патч с `released_at <= started_at`. Для неоднозначных дат/данных сохранять `NULL` и предупреждение, а не подставлять текущий патч. Проверять границы публикации патча, включая матчи на переходе. Патч `unknown` не означает `unchanged`.

Источники: OpenDota/dotaconstants для кода патча/метаданных; первичные заметки Valve `https://www.dota2.com/patches/` или официальные анонсы для изменённой механики; данные из сторонних каталогов перепроверять. Обновлять registry при выходе патча; прогноз не должен молча ссылаться на старый как на текущий.

## 3. Политики актуальности — два разных набора

| Вид признака | Что ценнее | Что уменьшаем | Примечание |
|---|---|---|---|
| Pre-match: Elo и сила команды | Недавние игры **текущего состава** | Давность, изменения состава | Патч — дополнительный фактор, не обнуляет командную историю |
| Pre-match: личная форма/позиция | Текущий игрок/роль, последние игры | Старые команды, старые роли | Можно использовать более длинное окно с отдельной метрикой |
| Post-draft: сила героя и player×hero | Текущий патч, релевантная роль | Старые патчи, изменения героя | После серьёзного переработки героя переносимость может стать почти нулевой |
| Post-draft: союзные пары и контрпики | Текущий патч и близкая мета | Существенные изменения баланса, предметов и механик | Обязательно учитывать N и перекос состава противников |

Нельзя автоматически считать две соседние буквенные версии одинаковыми; маленькое обновление иногда существенно меняет одного героя. Нельзя считать все крупные патчи одинаково «разрушительными». Для MVP допустима ручная маркировка важности патча и отдельных героев; автоматический NLP-анализ patch notes — вне MVP.

## 4. Базовая формула весов (настройки и последующая калибровка)

Для исторической карты `m` до прогнозируемой карты в момент `T`:

```text
age_days = max(0, (T - m.started_at) in days)
w_time  = 2 ^ (-age_days / half_life_days)
w_patch = exp(-sum(patch_transition_penalties between patch(m) and patch(T)))
w_hero  = hero-impact adjustment for the involved hero(s), if verified
w_total = w_time * w_patch * w_hero
```

Пример **исходных гипотез для экспериментов** (не hard-code как подтверждённое качество): `half_life_days=180` для командной формы и `60` для draft-метрик. `w_patch=1` при одном патче; для старых патчей каждый переход даёт неотрицательный штраф, более серьёзный переход в среднем сильнее. `w_hero` меняется только при подтверждённых изменениях героя; при неполноте метаданных — нейтральная обработка с флагом `incomplete_patch_metadata`, либо недоступность, если нет надёжного способа определения патча.

Не применять одновременно агрессивное time decay и patch decay без бэктеста: они коррелируют. Параметры определять по строго хронологической валидации, включая периоды **сразу после крупных патчей**. Нельзя выбирать параметры по тестовому набору.

Показатели для моделирования:

```text
weighted_rate = sum(w_i * outcome_i) / sum(w_i), if sum(w_i) > 0
n_raw         = count(eligible maps)
n_eff         = (sum(w_i)^2) / sum(w_i^2), if sum(w_i^2) > 0
```

`n_eff` — Kish effective sample size (аппроксимация неоднородности весов), **не** число независимых матчей: карты в серии и матчи одного состава коррелированы. Не использовать `weighted_rate` непосредственно как вероятность победы без обученной и прошедшей проверку модели.

## 5. Patch cold-start

Если патч только вышел и данных мало, система должна:

1. Показывать отдельную сырую статистику текущего патча (`wins`, `games`) без маскировки.
2. Для модельных признаков использовать подходящую старую историю **с сильным уменьшением веса**, а не бездумный полный перенос win rate.
3. Рассмотреть регуляризованное частичное объединение оценок (shrinkage к сопоставимому pro-пулу/предыдущей мете), параметры только из train/calibration.
4. Отмечать `patch_cold_start`, `low_effective_sample`, `patch_metadata_missing` и повышенную неопределённость.
5. Для post-draft модели: если данные/проверки после смены режима недостаточны, возвращать `status=unavailable` и `probability=null`. Pre-match оценка может оставаться доступной *только* при подтверждённой применимости модели и пройденном quality gate.

**Пример:** 3-летний матч может сохранить малый вклад в долгосрочную оценку опыта игрока; его вклад в комбинацию двух героев после нескольких крупных обновлений должен быть минимальным либо нулевым при подтверждённом несовместимом rework.

## 6. Защита от утечки и контроль смещения

- Для любой исторической фичи `m.started_at < cutoff_at`; информация об обновлениях патчей и изменениях героев тоже должна быть опубликована *до* этого cutoff при ретро-прогнозе.
- Нельзя обучать прогноз прошлого с глобальными геройскими win rate, пересчитанными на будущих матчах, даже если их патч совпадает.
- Делить Train / Calibration / Test **по времени и группам серий**, дополнительно считать метрики на патч-переходах и новом патче: Brier, log loss, ECE, N, coverage.
- Сравнить минимум три абляции: без весов; только давность; давность + патч + геройские изменения. Тестировать ту же совокупность матчей и одни и те же признаки доступности.
- Не гарантировать улучшения от весов; при ухудшении holdout вернуться к более простой схеме.

## 7. Снимки, кеширование и UI

- При расчёте сохранить `target_patch_id/label`, `patch_registry_revision`, `weight_policy_version`, `feature_schema_version`, окно, `n_raw`, `n_eff`, распределение карт по патчам и предупреждения в `feature_snapshot`, `coverage`, `quality` существующих `prediction_runs`/`analysis_runs`.
- После выхода нового патча или исправления его даты инвалидировать соответствующие модельные агрегаты/кэши. **Не менять** старые immutable snapshots; новый результат — новый run.
- UI: переключатель «Текущий патч / последние N дней / все патчи», индикатор актуального патча, гистограмма объёма данных по патчам (при наличии), предупреждение при малом `n_eff`. Не смешивать сырые показатели и взвешенные оценки под одной подписью.
- Возвращать предикт только если quality gate пройден на релевантном наборе; отдельно отображать предупреждения о патч-дрейфе.

## 8. Acceptance tests

1. Две карты с одинаковым исходом, но разными возрастами имеют меньший/больший вес согласно time decay.
2. При одинаковой давности карта после существенного несовместимого изменения героя весит меньше для hero-признака, чем для team-признака.
3. На выбранном патче сырые `games/wins` **не включают** соседние патчи.
4. Игры на/после `cutoff_at` не входят ни в один признак, включая patch snapshots.
5. Для эпохи без достоверного `patch_id` отображается явный coverage warning, не выдумывается версия.
6. `n_eff` правильно считается на неравных весах, `n_raw` не заменяется им.
7. Холодный старт нового патча выдаёт флаг и при непройденном quality gate — `unavailable`, а не фиктивную вероятность.
8. Применимость модели при переходе патчей валидируется отдельно; параметры не подбираются на final holdout.

## Roster-sensitive переносимость данных

Совместная игра двух игроков в прошлой организации сохраняет информативность после их общего перехода, но старые hero-specific показатели по другой мете уменьшают вес значительно сильнее. Для `pairwise player co-play`, `exact-five` и team-churn использовать **раздельную** временную политику, не путать её с weight героев/геройских связок. На новом составе отмечать `ROSTER_COLD_START`, низкое покрытие ID и roster drift; качество pre-match модели измерять также на решафлах и stand-in матчах.
