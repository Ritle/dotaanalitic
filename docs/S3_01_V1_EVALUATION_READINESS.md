# S3-01/V1 — готовность независимой проверки

**Обновление 6 ноября:** [проверка формата и участников](S3_01_TIER1_PREFLIGHT.md) выявила ошибку исходного scope: объявленный формат BLAST IX даёт34 серии, а старый план требует40. Даты ниже остаются исторически зарегистрированными; **ожидание2 декабря не делает проверку выполнимой**. Старый план не изменён, оценка не запускалась. Предложение отдельного теста BLAST IX + DreamLeague30 пока не зарегистрировано; следующий шаг — protocol-feasibility, а не обещание активации после прежней даты.

Проверка 5 ноября 2026. Код для сбора, оценки и регистрации результата подготовлен. Качество модели ещё не проверено: будущий турнир не начался, активной модели нет. [Результаты этого аудита](evidence/s3-01-v1-evaluation-readiness.json) не являются model evaluation report.

## Что уже проверено

- Отдельный оценщик `.tools/v1-frozen-runtime`: все 232 закреплённых файла, Node binary, план, кандидат и зависимости workspace проходят прежнюю проверку. 150 прежних compiled modules основного приложения сохранены; runtime остаётся совместимым.
- Прямые команды `freeze verify` и `release-execute check` работают. Последняя намеренно возвращает `sourceEvidenceChecked:false`: она не проверяет будущие discovery/detail-файлы. В исходном config ещё находятся placeholders; это ожидаемая неполная конфигурация будущей оценки.
- Выполнены `collect → verify → merge → details capture → details verify` до начала окна. Результат `not_started`, ноль карт и HTTP-запросов. Это проверка управления сбором, **не эмпирическое покрытие будущего турнира**. Её пустые файлы хранятся отдельно от будущего release-сбора.
- Реальные команды `capture`, `verify`, `evaluate`, `revise` отвергнуты с `RELEASE_CAPTURE_TOO_EARLY` до открытия выходного файла/БД/отсутствующего capture. Часы и параметры протокола не подменялись.
- Рабочая БД: 340 карт, 314 игроков, 172 серии, один неактивный кандидат; release/research journals, активации и прогнозы пусты. Карт в будущем временном окне нет. Это текущая локальная инвентаризация, а не размер будущего теста.

## Зафиксированные условия

Даты ниже взяты из [неизменного зарегистрированного плана](evidence/s3-01-v1-release-plan.json); расписание организатора в этом аудите повторно не проверялось. Все пользовательские даты — МСК (UTC+3).

|---|---|
| Событие | BLAST Slam IX main event, OpenDota league `20208` |
| Начало целевого окна | 20 ноября 2026, 03:00 МСК, включительно |
| Конец целевого окна | 30 ноября 2026, 03:00 МСК, **исключительно** |
| Снимок доступных источников | 2 декабря 2026, 03:00 МСК |
| Самое раннее выполнение оценки | 2 декабря 2026, 03:00 МСК |
| Минимум пригодных карт / целых серий | 100 / 40 |
| Минимальное покрытие карт / известных серий | 80% / 80% |
| Идентичности и история | 10 разных verified accounts; минимум 5 пригодных завершённых pro-карт на каждого |
| Максимальный Brier / log loss | 0,245 / 0,685 |
| Сравнение с базовым 50/50 | Верхние границы paired whole-series bootstrap для обеих разностей строго ниже нуля |
| Калибровка | ECE ≤ 0,08; верхняя граница ≤ 0,15; абсолютная ошибка среднего ≤ 0,05 |

Дополнительно обязательны неизменные проверки временной устойчивости и исходного покрытия из плана. Числа здесь — заранее выбранные критерии, не достигнутые результаты. Ноль наблюдений означает неизвестное покрытие и null-метрики. Неудачные/неполные карты и серии сохраняются в знаменателях.

**Критичный порядок:** сначала собрать и проверить реальные source receipts, затем дождаться момента оценки. Ответы источника, полученные после `snapshotAt`, не становятся допустимыми благодаря более раннему времени самой карты. Новые identity proofs тоже нельзя задним числом объявить доступными в снимке. Финальный сбор и устранение выявленных пробелов следует завершить заранее, например 1 декабря; точный cutoff остаётся прежним.

Дата не гарантирует достаточную выборку или успешные метрики. При недостатке данных сохраняется `insufficient_evidence`, при провале качества — `failed`. Порог, окно и первая оценка не переписываются; новый тест требует отдельной заранее зарегистрированной нетронутой выборки. EPL и другие события не включаются в этот тест автоматически.

## Как выполнять сбор

Дополнение 5 ноября: для операторского запуска подготовлен [управляемый CLI](S3_01_V1_COLLECTION.md) — нумерованные попытки, идемпотентный повтор, сохранение ошибок и объединение всех captures. Используйте его рабочий каталог `.tools/v1-release-collection-managed`. Ниже описан низкоуровневый путь; его отдельные captures нельзя молча смешивать с управляемой коллекцией или исключать из учёта.

Сбор этого турнира **не выполняется автоматически** ни при открытии страницы, ни history-worker. Не создано новой фоновой задачи или системного расписания. Нужен операторский запуск существующего collector во время окна и завершающая проверка источников до snapshot. Общий worker запускать ради этого не требуется.

Для этого ПК подготовлен конфиг `.tools/v1-readiness-20261105/discovery-config.json`, закрепляющий прежние plan/catalogue/development SHA и абсолютные пути к bundle. Его SHA приведён в evidence. При переносе ПК/каталога нужно создать новый конфиг с правильными путями; сами plan/kernel/freeze не менять.

1. Перед началом проверить bundle по [инструкции freeze](S3_03_V1_EXECUTABLE_FREEZE.md). Использовать прямой Node из bundle, без `shared:build` и pnpm aliases внутри него. Credentials читать из локальной `.env`, не копировать в bundle или отчёты.
2. После начала окна запускать bounded discovery. Каждый запуск получает новый каталог; сохраняются request, manifest, SHA и все receipts, включая ошибки. В режиме V1 запрашивается только закреплённая лига, без обхода всех pro-матчей. Лимиты, quota и Retry-After действуют через прежний клиент.
3. `verify` каждого запуска → полный список `{directory, manifestSha256}` → `merge`. Нельзя отбирать только удачные запуски. Текущий union принимает не более 10 runs; планировать редкие контрольные сборы с резервом для ошибок, а не почасовой polling. Пустой подготовительный прогон этого аудита не является сбором турнира.
4. Для закреплённого union выполнить все необходимые detail batches по 50 IDs, включая связанные карты серий. `verify` → canonical import → проверка numeric identities, series и исходов. Недостаток доказательств оставлять явной причиной исключения. Новая версия union требует совместимых с её SHA batches; старые captures не перезаписывать и не выдавать за новые.
5. До snapshot проверить сохранность полного union, batches, account/series evidence и истории. Условие минимум 5 карт относится к истории **каждого фактического участника до соответствующей карты**, а не к общему числу записей в БД. Другие проверенные профессиональные турниры могут давать warmup. Последние 320 eligible maps для YeS—GL не доказывают покрытие будущих участников BLAST.
6. Создать отдельный execution config с реальными `evidence.configPath/configSha256`, `unionPath/unionSha256`, всеми batches. Сохранить прежние plan/kernel/freeze, посчитать SHA нового config. Оригинальный `frozen/config.json` с placeholders сохранить.
7. Не ранее установленного момента выполнить `release-execute capture → verify → evaluate`. Первый результат сохраняется в неизменяемом журнале, даже если он unavailable. Команды восстановления и explicit revision — в [инструкции оценки](S3_03_V1_RELEASE_EVALUATION.md). Активация возможна только отдельным действием после passed gate.

Пример **будущего** запуска из корня проекта, когда наступит целевое окно; имя `run-01` используется только один раз:

```powershell
$taskRoot = (Get-Location).Path
$taskConfig = Join-Path $taskRoot '.tools/v1-readiness-20261105/discovery-config.json'
$taskRun = Join-Path $taskRoot '.tools/v1-raw-release-collection/run-01'
New-Item -ItemType Directory -Path (Split-Path -Parent $taskRun) -Force | Out-Null
Push-Location -LiteralPath (Join-Path $taskRoot '.tools/v1-frozen-runtime')
try {
  node --env-file-if-exists=../../.env scripts/collect-evaluation-discovery.mjs collect $taskConfig $taskRun
} finally {
  Pop-Location
}
```

Команда выполняет сбор metadata и сохраняет источники; не рассчитывает прогнозы и не активирует модель. SHA из результата нужно записать вместе с каталогом и проверить командой `verify`. Для реального финального набора нельзя подставлять SHA пустого prewindow-прогона.

## Ограничения и следующий шаг

Независимая валидация, успешность критериев, первая активация и приёмка реального прогноза остаются открытыми. Техническая готовность оценщика не доказывает способность API предоставить полный будущий турнир. `remoteCompleteness` остаётся `unknown`. Нового live-аудита pro API не было: этот срез не менял importer/features/model и не запрашивал будущие результаты; прежние эмпирические исследования сохранены.

Следующий точный шаг — **S3-01/V1-evaluation/collection**: по зарегистрированному окну собрать и проверить реальные discovery/detail/identity/series evidence до snapshot, сохранив полный знаменатель и прежний протокол. До 20 ноября новых целевых карт этот collector не ищет. Для этой границы данных и последующей независимой оценки: **GPT-6 Astra · Extra High**. Более широкие owner coverage и Linux deployment этим аудитом не закрываются.

QA: frozen offline install, root typecheck/build, 825 unit/CLI и 23 PostgreSQL-теста четырёх связанных suites — PASS. Проверены реальное сохранение/восстановление оценки, конкуренция, неизменяемость, запреты подмены и активации, source coverage. Все эти model-результаты синтетические и находятся только в удаляемых тестовых БД. Полные PG/Chromium/Node/Python/Docker/Linux suites повторно не запускались. 75 рабочих public tables и очередь сохранили контрольные суммы/состояния. PostgreSQL, API, web и отдельный history-worker восстановлены после выключения; общая очередь не запускалась. API health — ok. Production code, модель, зависимости и данные не изменены.
