# S1-16 — имена в покрытии истории и таблице силы

Задача №7: `S1-16/BUG_REPORT/readable-labels/history-strength`.

## Что изменилось

В «Личной pro-истории» покрытие и пригодность для Elo показывают ники
по точным canonical player IDs сохранённого отчёта. Два списка используют
одну общую загрузку имён: до10 разных игроков, обычно5. Steam32 остаётся
видимым для проверки; локальный ID и карточка доступны в «Данных записи».
Имена не связывают аккаунты, не меняют raw/eligible N или период загрузки.
Смена текущей выбранной пятёрки не используется как источник имён старого
отчёта: запрашиваются собственные IDs report.players/enrichment.players.

В «Elo и сила соперников» соперник показан названием организации.
`opponentId` здесь — локальный team ID из стороны завершённой карты
(`strength-report.ts`), не аккаунт, не список игроков и не provider team ID.
Номер карты, реальная сторона и прежние рейтинги/период сохранены.
Одинаковые названия не объединяют организации или строки статистики.
Неизвестный opponentId не получает предположительную команду.

Пустое имя отличается от отсутствующей записи. При проблеме metadata
остаются ссылка и точный ID, доступные имена кэша сохраняются. Кнопки
обновления имён не запускают загрузку карт, повторный импорт, проверку
аккаунтов или пересчёт рейтинга. Подписи — текущий локальный каталог,
не историческое доказательство; время чтения показано отдельно.

## Ограниченные запросы

Игроки используют прежний private GET `/api/v1/catalog-labels`, один batch
для coverage/enrichment. Новых provider HTTP нет. Повторное раскрытие
покрытия не создаёт запрос на каждого игрока.

Для организаций расширен существующий private read-only
`GET /api/v1/context-catalog?kind=teams&ids=...`. Новый необязательный `ids`
принимает1–20 положительных локальных bigint ID через запятую, до400 знаков.
Он не смешивается с `id`, непустым `query`, ненулевым `offset` и другими
kind. Пустая строка, >20 элементов и небезопасный ключ дают400;401 без owner.
Дубли удаляются после валидации; неизвестные IDs не возвращаются, пустые
имена не заполняются. SQL использует параметризованный `ANY(bigint[])`
и закрытый mapping таблицы. JSON ответа и прежние id/search режимы сохранены.
Пакет имеет `hasMore:false`, не расширяет поиск и не обращается к провайдеру.

TeamDisplayLabels группирует разные ключи по20, максимум100 организаций
из отчёта с лимитом100 карт: до5 запросов вместо запроса на строку. Null
не запрашивается; одинаковые соперники читаются один раз. Общий кэш5min
зависит от набора IDs, не от рейтингов или даты фильтра. При обновлении
того же отчёта свежие имена переиспользуются. Частичный сбой не удаляет
успешные пакеты; «Повторить недоступные названия» перечитывает только
ошибочные. Автоматический retry и refetch-on-focus выключены. Новый mount
при пустом/устаревшем кэше может снова прочитать metadata.

Ничего не добавлено в общие пакеты, model runtime, feature builders,
зависимости или SQL-миграции. Меняются только metadata query/API reader
и frontend-представление. Elo остаётся описательным экспериментальным
рейтингом; этот срез не создаёт вероятность и не меняет quality gate V1.

## Проверки

[Фактические результаты](evidence/bug-report-history-strength-labels.json).
Контрактные тесты проверяют старые формы запросов, bigint keys,20/21,
пустые/смешанные/небезопасные режимы. Чистые тесты проверяют stable batch,
null/duplicates, отсутствие мутации входа и максимум5 запросов.
Браузер проверяет owner/401/400, чтение local ID вместо provider ID,
read-only SELECT,21 ключ двумя запросами, дубли/blank/missing/null,
rename/частичный503/retry с сохранением рейтингов и summary.
Расширенный23-map ответ — явно синтетический display fixture, не импорт
новых карт. Обычная двухкарточная хронология проверяется отдельно прежним
strength.spec. Настоящий тестовый worker загрузки истории использует только
синтетический источник во временной БД: ники обоих списков, общий lookup,
неизменность report JSON и отсутствие дополнительных provider calls.
