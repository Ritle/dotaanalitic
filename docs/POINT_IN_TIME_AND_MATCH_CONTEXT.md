# Point-in-Time & Match Context — обязательный архитектурный контракт P0

## 1. Различать 3 времени

- `started_at` / `event_at`: когда событие реально произошло.
- `known_at`: самое раннее **подтверждённое** время, когда фактор стал публично или нам доступен. Если неизвестно — `NULL`, ретроспективно утверждать раннее знание нельзя.
- `fetched_at`: когда backend запросил и сохранил запись; не показатель исторической доступности.

При обучении на карте M в момент cutoff T разрешены исторические завершённые карты со `started_at < T`, а конкретный контекстный фактор должен быть подтверждён как известный на нужной стадии (`known_at <= T`), либо пройти строго документированное правило доступности по природе события. Если подтверждения исторической доступности состава/факта нет — missing indicator или исключение из набора, не «известен, потому что API вернул сегодня».

Надёжная training target может использовать итог победы M как **label**, но не как входной feature M. Исходы предыдущих карт серии можно использовать только в отдельном between-map сценарии после их завершения. Для предматчевого pre-map *до первого драфта* сведения о текущих героях/first-pick, ставшие известными позже, запрещены.

## 2. Одна карта и одна серия

`series` хранит BO-формат (1,2,3,5), турнир, команды. `matches` хранит конкретную карту с `map_number`, `series_id`, результатами карты и **верифицированным** счётом серии на начало карты. Если map number, series linkage или счёт недоступны — оставляем `NULL` (не подбираем BO3 по времени для обязательных признаков). Использовать историю серии по времени можно только при достаточной проверке участников/ID, без переносов результатов будущих карт.

MVP prediction target = победа **на одной карте**. Серийные вероятности — P2, даже если хранение series context — P0. Whole-series split: известные карты одной серии не могут попасть одновременно в train и test; неизвестные series группируются консервативно с аудируемыми правилами и ограничением риска утечки.

## 3. Сторона, первый пик, порядок драфта

`team_slot A/B` — предмет UI, `radiant/dire` — игровой атрибут отдельной карты, `first_pick_side` — отдельное измерение. Нельзя выводить first pick из Radiant side. Версия draft order зависит от исторического патча. Без verified side/pick order перед прогнозом feature = unknown; если пользователь строит what-if, это явная гипотеза. Pre-map перед началом драфта никогда не берёт heroes/bans/order текущего драфта.

`draft_order_version` задаёт правило последовательности действий на дату карты; его нельзя автоматически считать актуальным для древнего патча. Модуль `DraftOrderRegistry` / `MatchContextResolver` (границы, а не отдельные микросервисы) реализуется в API/data-domain.

## 4. Турнирный контекст

`league.tier`, `stage`, `venue_kind=lan|online|hybrid|unknown` — **возможные**, а не гарантированные поля источника. Пустое поле остаётся `NULL`. Произвольные веса вроде «финал ×2» недопустимы: вклад определяется offline ablation, после контроля силы соперников. Нельзя выводить физическое место проведения только по названию турнира.

## 5. Доступность героев

`hero_availability_rules` — подтверждённые запреты/допуски для определённого времени, патча и/или турнира, с `source/evidence_ref/known_at`. Отсутствие записи — **неизвестно**, а не `allowed=true`. Проверить конфликт правил; не применять новые правила к прошлой карте. Для MVP при недостатке метаданных предупреждать, а не запрещать варианты пользователя произвольно.

## 6. Изоляция train/inference и invariants

`FeatureBuilder.build(snapshot, cutoff, stage)` используется идентично в offline + runtime. Функции чистые и детерминированные, все зависимости содержат version/fingerprint. Каждый stored prediction фиксирует known inputs, cutoff, source revisions, lineup/roles, patch, model version, flags missingness и политику весов. Любая ошибка в legacy import порождает **новую ревизию** вычислений, а не переписывает прошлый прогноз.

## 7. Тесты P0

1. Исторический match из 2024, загруженный в 2026: не становится известным заранее как published lineup без исторической даты.
2. Карта №2 BO3: результат карты №2 не входит в фичи карты №2; счёт после №1 может попасть лишь в between-maps модель (P2).
3. Swap Team A/B и Radiant/Dire сохраняет семантику и симметрию.
4. `first_pick_side` может отличаться от Radiant. Unknown side не подменяется Team A.
5. Неполная последовательность банов не маркируется полной; правила старого патча не заменяются сегодняшними.
6. Нет данных по LAN/online и stage — `null`, не фиктивный online.
7. Hero pool ограничен доказанной rule validity, null availability не становится false.
