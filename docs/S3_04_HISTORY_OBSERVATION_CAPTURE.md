# S3-04: фиксация проверенной истории до нового драфта

При обычной фиксации нового снимка драфта сервер теперь сначала сохраняет проверку локальной профессиональной истории, завершает её транзакцию и только затем получает cutoff для снимка. Дополнительного действия владельца нет. Повтор того же запроса читает прежний снимок; проверка исходов повторно не выполняется.

## Граница времени и версии

SQL060 добавляет append-only `owner_draft_history_observations` и `owner_draft_history_links`. Для связи обязательно `readAt <= observedAt <= recordedAt < decisionCutoffAt <= capture.recordedAt`. Запись наблюдения и снимок не могут быть связаны в одной незавершённой транзакции: SQL проверяет также transaction ID наблюдения. Время задаёт сервер, клиент не передаёт дату проверки.

`readAt` — срез чтения и аргумент существующего SQL018 OutcomeVerifier; его `labelVerifiedAt` сохраняет прежнюю миллисекундную семантику. `observedAt` снимается после выполнения пакетной проверки, `recordedAt` задаётся триггером при записи. Эти часы не превращаются в provider `known_at`. Реальные event/known/fetched/recorded timestamps источников остаются отдельными.

`owner-scenario-selection-v2` закрепляет scenario ID/revision/hash; `actualMatchId` остаётся `null`. Поздняя SQL059 native-привязка — отдельное свидетельство, не изменение первоначального выбора. Старый `selectionDigest`, SQL058 и research artifacts не переписаны. Доказанность старта карты, соответствие расписанию и готовность модели из этой записи не следуют.

## Компактный срез

Проверка рабочего корпуса выявила лимит старого raw-снимка: подробные field observations занимают около 79 МБ, а лимит снимка — 30 МБ. Поэтому новый `draft-history-projection-v1` явно имеет `sourcePayloadsIncluded:false` и `fieldObservationsIncluded:false`. Сохраняются все попавшие в ограниченную выборку карты, игроки/герои/стороны, серии, identity evidence, метаданные receipts с ID/SHA и результат проверки каждой карты. Исходные payload и field observations остаются в своих таблицах. Это не их полная архивная копия.

Неуспешные проверки остаются в массиве outcomes с причинами. Одна canonical map появляется один раз; `verified` означает проверенный прошлый исход, а не готовность всех признаков. Source hash покрывает точный компактный срез; evidence SHA — всю запись. Зафиксированы checksum SQL012/018, обеспечивающих проверку исхода. Snapshot retrieval валидирует схему, SHA, часы, соответствие verified результата карте и receipt.

Для исторических outcomes verifier вызывается с `teamASide: radiant`: `teamAWon` здесь равен `radiant_win`. Это не сторона команды A выбранного владельцем будущего матча; контракт дополнительно сверяет обе команды с историческими Radiant/Dire.

Лимиты: 5000 карт, 50000 строк участников, 10000 receipts, 50000 identity evidence, 30 MiB проекции и 32 MiB записи. Превышение лимита проекции сохраняет явный `DRAFT_CAPTURE_HISTORY_LIMIT` с недоступной историей, без успешной обрезанной выборки. SQL statement timeout30s, lock timeout10s. Проверка не обращается к API провайдеров, не обучает и не активирует модель.

Старый raw-блок SQL058 остаётся прежним и может сообщать свой лимит, даже когда отдельная компактная проверка сохранена. Новый offline-адаптер должен явно использовать SQL060; текущий экспорт предыдущего среза продолжает консервативно сообщать о недостающих observations, пока этот адаптер не подключён.

## Совместимость и повторы

Исходный HTTP-контракт и UI не менялись. Обе транзакции проверяют владельца и редакцию сценария. Повторы и конкурентные запросы создают одну запись на редакцию; при изменении сценария между подготовкой и фиксацией возвращается конфликт. Подготовленная запись может остаться без снимка — она не становится прогнозом или обучающим примером.

Для старого SQL058-снимка новая подготовка не выполняется. Его байты и прежний cutoff остаются прежними; восстановить отсутствующее наблюдение задним числом нельзя. Для новой проверки нужен новый сценарий или новая редакция.

Код: `apps/api/src/modules/scenarios/draft-history-{contract,source,repository}.ts`, вызов подготовки в `draft-capture-repository.ts`, миграция060. Shared contracts/db/prediction exports и рецепты признаков не менялись.

## Проверки и продолжение

Реальный локальный пилот: 2260 карт, 2243 verified outcomes, 17 `TEAM_SIDES_UNKNOWN`; проекция6 618 941 байт. Первый проход проверки занял около17с; полный повтор с валидацией схемы под тестовой нагрузкой — около25с. Это измерения этого компьютера, не гарантия времени ответа. Пилот ничего не сохранял в рабочие таблицы; технический selection использован только для проверки схемы. Положительное сохранение/commit/cutoff проверены на отдельных синтетических БД.
