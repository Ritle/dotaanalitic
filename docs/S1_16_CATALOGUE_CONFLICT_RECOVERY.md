# S1-16 / BUG_REPORT №10 — восстановление после конфликта связей

11 ноября 2026. Продолжение исправления BUG_REPORT по выбору владельца.

## Воспроизведённая причина

Форма хранит результат подготовки игроков отдельно от прочитанных связей.
Другой редактор может сохранить новую редакцию той же пятёрки. Сервер
обоснованно отклоняет старую редакцию с HTTP409. После «Перечитать связи»
форма уже получала новые `expectedRevision` и `linkToken`, но при следующем
сохранении подставляла старые токены из результата подготовки. Поэтому
даже повторное подтверждение приводило к повторному409.

Теперь токены запроса берутся из актуального состояния связей. Результат
подготовки остаётся подсказкой аккаунтов, а не источником версии для записи.
При изменении редакции, заявки или токенов подтверждение сбрасывается;
выбранные команда, аккаунты и отметки участников остаются в форме.

## Как продолжить после ошибки

1. Для конфликта связей нажмите **«Перечитать связи»**.
2. Проверьте сохранённую редакцию и выбранные аккаунты. Ручная замена
   не отменяется автоматически.
3. Подтвердите соответствие команды и пяти аккаунтов заново и сохраните.

До успешного перечитывания после409 подтверждение заблокировано. Если
чтение недоступно, выбор сохраняется; «Повторить чтение составов» выполняет
тот же безопасный переход. Повторная запись сама не запускается.

Если изменился источник, сначала обновите заявку; при изменении каталога
повторите подготовку или поиск аккаунта, затем проверьте выбор. Если
источник недоступен, повторите позже. Эти состояния имеют отдельные
сообщения; ошибка состава больше не называется изменением сценария.
Показывается локальный текст по разрешённому коду, не произвольный ответ
внешнего источника.

После409 новый подтверждённый запрос получает новый `requestId`. Для
сетевой ошибки без подтверждённого конфликта прежний механизм повтора
того же запроса сохранён. Никаких автоматических перезаписей или обхода
проверок canonical identity, revision, source hash и leases нет.

## Границы проверки

Ошибка воспроизведена в Chromium с реальным Fastify и отдельной синтетической
PostgreSQL-базой: конкурирующее сохранение →409 → перечитывание → ручное
подтверждение →200. Без исправления токена последний шаг возвращал409.
Отказ чтения отдельно моделируется единственным HTTP503 в браузерной
фикстуре; это не наблюдение доступности реального провайдера.

Для исходной встречи1791664 сохранился кэш «PlayTime vs TS» с началом
11 ноября13:00МСК. На момент диагностики это время уже прошло. Запись в
рабочую встречу не повторялась: исходный запрос и тело ответа409 отсутствуют,
его точная причина остаётся неустановленной. Исправлен общий воспроизведённый
механизм, а не утверждена причина прежнего отказа владельца.

API обработчики и формат успешного сохранения, SQL, canonical links,
immutable snapshots и модель V1 не меняются. Добавлена только читаемая
Zod-схема известных кодов ошибки и обработка состояния формы.

Декодер находится в `packages/contracts/browser/catalogue-error-code.ts`
и импортируется веб-клиентом как исходный модуль. Он намеренно исключён из
серверного `src/dist`: активация модели фиксирует весь список серверных JS
модулей, поэтому даже новый неиспользуемый файл изменил бы runtime manifest.
Публичные exports пакета, существующие compiled contracts, зависимости и
lockfile сохранены. Zod берётся из уже объявленной зависимости contracts.
