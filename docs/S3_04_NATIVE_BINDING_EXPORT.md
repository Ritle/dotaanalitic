# S3-04: экспорт снимков Draft Lab и привязок к картам

Экспорт связывает SQL058/059 с существующим offline-контрактом признаков и показывает причины, по которым сохранённый снимок нельзя использовать для расчёта. Это диагностический инструмент разработчика: числовые признаки H1/H2, обучение и прогноз после драфта этим срезом не включены.

## Что сохраняется

`tools/audits/draft-native-export.mjs` читает весь ограниченный инвентарь в одной read-only repeatable-read транзакции. Сохраняются исходные JSON-тексты и SHA снимков, все попытки native-привязки, время записи с микросекундами и полный замороженный срез истории. Новая история и внешние API не запрашиваются.

`draft-native-export-core.mjs` проверяет схемы, ссылки владельца/снимка, последовательность времени, SHA и заново выполняет чистую проверку каждой привязки. Изменение результата привязки с пересчитанным SHA также отклоняется. Для каждой исторической карты остаётся запись с причинами исключения.

Один native Dota match ID — одна фактическая карта. Если к ней привязаны несколько снимков, диагностический представитель выбирается по самому раннему `recordedAt`, затем UUID; остальные сохраняются как дубли. Выбор не зависит от исхода или полноты признаков. Это не назначение основного прогноза и не пример для обучения. Снимки без успешной привязки также остаются в отчёте.

Пределы: 100 снимков, 1000 попыток, 60 MiB исходных текстов в БД, 64 MiB JSON источника, 128 MiB файла. Превышение приводит к отказу всего экспорта; молчаливой обрезки нет. Запись разрешена только в `.tools/*.json`, исключительно в новый файл. Экспорт содержит частные данные владельца и не предназначен для публикации.

## Обнаруженный разрыв данных

SQL058 хранит состав, героев, историю и receipts, но не отдельные записи проверки исходов и доступности исторических фактов до cutoff, требуемые строгим prospective-контрактом. Поздняя native-привязка не создаёт эти свидетельства. Повторный запуск OutcomeVerifier сейчас с параметром старого времени также не доказывает, что проверка выполнялась тогда.

Поэтому адаптер запускает прежний builder в явно обозначенном режиме `missing_evidence_probe`: реальные выбранные игроки/герои, отсутствие подтверждённых observation-записей, пустая **доверенная** история. Полная исходная история остаётся отдельно в источнике и журнале исключений. `trustedHistoryMaps: 0` означает отсутствие допущенных свидетельств, а не отсутствие опыта у игрока. `inputs: null`, `featureReady: 0`, `trainingExamples: 0`, вероятность `null`, `primaryEligible/deployable: false`.

ID сыгранной карты используется только как диагностическая связь. Старый selection digest включает target ID; pending-снимок нельзя задним числом объявить ранее известным выбором этой карты. Проверка реального старта игры, соответствия расписанию и номера карты также остаётся отдельной. Экспорт не обходит ни один из этих gate.

## Запуск

Из корня `dotaanalitic`, после frozen install и сборки пакетов/API:

```powershell
node node_modules/typescript/bin/tsc tools/research/player-hero-prospective-features.mts tools/research/player-hero-inference.mts --strict --noUncheckedIndexedAccess --skipLibCheck --target ES2022 --module NodeNext --moduleResolution NodeNext --types node --typeRoots packages/db/node_modules/@types --outDir .tools/s304-prospective-features-runtime
node --env-file-if-exists=.env tools/audits/draft-native-export.mjs capture .tools/my-native-export.json
node tools/audits/draft-native-export.mjs verify .tools/my-native-export.json <SHA256_из_capture>
```

`verify` работает без соединения с БД и внешней сети. Внешний SHA файла проверяется до разбора; затем проверяются источник, сохранённые хеши кода/runtime/SQL/lockfile, версия Node и полное совпадение результата повторного аудита. При изменении среды нужен новый экспорт; старый файл не перезаписывается. На этом рабочем checkout дополнительно выполняется старый `player-hero-prospective-features.mjs compile`, проверяющий прежние frozen research manifests.

Новые тесты сами компилируют prospective runtime из исходников и не требуют частных demo/fit-артефактов. PostgreSQL-тест создаёт отдельную базу, использует явно синтетические данные и удаляет только её.

## Проверки и следующий шаг

Фактически выполненные проверки и локальный инвентарь: [evidence](evidence/s3-04-native-binding-export.json). Нулевой реальный инвентарь не является подтверждением покрытия настоящих draft-снимков; положительные и ошибочные случаи проверяются на синтетике.

Следующий срез: **S3-04/player-hero-history-observation-capture** — сохранять отдельные доказательства проверки прошлых исходов и доступности истории до фиксации будущего драфта; предусмотреть версию контракта для pending target и последующей native-привязки. Начать с проверки порядка серверных часов и совместимости, затем реализовать минимальный сбор наблюдений. Старые снимки не переписывать и не датировать задним числом. Модель: **GPT-6 Astra · High**.
