## Что уже решено и не должно возвращаться в блокеры V1

- Ожидаемая пятёрка из актуального источника достаточна; официальное подтверждение явки не требуется. Ручные изменения владельца авторитетны для сценария. Ник не заменяет numeric identity.
- Отсутствующие роли, patch metadata, герои и draft order не блокируют hero-free/role-free V1 Elo. Роли автоматически предлагаются/применяются с существующими ограничениями и ручной коррекцией; отдельная измеренная точность определения позиций не установлена.
- В player history могут входить проверенные pro-карты разных уровней и организаций. Их не нужно удалять ради Tier1 scope будущего прогноза.
- Ranked hero practice S2-07 реализована как отдельная описательная таблица OpenDota; STRATZ дополняет контекст известных карт. Независимая STRATZ ranked player-history выдача не валидирована, pub WR не входит в V1. Его добавочная предсказательная ценность остаётся будущим экспериментом.
- S1-07 patch/hero impact, logistic/recent-form/cohesion/role features, S3-04 post-draft, S2-05 draft order, richer what-if и S5-06 automated retraining остаются отложенными улучшениями. Их существование в старом P0-плане не делает их текущими blockers сокращённого V1.
- Проблема свежести расписания из сверки5 ноября закрыта [S4/V1-schedule-freshness](S4_V1_SCHEDULE_FRESHNESS.md): новое назначение/прогноз требуют source age<5min. Evidence-only resume истории реализован [отдельным срезом](S2_01_HISTORY_ENRICHMENT_RESUME.md).

## Даты и практический порядок

Даты здесь описывают **закреплённый внутренний протокол**, не новую проверку текущего расписания организатора:

1. Сбор test sources начинается **20 ноября2026,03:00МСК**. Окно целевых стартов заканчивается **30 ноября,03:00МСК** (правая граница исключена).
2. Подходящие source receipts/identity/series/history должны быть получены до snapshot **2 декабря,03:00МСК**. Ручной управляемый CLI готов; автоматическое расписание этого сбора не создано.
3. Не ранее snapshot — независимая оценка. Нужны100 карт/40 серий,80% покрытия и все quality gates: Brier≤0.245, log loss≤0.685, проверка baseline/калибровки/устойчивости по [полной policy](MODEL_VALIDATION.md). Наступление даты не гарантирует прохода.
4. После passed gate — явная активация, финальная приёмка с реальной моделью и проверка восстановления. Нехватка данных или failed quality сохраняют unavailable; пороги и первый результат не переписываются.

Ожидание декабря не является математическим требованием Elo. Это следствие конкретного выбранного независимого теста. Другой срок возможен через отдельный заранее зарегистрированный untouched протокол; текущие просмотренные development/E0/E1 результаты не становятся таким test. В этом аудите новый протокол не создавался.

До окна полезно согласовать рабочие Tier1 target events и устранить ограничение forecast-source первой страницей. Это отдельные операционные/продуктовые действия; дата качества от них не становится пройденным gate. По текущему порядку следующая открытая задача остаётся S3-01/V1-evaluation/collection.

## Где документы создавали путаницу

1. Исторические checkpoints внутри плана содержат старые «следующие шаги», а исходные S3 tickets шире V1. Открытый S3-03 не означает, что kernel ещё не написан; открытый общий S3-07 не отменяет закрытый базовый V1-journal.
2. ТЗ§0.6 прямо описывает момент первоначального решения и не является текущим inventory реализации. Статус§0.7 про отсутствие scope/filter/runtime устарел; обновлён до фактического состояния без изменения требований.
3. Строка приёмки про фильтр только первой страницы устарела после S1-16/schedule-pages. Фильтр работает на выбранной странице; назначение прогноза пока действительно только с первой.
4. В ranked hero guide одновременно присутствовали ссылка на выполненное STRATZ enrichment и фраза «ещё не подключено». Устранено противоречие: известные карты дополнены, независимая история STRATZ всё ещё не подтверждена.
5. QA-01/02/03 и V7-таблица содержат starter/historical условия. Локальные Vitest/PostgreSQL/Chromium уже исполнялись; Docker/Linux/remote CI этим не доказаны. Их следует учитывать по отдельным доказательствам, не считать автоматически ни полностью невыполненными, ни полностью закрытыми.

Рекомендуемый формат дальнейшей приёмки: «код реализован / проверен локально / подтверждён на реальных данных / допущен к выпуску». Подсчёт процента готовности по галочкам здесь вводил бы в заблуждение.

## Границы этого аудита

Свежие проверки: read-only SQL counts и штатный collection status; чтение нормативных документов/кода и ранее исполненных отчётов. Provider HTTP, импорт, training/scoring, активация, owner data changes и тестовые suites не запускались. Последние887 unit/CLI+18 Chromium относятся к предыдущему исправлению аккаунтных подписей; полный S4-набор также является прошлой проверкой.

Обновлены только документы и handoff. Модель для дальнейшей обычной сверки/правки документации: **GPT-6.1 Sol · High**; для независимой release-оценки и решения о допуске: **GPT-6 Astra · Extra High**, по принятой матрице проекта.
