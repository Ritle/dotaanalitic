# S2-01 — проверка API для роли игрока в команде

**Продолжение:** по последующему выбору владельца схема [реализована в S2-01/role-profile-reader](S2_01_ROLE_PROFILES.md). Ниже сохранён исследовательский checkpoint до реализации.

2026-11-04, по вопросу владельца о более надёжном источнике позиций. Это read-only исследование и предложение следующего среза; production integration не изменена. Linux deployment остаётся отложен.

## Реальные ответы

Выполнены четыре ограниченных HTTP-запроса с уже настроенными ключами: два PandaScore, один групповой STRATZ и один отдельный профиль STRATZ. Все вернули HTTP200, но групповой STRATZ содержит GraphQL error и не даёт пригодных профилей. Обход ограничения и автоматические повторы не выполнялись. Отдельный документированный `player(steamAccountId:...)` успешно возвращает профиль.

- PandaScore `/dota2/matches/upcoming` → первая запись → `/tournaments/22247/rosters`: шесть команд, 32 игрока, у всех есть непустое поле `role`. Наблюдались позиции `1`–`5`. Это одна удобная для проверки заявка, **не** репрезентативная выборка Tier1 и не измерение точности.
- Некоторые команды имеют шесть записей и повторяющиеся позиции: Zenith — две позиции2, Yangon Galacticos — две позиции5. Заполненное поле нельзя превращать в гарантированную текущую пятёрку или подтверждение роли в конкретной будущей карте.
- STRATZ `player(steamAccountId:56351509) { steamAccount { proSteamAccount { id name teamId position } } }`: профиль DM, `POSITION_3`, `teamId:9824702`. Это факт ответа источника, **не** утверждение проекта о его фактическом текущем составе. Team ID нужно сверять с выбранной организацией, а не считать любой профиль автоматически соответствующим сценарию. По одному профилю нельзя заявлять покрытие всех команд.

Токены передавались только в Authorization headers. Данные БД, роли/сценарии/прогнозы и архивные evidence не менялись; importer/worker/training/activation не запускались. Приватные результаты: `.tools/role-api-probe-20261104.json`, `.tools/role-api-stratz-single-20261104.json`. [Проверяемая сводка](evidence/s2-01-role-api-review.json) содержит SHA этих файлов и диагностических скриптов.

## Что дают источники

| Источник | Подтверждено | Практическое применение |
|---|---|---|
| [PandaScore](https://developers.pandascore.co/docs/dota-2) | Документированы позиции1–5 и mixed roles, в выбранной живой заявке32/32 непустых `role` | Роль профиля в контексте заявки/команды; отдельные verified provider-to-canonical links обязательны |
| [STRATZ](https://stratz.com/api) | Сохранённая introspection содержит `ProSteamAccountType.position`; отдельный живой профиль возвращает позицию и teamId | Предпочтительный первый узкий reader: Steam32 можно сопоставить с существующей verified identity, сверяя организацию |
| [OpenDota](https://github.com/odota/core/blob/master/svc/util/compute.ts) | В коде есть `position_est`, использующий early gold/last hits10–12мин, линии и ранние ward purchases | Дополнительная оценка сыгранной карты; наличие в реальных ответах и покрытие нашего корпуса этим прогоном не проверены |
| [Cito API](https://citoapi.com/microsites/dota-2-api/dota-2-team-roster-api/) | Провайдер заявляет current roster/position fields | Дополнительный кандидат; живой role payload и numeric identity binding не проверены |
| [BALLDONTLIE](https://dota2.balldontlie.io/#tournament-roster) | Документирован tournament membership; в просмотренном описании нет подтверждения позиций1–5 | Состав турнира; пока не обоснован как источник ролей. Полная OpenAPI YAML в web tool не открылась |

Публичная документация и ответ профиля не подтверждают официальную роль на будущую карту. Несколько API могут использовать общие первоисточники; совпадение данных — проверка согласованности, не несколько независимых подтверждений точности.

## Следующий предлагаемый срез

**S2-01/role-profile-reader:** один SELECT-only/profile HTTP reader STRATZ для проверенного Steam32 с отдельной текущей позицией, teamId, source/fetchedAt и статусом отсутствия/несовпадения. STRATZ остаётся optional/OFF до явного подключения этого среза. Сначала проверить покрытие выбранной текущей пятёрки, rate limits и точную классификацию ошибки bulk endpoint. Не считать, что root `players` будет доступен, раз работает `player`.

Затем сохранять/использовать PandaScore `role` в roster metadata: текущая `PandaRostersSchema` намеренно нормализует только ID/имя и отбрасывает остальные поля. Отсутствие роли в нашем UI поэтому не означает отсутствия поля у провайдера. PandaScore player ID **не** Steam32; совпадающего ника недостаточно для автоматического объединения. Mixed `1/2` сохраняется множеством вариантов, а не принудительно первой позицией.

Приоритет для отображения: явная ручная правка для выбранного контекста → согласованный профиль, соответствующий выбранной организации → недавние оценки pro-карт сначала в этой организации → прочая история как fallback → нынешняя lane/GPM эвристика. При противоречиях показывать варианты и источники; не присваивать оставшуюся позицию ради красивой пятёрки. Показывать время наблюдения, не выдавая fetchedAt за время обновления профиля. Исторические роли и V1 Elo остаются прежними. Это предложение, а не внедрённый алгоритм и не измеренное улучшение точности.
