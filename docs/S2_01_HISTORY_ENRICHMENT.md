# Подготовка участников и серий личной истории

**Продолжение:** [evidence-only resume](S2_01_HISTORY_ENRICHMENT_RESUME.md) добавляет задание по прежним принятым картам, новый отчёт и lineage производных проекций. Ниже сохранён первоначальный checkpoint; его замечание об отсутствии отдельного resume относится к состоянию до продолжения.

Срез `S2-01/role-owner-check/history-evidence-enrichment`. Кнопка «Загрузить историю игроков» теперь после импорта подготавливает числовые связи остальных участников и серии. Это общий механизм для выбранной пятёрки, без правил для конкретных ников или команд.

## Порядок обработки

1. Discovery и details используют прежние ограничения: выбранное окно 90/180/365/730 дней, до 10/25/50 уникальных карт на пятёрку. Обогащаются только карты, принятые существующим импортёром; конфликты и исключённые ответы не являются основанием для новых связей.
2. Из принятых карт собирается уникальный список Steam32. Уже подтверждённые аккаунты пропускаются. Конфликтующие связи не заменяются. Среди неизвестных обрабатывается максимум 100 аккаунтов за задание.
3. Общий каталог `/proPlayers` читается через тот же часовой кэш и lease, что подготовка ростера. Для отсутствующих числовых записей допускается до 20 обращений к profile cache/fallback. Это максимум 42 HTTP attempts с retries, включая каталог; общий durable quota действует вместе с остальными запросами. Negative cache препятствует немедленным повторам. Ник используется только для подписи; Steam32/Steam64, уникальность и source SHA проверяются до существующего `IdentityProvisioner.preview/apply`.
4. Положительные series IDs передаются существующему `SeriesProvisionRepository.preview/apply`, по одной уникальной серии. Все локально известные карты/receipts серии проверяются вместе. Конфликт одной серии не отменяет обработку других. `series_id=0` не превращается в BO1, неизвестные организации не угадываются.
5. Те же полные ответы, полученные в текущем задании, повторно передаются неизменённому импортёру. Повторных HTTP details/reference запросов для этого нет. Исходные SHA, fetched/known clocks сохраняются; новые canonical links создают новую data revision и новый контекст receipt. Предыдущие receipts/datasets/predictions не переписываются.
6. Существующий замороженный history adapter и Elo builder проверяют локальный корпус до текущего среза, с warmup 2024-01-01 и лимитом 5000 карт. Для выделения допустимой истории диагностический builder получает фактическую пятёрку одной исторической карты; это локальная проверка списка использованных карт, без сохранения сценария, вероятности или прогноза. Итог показывает персональные raw/eligible counts выбранных игроков.

Проверка identity/lease повторяется перед изменениями и replay. Повторная доставка задания идемпотентна; лимиты не повышаются автоматически. Внутри `source_audit.enrichmentEvidence` остаются numeric reviews с исходными clocks/SHA и fingerprints применённых планов серий. Владелец не обязан подтверждать каждого прежнего соперника вручную; противоречивые данные остаются нерешёнными.

Успешный импорт может иметь частично подготовленную историю. Новых endpoint, миграций и зависимостей нет.

## Ограничение старых receipts

Старый importer намеренно сохраняет только разрешённую проекцию JSON, а не полные исходные bytes. Поэтому план предыдущего аудита о replay любых сохранённых payloads с тем же оригинальным SHA был слишком широким: SHA полного ответа нельзя применить к его сокращённой записи. Реализован безопасный replay полного capture **внутри текущего задания**. При новом задании или повторе после рестарта details запрашиваются заново в пределах прежнего бюджета. Реестр аккаунтов и профили при этом используют общий кэш; подготовка series references не требует внешних запросов.

Долговременный replay без HTTP потребовал бы отдельного контракта хранения исходных bytes либо явно помеченной производной проекции с provenance. Это не реализовано и не имитируется пересчётом SHA под видом оригинала.

## Проверки

Тесты проверяют числовую идентичность при одинаковых никах, duplicate registry rows, Steam mismatch, source SHA/endpoint/clocks, profile fallback, private/null profiles, предел 20 и negative cache, конфликт/rejected identity, отменённое задание, повторное применение series/identity и отсутствие второго detail call на replay. Production frozen kernel и SQL001–042 не меняются.
