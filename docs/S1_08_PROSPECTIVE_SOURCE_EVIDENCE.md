## Реализованный срез

Новая forward-only [миграция 021](../packages/db/migrations/021_upcoming_source_observations.sql) добавляет `upcoming_source_observations`. Каждый успешный **живой** refresh расписания или заявки через существующий `UpcomingService` атомарно обновляет пятиминутный кеш и добавляет неизменяемую запись: ключ, endpoint, SHA исходного ответа, время fetch, серверное время записи, точный JSON нормализованного снимка и его SHA. SQL запрещает UPDATE/DELETE и не допускает `source_fetched_at > recorded_at`. Снимок добавляется только после проверки схемы и совпадения endpoint; устаревшая lease, повторное чтение кеша, отражённый секрет или ошибка провайдера запись не создают.

При чтении будущей карты граница исторической доступности такого снимка — **recorded_at**, а не задним числом назначенный `known_at` или `scheduled_at`. Даже запись до планового начала доказывает только то, что приложение тогда видело *расписание или турнирную заявку*. PandaScore ID ещё не связан с Dota map ID и Steam аккаунтами; заявка не является фактической пятёркой конкретной карты, не сообщает роли, сторону или драфт. Старые mutable cache rows не переносились в таблицу с прежним временем; миграция пустая по умолчанию. Известность героев/патча/исходов и temporal quality gate по-прежнему отсутствуют.

Рабочий DatabaseBuilder сейчас не читает эти записи как признаки и не повышает их автоматически до `strict_verified_asof`. В будущем отдельный reviewed join должен связать provider match/tournament, Dota map/series и canonical players числовыми доказательствами, затем проверить `recorded_at < map.started_at` и фактическое участие. Пока обучение и вероятности остаются `unavailable`. Это первая автоматически сохраняемая предпусковая source provenance при штатном owner refresh, без Codex и без фонового polling.

## Чтение источников на выбранный момент — 2026-11-01

Добавлен `UpcomingEvidenceRepository.readAsOf` и локальная команда:

```powershell
pnpm schedule:evidence 1756304 2026-11-01T17:12:24.000Z .tools/upcoming-evidence.json
```

Команда читает только PostgreSQL в `REPEATABLE READ / READ ONLY`, не обращается к провайдерам и создаёт новый JSON-файл с запретом перезаписи. Аргументы — строковый PandaScore match ID, прошедший UTC cutoff с миллисекундами и путь нового файла. Будущий cutoff отклоняется. `observed` означает наличие сохранённого расписания и непустых заявок обоих соперников; это **не** подтверждение состава карты, identity, актуальности объявления, результата или готовности модели. `partial`/`unavailable` сохраняют отчёт с причинами и завершают CLI кодом3; ошибки целостности не создают отчёт.

Политика `upcoming-observations-asof-v1`:

- Используются только строки с `recorded_at < cutoff`; равенство исключено. SQL сравнивает исходную точность PostgreSQL, отчёт сохраняет время записи с шестью знаками. Более ранний fetch или плановый старт не заменяют время записи.
- Поиск идёт по последним200 страницам расписания до cutoff. Выбирается последняя, на которой был указанный ID. Пропуск в более новых ограниченных страницах считается отдельно и не доказывает отмену. Если поиск упёрся в лимит, причина `schedule_history_limit` прямо сообщает неполноту поиска.
- Для турнира из выбранного объявления берётся последняя заявка до cutoff. Отсутствующая в ней команда не восстанавливается из старой заявки. Другие команды турнира не попадают в отчёт; все зарегистрированные игроки выбранных команд сохраняются, включая шестого запасного. Порядок соперников не означает Radiant/Dire, роли не назначаются.
- Проверяются SHA точного нормализованного текста, строгая схема, endpoint, совпадение source SHA/fetched time с колонками, уникальность ID встреч/команд/игроков внутри команды. Повреждённый рассматриваемый снимок останавливает чтение без подстановки старого. Один player ID в обеих заявках даёт `roster_player_conflict` и `partial`. SHA исходного HTTP-ответа сохраняется как ссылка; исходных HTTP bytes в этой таблице нет, поэтому reader не заявляет их повторную проверку.
- `mapBinding` и `lineupVerification` всегда `not_assessed`, `trainingReady/deployable:false`. Reader не создаёт context/identity proof и не меняет `knownAt:null` источника. Последующая проверка должна отдельно установить фактическую карту и сравнить сохранённое время с её настоящим стартом и границей стадии.

Повторное чтение дало идентичные отчёты; pro maps16/source observations2/datasets0/active models0/scenarios0 не изменились, новых HTTP-запросов0.
