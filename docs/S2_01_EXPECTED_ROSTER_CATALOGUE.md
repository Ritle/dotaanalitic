# Соединение ожидаемой заявки с локальным каталогом

Owner-approved S2-01/expected-roster-catalogue, 2026-11-04. Текущая заявка PandaScore служит списком кандидатов. Канонический аккаунт подтверждается числовой парой Steam32/Steam64 из OpenDota; соответствие строки PandaScore выбранному аккаунту указывает владелец. Совпадение ника не объединяет записи.

## Как пользоваться

Актуальная пакетная подготовка, общий каталог и переиспользование связей после трансферов: [S2-01/unified-player-catalogue](S2_01_UNIFIED_PLAYER_CATALOGUE.md). Ручной поиск ниже остаётся доступен.

Если ник не находится, вставьте в поле аккаунта ссылку на его STRATZ/OpenDota/Dotabuff/Steam-профиль либо Steam32/Steam64. При отсутствии аккаунта в общем каталоге сервер проверяет отдельный профиль OpenDota и предлагает его для явного выбора. Пример владельца: sailyn в заявке Spirit Academy, [inori — аккаунт480210721](https://stratz.com/players/480210721). Числовую связь строки заявки с этим аккаунтом указал владелец; профиль OpenDota подтвердил Steam64 `76561198440476449` и текущий ник inori. Это не утверждение о гарантированном участии в матче.

1. Открыть «Предстоящие матчи», выбрать встречу с двумя указанными участниками. При необходимости обновить составы.
2. Нажать **«Подготовить составы»** под заявками.
3. Для каждой стороны найти команду в OpenDota и выбрать результат с числовым ID. Для новой команды без профиля OpenDota нажать **«Использовать команду из заявки A/B»**: организация будет связана по ID PandaScore. Затем найти аккаунты участников; у каждого результата видны имя, ID и команда источника. При одинаковых никах выбрать нужный аккаунт явно. Организация игрока в источнике может отставать после трансфера.
4. В заявке из пяти участников выбраны все пять строк, но аккаунты ещё требуют выбора. В заявке из шести и более необходимо явно отметить пятерых. Неизвестные аккаунты не заполняются автоматически.
5. Подтвердить соответствие и нажать **«Сохранить связи и подставить пятёрку A/B»**. Канонические записи создаются либо повторно используются по проверенным числовым ID. Форма сценария открывается с выбранными игроками и именами.
6. Проверить роли и подтвердить 5+5 в форме. Можно сравнить историю или создать ручной сценарий одной карты. Порядок заявки сам по себе не подтверждает роли. Отдельный статус модели по-прежнему определяет возможность расчёта вероятности.

При следующих встречах доступна **«Подставить сохранённую пятёрку A/B»**. Подстановка всегда явная; перечитывание связей не заменяет ручные изменения формы. Изменившаяся заявка или конфликт числовых аккаунтов блокируют повторное использование. Сохранённые сценарии остаются самостоятельными снимками.

Рядом с сохранёнными игроками показано число локальных завершённых pro-карт. Ноль означает отсутствие подходящей локальной истории; для загрузки используется существующее действие обновления pro-истории команды. Подготовка каталога не запускает импорт карт, worker, обучение или активацию модели.

## Источники и ограничения

- Поиск использует текущий `/proPlayers` OpenDota; сервер проверяет raw SHA, схему, Steam32/Steam64 и текущие конфликты identity. Имя является поисковой подсказкой. Account IDs остаются строками.
- Организации ищутся в отдельном `/teams`, а не выводятся из `proPlayers.team_id`; прямой числовой поиск проверяет `/teams/{numeric_id}`. Полученная первая страница содержит до1000 команд и не гарантирует полноту каталога. [Первичный контракт OpenDota](https://raw.githubusercontent.com/odota/core/master/svc/api/spec.ts).
- При отсутствии организации в OpenDota используется положительно установленный ID команды PandaScore из выбранной заявки. `teams.opendota_team_id` остаётся NULL; числовой ID PandaScore никогда не записывается как игровой ID. Стабильная provider→canonical связь хранится отдельно, не создаётся по совпадению названия. Проверка Steam32/Steam64 игроков при этом обязательна. Трансфер/другой текущий team tag не запрещает выбранный состав.
- Общий поиск дополнительных профилей реализован в S2-01/unified-player-catalogue. Склейки разных аккаунтов по нику нет.
- Источник сохраняет реальное `fetchedAt`; evidence имеет `eventAt:null`, текущий `knownAt`, не утверждает историческую доступность заявки. История организации и игрока не смешивается.
- Соответствие PandaScore↔canonical хранится как текущий выбор владельца с source hashes, request ID, revision и recorded time. Оно не превращается в доказательство исторической явки или ground truth.
- Для role hints сохраняется существующее явное PandaScore-сопоставление. Правила verified identity, freshness и приоритетов ролей продолжают действовать.

## API и хранение

- `GET /api/v1/upcoming/:id/catalogue`: текущая заявка, последние связи, пригодность повторного использования и локальное покрытие pro-карт. Без внешних HTTP-запросов.
- `POST .../catalogue/search`: `{kind:'teams'|'players',query}`; до 25 кандидатов с provenance. Только поиск, без канонических записей.
- `POST .../catalogue/apply`: request UUID, provider team, выбранный OpenDota team, пять разных provider-player/account пар, expected revision, roster/registry SHA и `confirmedByOwner:true`. Сервер заново проверяет источник и membership.
- Все маршруты защищены owner session/CSRF и rate limit. Ошибки локализованы; raw payload, токены и provider error details в ответ не попадают.
- SQL **036_expected_roster_catalogue.sql** добавляет общий cache, append-only историю связей и lease операций. **037_roster_team_directory.sql** разрешает отдельный cache справочника организаций, **038_provider_team_catalogue.sql** добавляет неизменяемую числовую связь организации PandaScore с локальной записью. SQL001–036 после применения не переписываются.
- Один registry HTTP обслуживает поиск аккаунтов обеих команд, отдельный `/teams` обслуживает поиск организаций; cache годен час от фактического получения, конкурентный запрос ограничен lease, неудача имеет минутный cooldown. Новый metadata adapter использует ту же durable quota, ограничивает ответ8MiB/двумя попытками и сохраняет Retry-After. Подготовка через OpenDota обычно требует directory + registry + два team endpoint; через запись PandaScore достаточно registry и проверки заявки. Повторное использование сохранённой пятёрки не делает HTTP к источникам.
- При сохранении устаревшей заявки разрешено одно штатное обновление PandaScore. Если raw SHA изменился, требуется повторная проверка владельцем; изменившиеся данные не подставляются молча. Истёкший пятиминутный cache сам по себе не требует заново выбирать все аккаунты при неизменной заявке.
- Provisioning использует существующий `IdentityProvisioner` и его числовые conflict/fingerprint guards. Затем сохраняются role binding и append-only owner association. Если выполнение прервётся между этими этапами, безопасные записи каталога могут уже существовать; повтор их использует, существующие личности не перезаписывает. Lease предотвращает одновременное двойное сохранение одной стороны; request replay и expected revision защищают финальную связь.

## Проверки

Pure tests: неоднозначные ники, явный выбор пяти из шести, трансферы, отсутствующий/неверный Steam64, неизвестные/повторные аккаунты, tampered SHA. PG/API tests: auth/CSRF, общий cache, stale source, owner confirmation, concurrent lease, idempotent replay, immutable revisions, изменившийся roster, identity conflict и durable cooldown.

Chromium проходит путь от пустого локального каталога через обе выбранные пятёрки до сохранённого сценария, проверяет нулевую историю, повторное использование без provider HTTP, сохранность ручной правки и ширину 360px. Фикстуры синтетические и живут только в disposable PG.

Фактические результаты общего QA и live-проверки приведены в итоговом evidence и PROGRESS. Следующий срез: **S2-01/role-owner-check** — проверка подготовленных реальных пятёрок и удобства исправления ролей.
