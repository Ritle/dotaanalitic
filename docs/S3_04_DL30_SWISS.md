## Условия регистрации и оценки

На этом ПК восстановлена исходная ревизия исключений r2. Из проверенного по SHA родительского реестра взяты массивы `mapIds` и `canonicalSeriesKeys`, добавлены опубликованные ID, оба массива отсортированы. Результат байт в байт совпал с сохранённым SHA-256 `d59ce0535a1a522b7ba517d62bd85a6fa7059b6d6a465359892718ba7c46b8d7` и содержит 5 692 карты и 1 795 серий OpenDota. Повтор подготовки прежнего декабрьского пакета прошёл сверку этих исключений и остановился на версии Python. Локальная `.venv` использует 3.11.9, в исходной квитанции записана 3.13.18. [Состав исходной ревизии](evidence/s3-04-dl30-exposure-refresh-r2.json) · [Версии среды](evidence/s3-04-dl30-registration-inputs.json)

1. До срока привязать ID основной лиги OpenDota, редакции и этапа расписания к календарю ESL. Сохранить исходные свидетельства и нижнюю границу времени первой серии. Состав пар в поздних швейцарских раундах может определиться по ходу этапа.
2. Воспроизвести среду оценки, проверить SHA исполняемых файлов, дополнить восстановленные исключения с учётом новых разобранных карт, включая BLAST IX. В отдельном пути регистрации закрепить только один протокол для пересекающихся карт. Декабрьский регистратор полного турнира принимает другой SHA и срок оценки. Если срок регистрации пропущен, этот этап останется доступен для ретроспективной диагностики.
3. Сверить каждую позицию официальных раундов с полным списком серий и карт провайдера. Учитывать отмены, технические победы без сыгранных карт и пропуски. Сравнивать модели на одинаковых картах целых серий. Финальные герои и участники восстанавливаются по завершённой карте, история признаков ограничена более ранними доступными фактами, целевой исход присоединяется отдельно.
4. Действуют исходные пороги, включая 50 парных карт, 25 серий, минимум 10 исходов каждого класса, покрытие от 80% и ECE H2 до 0,10. При полном этапе из 144–216 карт покрытие потребует от 116 до 173 парных карт соответственно. Для преимущества H2 верхняя граница 95% интервала разницы log loss относительно H1 должна быть ниже нуля. Также проверяются log loss относительно H0 и Brier относительно обеих базовых моделей. Публикация вероятности в Draft Lab потребует отдельного решения и проверки применимости модели к рабочим входам. [Критерии модели](../tools/research/player-hero-conditional-future-policy.json)

## Выбор одного протокола в PostgreSQL

Миграция 074 хранит один выбор владельца для DreamLeague 30. Варианты — `full_event` (весь основной турнир) и `swiss_stage` (шесть швейцарских раундов). Для работы с двух ПК направляйте команды выбора и регистрации в одну базу: у двух отдельных копий PostgreSQL независимые записи. [Миграция](../packages/db/migrations/074_dl30_protocol_choice.sql) · [Команда владельца](../tools/research/dl30-protocol-choice.mjs)

После применения миграции оператор может посмотреть текущий выбор из корня проекта:

```powershell
node --env-file=.env tools/research/dl30-protocol-choice.mjs status
```

`no_choice` означает свободный выбор. `protocol_chosen` возвращает протокол, SHA предложения, ID владельца и серверное время решения. Для явного выбора используется форма `choose OWNER_UUID PROTOCOL PROPOSAL_SHA256`. Команда записывает **окончательный выбор окна**. Используется SHA предложения из таблицы:

| Протокол | SHA-256 предложения |
| --- | --- |
| `swiss_stage` | `5d6015e97563ed366f5ec40ec3c941c3896607b29c1e0b0735431bd5be2b55f0` |
| `full_event` | `9f38b8f0af80b905e6fe6d04f0249e320f82dd5fbbd2065141e8288ceb569045` |

Действующий регистратор полного турнира фиксирует свой вариант при первой успешной записи пакета, в той же транзакции. При обновлении существующей базы уже записанная попытка сохраняет исходное время и владельца, в том числе когда квитанция ещё ожидается. Две конкурирующие транзакции получают только один выбор. Откат первой освобождает выбор. Повтор того же решения тем же активным владельцем возвращает первоначальную запись, в том числе после срока 30 ноября, 21:00 МСК.

Выбор окна сам по себе не выдаёт квитанцию регистрации, не запускает сбор и не публикует прогнозов. Для швейцарского этапа ещё требуется путь регистрации, который свяжет выбранный протокол с проверенным пакетом, источниками этапа и актуальными исключениями.

22 ноября прошли 6 тестов выбора и 5 тестов прежнего пути сбора на временных базах PostgreSQL. В тестах конкуренции использованы синтетические сведения о турнире. Ожидание второй транзакции зафиксировано по блокировкам сервера для обоих вариантов. [Интеграционные тесты](../packages/db/tests/dl30-protocol-choice.integration.test.ts)

Первая транзакция сохраняет доказательства с их SHA-256. Вторая сверяет время сервера и актуальность исключений, затем записывает одну квитанцию. Появление карты между транзакциями, попытка подтвердить собственную незавершённую запись или достижение срока блокируют квитанцию. Повторные попытки можно проверить чтением сохранённого SHA.
