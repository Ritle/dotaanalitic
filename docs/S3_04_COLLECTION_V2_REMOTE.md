# Draft Lab — ограниченный сбор OpenDota

20 ноября 2026. Задача `S3-04/conditional-collection-v2-remote-adapter`.

Один вызов CLI обрабатывает одну рекомендацию discovery в первом проходе зарегистрированного эксперимента. Это позволяет продолжить с сохранённого места после прерывания. Расписание автоматических запусков и повторный удалённый обход уже завершённого списка в этот срез не входят.

## Запуск

Для заранее зарегистрированного эксперимента оператор создаёт локальный JSON-запрос со следующими полями.

```json
{
  "mode": "opendota-remote",
  "ownerId": "<UUID активного владельца>",
  "registrationId": "<UUID подтверждённой регистрации v2>",
  "registrationSha256": "<SHA-256 пакета регистрации>",
  "operationId": "<UUID одной операции>"
}
```

```powershell
node --env-file=.env tools/research/run-conditional-collection-v2-remote.mjs --request request.json
```

После прерывания повторяют тот же файл. Сохранённые байты привязываются к журналу по исходной попытке. Резерв без квитанции даёт `inflight_outcome_unknown` и требует проверки. При `resume_required` ответ содержит UUID незавершённой операции. Новый UUID означает явный запрос следующего шага. Отказ источника или лимита записывается в журнал. Ответ `no_next_request` содержит причины остановки из discovery.

Действующая регистрация требует ревью основных изданий турниров, сверки исключений и подтверждения транзакции до крайнего срока. Для удалённого запуска оба новых файла CLI и адаптера должны войти в закреплённый манифест. Сборщик сверяет владельца, пакет, файлы и среду, получает блокировку на регистрацию и выбирает следующий endpoint по воспроизведённому архиву. Общая PostgreSQL-квота выдаёт разрешение перед HTTPS-запросом. Перед отправкой перепроверяются действительность резерва и срок сбора. Используется публичный OpenDota без ключа, с фиксированным адресом и запретом редиректов. Полный ответ 2xx ограничен 8 МиБ. Невалидный полный ответ сохраняется с отметкой ошибки. При сбое записи наблюдения квоты попытка остаётся открытой.

## Перенос H2 со старого ПК

Самый короткий путь — перенести со старого ПК `.tools/s304-hero-fit-r1/artifact.json`. Если расположение неизвестно, скопируйте [скрипт поиска H2](../scripts/recover-draft-h2.py) в корень старого проекта и запустите оттуда:

```powershell
python recover-draft-h2.py .
```

Скрипту нужен только Python 3.8 или новее. Он ищет в JSON-файлах проекта, в том числе в скрытой папке `.tools`. Проверяются исходный файл, сохранённый теневой результат, экспорт нескольких записей драфта и пакет регистрации с вложенным текстом модели. Путь к отдельному JSON или каталогу экспорта можно передать вместо точки. При совпадении закреплённой SHA-256 скрипт сохраняет точные байты в `DraftLab-H2-recovered/artifact.json` и печатает полный путь. Перенесите папку `DraftLab-H2-recovered` в корень проекта на новом ПК. В ней нужен один файл — `artifact.json`.

Если на старом ПК запись драфта сохранилась только в PostgreSQL, в собранном старом проекте можно выполнить штатный экспорт. Первая команда читает БД из локального `.env` и сохраняет новый файл в `.tools`. Вторая ищет модель внутри него.

```powershell
node --env-file=.env tools/audits/draft-committed-shadow.mjs capture .tools/h2-recovery-shadow-export.json
python recover-draft-h2.py .tools/h2-recovery-shadow-export.json
```

### Запись декабрьского протокола в PostgreSQL

Миграция [072](../packages/db/migrations/072_dl30_registration.sql) добавляет таблицы `dl30_registrations` и `dl30_registration_receipts`. [Локальный регистратор](../tools/research/register-dl30.mjs) работает на закреплённом Node 22.15.0 из корня проекта. Первая команда принимает файл ревью, актуальные исключения и путь для нового пакета. Вторая требует явной передачи UUID активного владельца и SHA-256 именно того файла, который он проверил.

```powershell
.tools/node22/node.exe tools/research/register-dl30.mjs package .tools/dl30-review.json .tools/dl30-exclusions.json .tools/dl30-reviewed-package.json
.tools/node22/node.exe --env-file=.env tools/research/register-dl30.mjs register <UUID-владельца> .tools/dl30-reviewed-package.json <SHA-256-пакета>
```

Имена в примере обозначают будущие входы владельца. Поля ревью следуют [контракту привязки турнира](S3_04_TOURNAMENT_BINDING_V2.md). Укажите `format=dl30-tournament-review-v1`, SHA декабрьского предложения в `policySha256`, фактические часы получения источников и проверки, одну привязку DreamLeague Season 30. Календарь ESL, запись каталога OpenDota и ссылка организатора на конкретную лигу сохраняются с телами источников. В `exclusions` входят массивы строк `mapIds` и `canonicalSeriesKeys` от r2 со всеми последующими известными исключениями. Полученная от команды `package` сумма идентифицирует подготовленные байты. Регистрация состоится только после ревью и второй команды.

PostgreSQL сверяет исключения с текущими картами, сериями и квитанциями импорта при обеих записях. Первая транзакция сохраняет пакет, вторая подтверждает уже зафиксированную запись и проверяет срок ещё раз. Успех определяется наличием квитанции. Повтор команды возвращает исходную квитанцию. Если между транзакциями импорт добавил новую карту или серию, требуется дополнить исключения, повторить ревью и передать новый SHA. Предыдущая попытка сохраняется в истории. У декабрьского протокола может быть одна подтверждённая регистрация. Результат `registered_plan_only` относится только к плану проверки.

### Первый запрос декабрьского сбора

Миграция 073 и команда ниже добавляют одну явную попытку чтения списка карт. Оператор сохраняет UUID операции и использует его при каждом повторе. SHA-256 берётся из подтверждённой квитанции декабря. Запуск требует миграции в выбранной базе.

```text
node --env-file=.env tools/research/run-dl30-first-collection.mjs <registrationSha256> <operationId>
```

PostgreSQL сверяет квитанцию активного владельца, SHA регистрации, ID лиги и окно `[2026-12-01T00:00:00Z, 2026-12-29T00:00:00Z)`. Сначала фиксируется запись `dl30_first_requests`, затем используется общий лимит OpenDota. Единственный допустимый запрос — `GET /api/leagues/<registeredLeagueId>/matches`. Клиент соблюдает лимит 8 МиБ на ответ, таймаут и `Retry-After`. При успешном HTTP-ответе сохраняются исходные байты, их SHA-256, серверное время и результат проверки формата. При отказе сохраняются статус и код ошибки. Обе таблицы доступны только на добавление.

Повтор с тем же UUID возвращает сохранённую квитанцию даже после закрытия окна. Если есть только запись попытки, команда возвращает `inflight_outcome_unknown`. Другой UUID также не запускает второй запрос. Так обработанные ответы переживают сбой между записью и выводом, а сбой до записи ответа требует ручной сверки. Детали карт и оценка H2 потребуют отдельного шага.
