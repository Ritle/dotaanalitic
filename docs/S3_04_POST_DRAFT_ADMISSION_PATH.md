# Путь допуска модели после драфта

Решение по запросу владельца от 14 ноября 2026. Задача `S3-04/post-draft-admission-roadmap`. Это план работ, а не разрешение публикации вероятностей или регистрация нового эксперимента. Отдельное исследование времён API отложено; проверка доступности входов и корректность независимой оценки сохраняются.

## Что именно хотим выпустить

Пользователь вручную выбирает десять разных героев для выбранных игроков, сохраняет карту и получает вероятность победы **одной карты** от отдельно допущенной post-draft модели. Автоматическая загрузка пиков, полный порядок драфта и live-телеметрия для первого такого расчёта не обязательны. Нужны проверенные аккаунты, допустимая предыдущая pro-история и точная фиксация выбранных входов. Прогноз не учитывает текущий счёт, золото, предметы, башни или исход целевой карты.

Наиболее подготовленный исследовательский кандидат — **H2_cal**: сила выбранной пятёрки Elo плюс наблюдаемый объём профессиональной практики каждого игрока на выбранном герое за 90 дней. Это **не полноценная оценка сочетания героев**: в нём нет отдельного моделирования контрпиков, синергии, ролей или пабликов. Сравнения: H1_cal с тем же Elo без hero-practice и фиксированный H0. Рекомендуется продолжить уже подготовленный протокол H2, не выбирать новую модель по результатам старого теста.

## Почему нельзя просто активировать H2

[Последняя оценка](S3_04_PLAYER_HERO_EXPERIMENT_EVALUATION.md) на 186 картах/86 сериях дала log loss H2_cal **0,631092**, H1_cal **0,634834**. Разница −0,00374137; 95% парный интервал по сериям **[−0,00991893; +0,00209662]** включает ноль. Результат по заранее выбранному критерию — **negative**, несмотря на улучшение средних метрик. 124 правильных выбора из186 не доказывают будущую точность66,67%.

Этот корпус уже раскрыт, поэтому повторное обучение, повторный backtest или расширение ранней истории не превращают его в независимый выпускной тест. Прежний вариант M2 с признаками идентичности героев тоже не допущен: [R2](S3_04_R2_OFFLINE_EVALUATION.md) не показал преимущества и не прошёл несколько критериев качества. Старые результаты и пороги остаются неизменными.

## Последовательность до выпуска

**Выполнено 14 ноября:** [offline shadow runtime](S3_04_POST_DRAFT_SHADOW_RUNTIME.md) сохраняет fixed H0/H1/H2 и поддерживает pending ID. Его новая политика исключает исторические встречи тех же десяти аккаунтов и целые известные серии; её нужно явно учесть до независимой регистрации. В рабочей БД пока нет captures/observations, положительный live-прогон не заявляется. Следующий срез — `S3-04/post-draft-validation-readiness`.

**Подготовка регистрации, 14 ноября:** [проверка готовности](S3_04_POST_DRAFT_VALIDATION_READINESS.md) зафиксировала минимальный exposure union2260карт/1096серий,26неопределённых series aliases,0captures и отсутствие ещё не начавшегося выпуска в локальном Tier1-каталоге. Новое численное ядро проверено на синтетике и пока отклоняет реальные payloads без verified source adapter. Регистрация закрыта; ближайший срез той же задачи — durable shadow persistence при сохранении драфта.

1. **Сквозной теневой расчёт выбранного драфта.** Связать immutable capture/history → прежние H0/H1/H2 inputs → проверенный fixed inference → отдельный неизменяемый исследовательский результат. Никакого повторного fitting или показа вероятностей в пользовательском интерфейсе. Проверить реальные ограничения снимка, причины отказов, десять account/hero bindings, временные границы, A/B, дубли, повторное выполнение и Python/TS parity.

   Практический разрыв сейчас: combined inputs требуют поздней native-привязки, а SQL059 проверяет уже имеющуюся фактическую карту. Нельзя объявлять такой путь расчётом до старта. Нужен отдельно проверенный путь pending target без фиктивного Dota ID: выбранная встреча/карта фиксируется заранее, целевой исход никогда не становится историческим признаком, позднее связывание не пересчитывает исходные входы. Если безопасное исключение цели не установлено — `unavailable`. Новые оболочки не меняют численные рецепты frozen builders молча.

2. **Подготовить независимую оценку к регистрации.** До начала целевых серий закрепить исполняемый код, артефакт, evaluator/environment, полный реестр ранее раскрытых карт/серий, конкретные выпуски Tier1, даты, полный знаменатель и выполнимость бюджета. Все фактически сыгранные карты области учитываются, включая пропуски. История игроков может включать другие уровни pro-турниров. Ручных подтверждений Tier1 для каждой попытки пользователя не добавлять.

   Точное определение времени начала игры нужно здесь для зачёта настоящих предварительных расчётов, а не как самостоятельное условие арифметики модели. Ввод героев владельцем допускается и не требует API пиков. Однако существующий [протокол](S3_04_PLAYER_HERO_INDEPENDENT_VALIDATION_PLAN.md) требует сохранения расчёта до подтверждённого gameplay start: одна серверная отметка доказывает время записи, но не фазу игры. До выполнения этого условия регистрацию/сбор по старому протоколу разрешать нельзя. Если понадобится другая conditional-когорта, сначала отдельная связанная версия и явное решение владельца, затем новые данные; старые критерии не переписываются.

3. **Провести один независимый тест фиксированного кандидата.** Текущий подготовленный протокол предусматривает 28 дней сбора и7 дней на исходы; даты пока не назначены. Минимумы: **50 карт,25 серий,10 исходов каждого класса,80% покрытия** полного знаменателя. На одинаковых картах нужны верхняя граница95% CI для log loss H2_cal−H1_cal ниже0, log loss ниже H0, Brier не хуже H0/H1_cal и ECE≤0,10. Сохраняются2000 парных bootstrap-повторов целых серий, seed42 и прочие зарегистрированные правила. Это инженерные минимумы, не гарантия достаточной мощности или успеха. Не останавливать тест при удобном результате, не продлевать окно и не снижать критерии после просмотра метрик.

4. **Отдельно подготовить выпуск прошедшей модели.** Даже положительный независимый исследовательский итог не означает активацию. Нужны post-draft release manifest и независимый gate, проверка применимых patch/hero-eligibility ограничений выбранных признаков и области выводов, registry/inference для stage `post_draft`, SHA/feature order/calibrator/parity, сохранение input/model snapshots и исходов отдельно, недоступность при недостатке данных, атомарная активация и rollback. Не выдавать pre-match V1 за post-draft модель и не закрывать неиспользованные требования по предположению.

5. **Подключить результат в Draft Lab.** После сохранения полного драфта сервер автоматически готовит входы и вызывает допущенную post-draft модель. Интерфейс показывает результат либо конкретную причину недоступности. Прежняя V1 до драфта продолжает работать отдельно. В статистике реальных прогнозов учитываются только подходящие зафиксированные до игры расчёты с отдельно проверенным исходом; повторные сценарии не увеличивают число независимых карт.

Если независимый тест даёт `negative`/`insufficient`, H2 не выпускается. Для улучшения модели нужен новый зарегистрированный эксперимент: новые признаки/обучение только на development, отдельная calibration и ещё не использованный конечный тест. Выбор победителя по старому holdout, подмена calibrated варианта raw-вариантом или публикация50/50 не являются запасным путём.

## Ближайшая реализация

**S3-04/post-draft-shadow-runtime:** реализовать offline теневой расчёт fixed H0/H1/H2 по серверному снимку выбранного владельцем драфта, включая безопасный pending target и замороженный результат. В production UI вероятности пока не добавлять; сбор по independent protocol не регистрировать автоматически. Проверка первой реальной записи должна явно сохранить её диагностическую/временную пригодность, а не выдать тестовую фикстуру или поздний снимок за prospective пример.

DoD: единый воспроизводимый путь, immutable output/SHA/replay, поздние/недоступные данные дают структурированный отказ, ни целевой label, ни поздняя привязка не меняют исходные входы, одна actual map не размножается. Артефакт и отрицательный первый результат H2 сохранены, рабочая V1 не меняется. Рекомендуемая модель: **GPT-6 Astra · High**.
