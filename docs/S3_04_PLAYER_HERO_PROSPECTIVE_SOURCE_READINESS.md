# S3-04 — готовность источников и сохранения реального драфта

**14 ноября 2026: аудит выполнен, сборщик ещё не готов.** Ручной ввод драфта остаётся рабочим направлением для первой post-draft версии. Ждать обязательного автоматического получения всех пиков не требуется. Следующая реализация — доверенное сохранение полного входа владельца; независимое окно H1/H2 не зарегистрировано.

Проверены код и данные действующего сервиса, три ранее сохранённые реальные карты OpenDota/STRATZ и один ограниченный запрос STRATZ Live. Нет обучения, импорта карт, новых миграций, изменения V1 или API/UI. Проверочный запрос изменяет только существующий счётчик квоты STRATZ. [Воспроизводимый аудит](../tools/audits/player-hero-source-readiness.mjs), [тесты](../tests/node/player-hero-source-readiness.test.mjs), [evidence](evidence/s3-04-player-hero-prospective-source-readiness.json).

## Что уже есть

`ScenarioRepository.save()` сохраняет ревизию сценария транзакционно. `scenario_input_snapshots` защищены от UPDATE/DELETE; триггер миграции 015 самостоятельно записывает `clock_timestamp()`. История предыдущих ревизий не заменяется. Драфт связывает роль A/B с героем, а состав — ту же роль с canonical player ID. Поэтому сервер может получить однозначные пары игрок/герой без повторного назначения ролей.

Это проверено не только по файлам: read-only запрос к системному каталогу PostgreSQL подтвердил, что триггер включён, а тело действующей функции совпадает с миграцией 015. Изменения или тестовые записи в рабочую БД для проверки не вносились.

Read-only SQL-инвентаризация рабочей БД:

| Наблюдение | Результат |
|---|---:|
| Сохранённых ревизий сценариев | 10 |
| Ревизий с десятью разными героями | 4 |
| Разных сценариев среди этих четырёх ревизий | 1 |
| Ревизий, записанных раньше указанного input cutoff | 9 |
| Ревизий с `context.seriesId` | 0 |
| Ревизий с номером карты | 9 |
| Ревизий с `targetMatchId` в input | 0 |

Четыре драфта записаны 12 ноября до планового времени встречи. Это **не четыре проверенных прогноза** и не доказательство фактического pre-start: расписание, реальная карта, время начала и совпадение финальных игроков/героев не связаны. Старые сценарии не переименовываются в prospective evidence задним числом.

## Чего нет в текущем сохранении

| Разрыв | Последствие | Ограниченное решение |
|---|---|---|
| В input хранятся player IDs, но не выбранные Steam32 и их доказательства | Позднее изменение identity mapping может изменить трактовку старого драфта | Заморозить десять подтверждённых account links и их observation IDs/SHA вместе с игроками и героями |
| `cutoffAt` приходит из редактируемой формы; для расписания исходно равен scheduledAt | Это пользовательский срез аналитики, а не серверное время принятия прогнозного решения | Отдельный серверный `decisionCutoffAt`, не переписывающий старый cutoff |
| API сценария возвращает recordedAt через JS Date | Теряется точность ниже миллисекунды | Для строгого сравнения читать PostgreSQL timestamp в точном строковом/microsecond представлении |
| `scheduleTarget` переносится в query маршрута; полный draft input не хранит его binding | Ссылка браузера сама по себе не доказывает назначение сохранённой ревизии реальной карте | Сохранить проверенную ссылку на provider match/series и номер карты отдельной неизменяемой записью |
| Существующая scheduled-runtime привязка обслуживает первую карту и pre-match V1 | Её нельзя автоматически объявить привязкой любой post-draft карты BO3 | Отдельная post-draft связь с конкретным ordinal; никакого прогноза победителя серии |
| Нет единого снимка драфта, identity evidence, доступной истории и вычислений H1/H2 с временем записи | Сохранение формы не доказывает сохранение полного прогнозного входа до старта | Новый server-side capture с явной ревизией, идемпотентностью и перечнем недоступных данных |

Сами ограничения актуальны для нового post-draft пути. Они не добавляются как условия к работающей V1 и не возвращают повторные подтверждения пятёрок или Tier 1.

## Что показали источники

### Сохранённые реальные карты

Взяты заранее ограниченные ID `9070527945`, `9068910292`, `9067177642` из существующих receipts. В каждой карте OpenDota имеет проверенный профессиональный исход, STRATZ — десять разных аккаунтов, десять разных героев и десять pick-событий. Дополнительно сверены все **30 связок slot → Steam32 → hero** и сторона. Все совпали. Unix start timestamps OpenDota и STRATZ совпали на трёх картах.

При этом все STRATZ receipts получены после указанного начала, `knownAt:null`. Это подтверждает пригодность полей для последующей сверки фактического драфта, но не доказывает доступность до старта. Совпадающие часы двух источников также не устанавливают точную границу «выбор героев → игра».

Отдельно прочитаны три самые поздние принятые pro-карты локальной БД: `9076476183`, `9076387949`, `9076056982` от 4 ноября. У них есть accepted receipts и series ID, но `map_number:null`, `known_at:null`; receipts получены 5 ноября. Их нельзя превратить в новые наблюдения до старта. Это локальная выборка, не утверждение о полноте истории турниров.

### Один запрос STRATZ Live

Ранее сохранённая официальная introspection-схема содержит `live.matches`, `matchId`, `gameState`, `gameTime`, `delay`, `players.steamAccountId/heroId/playerSlot/isRadiant`, created/modified timestamps. Есть состояния выбора героев, стратегии, pre-game и игры. [Официальный вход в API STRATZ](https://stratz.com/api).

Выполнен **один** запрос `live.matches(request:{isLeague:true,isCompleted:false,take:5})` только этих идентификационных/временных полей. HTTP 200, GraphQL errors нет, список пуст. Это подтверждает доступность запроса с настроенным токеном, но не наличие предматчевого покрытия. Повторный опрос и поиск «пока не найдём успешную карту» не выполнялись. `isLeague:true` не приравнивается к проверенному pro или Tier 1.

Использована существующая durable-квота `RoleProfileRepository.claimStratz`; максимум одна попытка, timeout 15 секунд, ответ не более 1 MiB, без redirect/retry. Учтены Retry-After и оставшиеся лимиты. Credentials, K/D/A, золото, предметы, преимущества и чужие вероятности не записывались. Этот запрос не включает STRATZ автоматически в production-прогноз.

### Семантика времени

- PandaScore описывает `scheduled_at` как плановое время; до старта `begin_at` повторяет его, после перехода в running — начало встречи. Это ещё не timestamp начала конкретной Dota-карты после драфта. [Документация жизненного цикла](https://developers.pandascore.co/docs/matches-lifecycle).
- OpenDota описывает `start_time` как Unix timestamp начала игры, но описание не уточняет интересующую нас границу относительно драфта/pregame. [Официальная схема](https://github.com/odota/core/blob/master/svc/api/responses/properties/commonProperties.ts). Их replay parser отдельно определяет game zero по игровому событию и нормализует время логов; это не разрешает автоматически переводить Unix start в эту границу. [Код парсера](https://github.com/odota/parser/blob/master/src/main/java/opendota/Parse.java).
- В сохранённой схеме STRATZ описание `MatchType.startDateTime` отсутствует. Live phase и относительный `gameTime` полезны для будущего пилота, но значение `fetchedAt - gameTime` не считается проверенным UTC start: остаются задержка источника, паузы и значение часов.

Аудит не утверждает, что источники дают неправильное время. Подтверждение точной семантики ещё не получено. До проверки source clocks нельзя засчитывать результаты в независимую prospective оценку.

## Следующая реализация

**S3-04/player-hero-owner-capture:** сделать минимальный серверный путь фиксации полного выбранного драфта. Вход — existing scenario ID + expected revision; сервер читает сохранённую ревизию, фиксирует пары A/B/player/account/hero и доказательства, берёт собственный cutoff, связывает её с сохранённым назначением карты. Пользователь не вводит повторно составы, роли, Tier 1 и временные поля для этой технической операции.

Сохранение должно быть транзакционным и идемпотентным, доступным только владельцу, с неизменяемым JSON/SHA и отдельным точным recorded_at. Изменившаяся ревизия — явный конфликт; неполные данные — сохранённый отказ/диагностика. Никаких исправлений старых снимков или подмены на текущие составы.

Доступная локальная история фиксируется в той же операции через неизменяемые факты/receipts и их clocks, а не только номер текущей версии БД. Отсутствующая история остаётся причиной отказа для этого снимка. Догрузка после cutoff может помочь следующему снимку, но не исправляет доступность предыдущего задним числом.

Если реальный map ID ещё неизвестен, использовать отдельную типизированную ссылку «provider series/match + map ordinal» со статусом pending. Не придумывать Dota match ID и не заполнять его плановым provider ID. Позднее связывание должно быть отдельной неизменяемой записью и не менять исходный снимок; для неоднозначной пары оставлять unavailable. Старый offline capture требует разрешённый targetMatchId, поэтому pending envelope не объявлять прошедшим этот контракт. Его дальнейший адаптер потребует отдельной проверки совместимости.

Первый срез — capture-only, без вероятностей, активации H1/H2 и регистрации 28-дневного окна. После него: ограниченный пилот для фактической связи карты/начала, доступности истории, времени сохранения вычислений и сверки финального драфта. Пилотные карты считаются уже просмотренными и не становятся независимым holdout автоматически. Автоматический импорт пиков — дополнительный путь к тому же контракту, не обязательное условие ручного Draft Lab.

Рекомендуемая модель следующей задачи: **GPT-6 Astra · High**.

Полные QA-результаты — в evidence и PROGRESS.
