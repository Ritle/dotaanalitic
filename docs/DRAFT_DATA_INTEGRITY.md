# P0 — Целостность данных профессиональных карт и драфтов (v9)

**Статус:** нормативный архитектурный контракт для S0-01/S0-02/S0-08/S1-08/S2-02/S3-00/S3-04. **Это требование, а не готовый production Data Collector.**

## 2. Ключевое разделение данных — неизменяемый источник и производные представления

1. **Raw source observation.** Сохранять оригинальный массив `picks_bans` **как получен** (включая 0, 11, 12 событий, дубли и противоречивые order/team), со статусом `missing` в случае `null/absence`, провайдером, версией адаптера, `fetched_at`, `payload_sha256`, `match_id`, ссылкой на исходный снапшот; не удалять «лишние» пики, не сортировать и не заменять данные при сохранении. Не сохранять ключи доступа к API или заголовки с секретами. Raw-представление — `match_draft_source_observations`; исходный HTTP-ответ при разрешённом хранении — `match_source_snapshots.raw_blob_ref`.
2. **Final draft / observed played heroes.** Десять фактических героев участников сохраняются отдельно в `match_players.hero_id`, связанные со строго проверенными `player_slot` и сторонами. Это результат игры, доступный как условное состояние **после завершения драфта**, но для настоящего исторического прогноза нужна проверка соответствия драфту и доступности в момент post-draft cutoff.
3. **Validated draft timeline.** `match_draft_actions` хранит **только события, прошедшие соответствующий контракт нормализации**, с версионированной политикой/провенансом. `draft_status='complete'` запрещён, пока не установлены соответствие picks, стороны и историческая допустимость хронологии; необработанные/аномальные события остаются в raw observation. Нельзя «исправить» history удалением 11-го или 12-го события только ради десяти героев.
4. **Quality assessment.** `match_quality_assessments` — отдельная ревизионная оценка различных граней качества. Нельзя записывать один бинарный `is_valid` на всю карту. При улучшении нормализатора создавать новую оценку, не переписывать историю; активную policy выбирать явно.
5. **Training features.** Строить из валидированных фактов as-of (`event_at`, `known_at`, `fetched_at` отдельно), не из raw `picks_bans` напрямую. Ссылка на quality policy/version включается в frozen manifest и fingerprint набора.

## 3. Ортогональные показатели пригодности

| Сигнал | P0 контракт | Не делать |
|---|---|---|
| `outcome_eligible` | подтверждённая pro-карта, `match_id`, `started_at`, `radiant_win`, обе стороны | Не приписывать исход команде при неизвестном ID |
| `player_eligible` | 10 уникальных слотов, проверенные canonical identity для нужной статистики | Отсутствующий игрок ≠ неизвестное имя в качестве ID |
| `hero_eligible` | 10 уникальных `hero_id` и 5 героев каждой стороны, про-контекст и verified outcome | Не требовать историю bans для hero-only анализов |
| `team_eligible` | два подтверждённых различных ID **исторических** организаций | Не восстанавливать из текущих команд игроков или совпавших никнеймов |
| `series_eligible` | проверенный идентификатор серии и принадлежность карты, если нужен grouping | `series_id=0` ≠ BO1 и не значит серия 0 |
| `draft_picks_exact` | 10 истинных `is_pick` | Не считать непустые действия валидным драфтом |
| `draft_heroes_match` | множество 10 героев пиков совпадает с 10 финальными | Не игнорировать дополнительные/отсутствующие hero IDs |
| `draft_teams_match` | проверенные `team` и стороны: по 5 точных соответствий героям Radiant/Dire | Не переносить неизвестный `team` на Radiant по порядку или ID организации |
| `draft_order_integrity` | целочисленный, уникальный и допустимый по форме `order` | Не путать структурную целостность с правилами Captains Mode |
| `draft_order_valid` | **только** после проверки `game_mode`/`lobby_type`, правил пиков и банов для конкретного патча/турнира | Не заявлять `true` на основании лишь 10 пиков |
| `draft_eligible` | downstream оценка по версии policy: picks, bans, side, order/режим проверены | Не использовать для hero-only post-draft, которому timeline не требуется |
| `training_eligible` | функция **stage + feature policy + known-as-of + dataset revision**, а не статический флаг матча | Не считать `hero_eligible` достаточным доказательством честного post-draft backtest |

Хранить причины в `anomalies[]` машиночитаемыми кодами: `TEAM_ID_MISSING`, `SERIES_ID_UNKNOWN`, `PICK_COUNT_EXTRA`, `PICK_COUNT_MISSING`, `PICK_EXTRA_HERO`, `PICK_MISSING_HERO`, `DRAFT_SIDE_MISMATCH`, `DRAFT_ORDER_DUPLICATE`, `DRAFT_EVENTS_MISSING`, `DRAFT_MODE_UNKNOWN`, `ROLE_UNVERIFIED`. Причина + источник + версия нормализатора + время проверки обязательны для расследования. **Не превращать неизвестный результат проверки в `false`:** использовать `unknown`/`null`, когда проверка не выполнялась.

## 4. Применение к моделям и аналитике

- **Hero/player/pair/counter descriptive:** использовать карты с доказанными десятью участниками, сторонами, финальными героями, исходом. ID организации необязателен, если не нужен конкретной метрике.
- **Team rating/organization statistics:** только подтверждённая historical organization identity; карты без неё могут участвовать в независимых общих геройских агрегатах.
- **Exact-five cohesion:** требуется каноническая личность пяти игроков и стороны, не обязательно organization IDs.
- **Pre-map:** только признаки с `known_at <= cutoff_at`, не подставлять фактические post-match lineups, даже если `player_eligible=true`.
- **Post-draft model (final 10 heroes):** не требует валидированного **Draft Timeline**, если ввод и финальный драфт подтверждены к cutoff; ретроспективно извлечённые герои — отдельный условный backtest cohort, не имитация живого прогноза.
- **Draft-sequence analysis (P1):** требует отдельного `draft_order_valid`, основанного на исторических правилах и режиме. Никаких «правдоподобных исправлений» аномальных picks.
- Данных с `is_pro` неизвестно / соревновательный уровень не подтверждён — не включать в pro-only corpus по одному наличию совпадающих героев или `leagueid`; хранить `pro_source_evidence` и отдельный `tournament_tier` с provenance/`known_at`. `proMatches` — сигнал discovery, классификация турнира — отдельная политика.
- Повторный импорт и исправление источника создают новые оценки/снапшоты, но не изменяют ранее замороженные прогнозы/датасеты.

## 6. Acceptance gates / регрессии

Обязательные синтетические кейсы (похожие **формой**, не утверждающие подлинные raw OpenDota payloads):

- 10 финальных героев + 12 различных `is_pick`, 2 extras → `hero_eligible`, но `draft_picks_exact=false`, `draft_heroes_match=false`, timeline не публикуется.
- 10 финальных + 11 picks, 1 extra → аналогично.
- 10 финальных + 0 picks / 1 raw action → `hero_eligible`, `draft_eligible=false`.
- 10 picks идеально совпадают, но `series_id=0`/нет обоих team ID → `hero_eligible` может быть true; `team_eligible=false`, `series_eligible=false`.
- 10 picks совпадают по множеству, но ошибочная side → `draft_teams_match=false`.
- Два raw import одинакового матча → канонический match один, payload dedup, assessments под policy version; новый payload создаёт новую source observation.
- **Без patch rule registry** `draft_order_valid=null` даже при идеальных событиях.
- Unknown `game_mode`/`lobby_type` или role нельзя молча апгрейдить до подтверждённых Captains Mode/Pos1–5.
- Для исторического pre/post вычисления отсутствует verified known-as-of → только conditional analysis/unavailable, не prospective accuracy.

Выпуск числового прогноза требует **отдельного успешного model evaluation gate** (`docs/ML_ENGINEERING_DECISIONS.md`), а не только положительных quality flags.
