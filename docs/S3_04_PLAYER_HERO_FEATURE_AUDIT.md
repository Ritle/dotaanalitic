# S3-04 — покрытие профессионального опыта игрока на герое

Историю игрока на выбранном герое можно рассматривать как **дополнительный исследовательский признак с явными пропусками**. Сейчас нельзя требовать хотя бы пять прошлых игр на герое у каждого из десяти участников: такое условие оставляет только **1 из 186** пригодных поздних карт. Это аудит наличия данных, а не доказательство полезности признака или готовности новой модели.

[Результаты, SHA и правила](evidence/s3-04-player-hero-feature-audit.json). Входы — [замороженный R2](S3_04_R2_FROZEN_DATASET.md); [отрицательная оценка R2](S3_04_R2_OFFLINE_EVALUATION.md) сохранена. Рабочий pre-match прогноз не меняется.

## Что проверено

Полный исходный реестр — 2232 карты. Покрытие рассчитано для 1657 пригодных R2-целей (881 train, 306 validation, 284 calibration, 186 поздних), без изменения прежней пригодности или отбора по исходу. Для остальных строк сохранены причины и `players: null`. 16 570 пар «участник целевой карты — герой» — **не** независимые карты и не новые обучающие наблюдения.

Из 2186 проверенных pro-карт истории удалось связать участников с героями в 2180. Шесть карт исключены из hero-истории целиком: в исходном hero capture отсутствует хотя бы один canonical player ID. Список сохранён в отчёте; количество таких прошлых карт отдельно учитывается как неполная история для затронутых игроков. Это консервативное исключение целой карты, не утверждение, что у всех её участников неизвестен герой. Непустые противоречащие ID, receipt/account/SHA и дубликаты вызывают отказ.

Входная история ограничена локальным окном `[2024-01-01; 2026-11-05)` UTC, с реальным временем capture 2026-11-13T16:08:56.576Z. «Вся история» ниже означает весь доступный локальный корпус в этом окне, а не карьеру игрока. Полнота удалённых данных не установлена. Новые 28 карт R2 используются только как более ранняя история, не расширяют реестр целей.

Warmup содержит 6 плановых целей без пригодных R2-target rows; ещё 15 исходных целей лежат вне зарегистрированных окон. Они сохранены в полном реестре. Для пустой выборки медиана/min/max — null.

В позднем блоке 314 из 1860 участник×цель не имеют ни одной ранней локальной игры на выбранном герое; за последние 90 дней таких записей 595. Нельзя превращать это в штраф или вывод «игрок не умеет играть на герое».

## Если сделать опыт обязательным для всех десяти

Диагностические пороги 1/3/5/10 и окно 90 дней закреплены в коде до подсчёта покрытия. Это не quality gates и не подобранные параметры модели. Существующие gates/denominators R1/R2 не менялись.

| Минимум игр на герое у каждого | Train, вся история | Поздние, вся история | Поздние, последние 90 дней |
|---|---:|---:|---:|
| 1 | 182 / 881 | 42 / 186 | 7 / 186 |
| 3 | 15 / 881 | 4 / 186 | 0 / 186 |
| 5 | 1 / 881 | 1 / 186 | 0 / 186 |
| 10 | 0 / 881 | 0 / 186 | 0 / 186 |

Такое жёсткое условие сделало бы модель недоступной для большинства карт. Следующий эксперимент должен сохранять численность и признаки неполноты; raw win rate на малом N не следует выдавать за прогноз. На этом этапе win rate, сглаживание и новые вероятности не вычислялись, полезность count-признака не измерена.

## Временные границы, идентичность и составы

Переиспользована действующая проверка verified pro-map/outcome/account evidence. После неё final heroes сверяются с canonical players и receipt по native slots 0–4/128–132; порядок массива не задаёт сторону. Десять игроков/аккаунтов/героев уникальны. История следует за точной парой canonical player ID + проверенный numeric account при переходе между организациями; совпадения ника и неподтверждённые cross-account merges не используются.

Для каждой цели строго `prior.started_at < cutoff` **и** `prior.completed_at < cutoff`. Сама цель, равное время завершения, пересекающаяся и будущая карта не включаются. Окно 90 дней имеет включённую нижнюю границу и тот же строгий верхний cutoff. Списки prior/recent match IDs сохранены для каждого участника. Подтверждённые серии связываются между двумя существующими форматами ключа: JSON `[provider,id]` у датасета и `provider:id` у истории. Разный provider/id не допускается.

Исходы целей и рейтинги не читаются функцией подсчёта. Исторические outcomes используются прежней границей только для установления пригодности завершённой pro-карты. Target hero восстановлен по финальному receipt, его доступность до начала карты/драфта не доказана. Целые серии и исходные окна R2 не перераспределяются; никакого нового train/test split не создаётся.

## Патчи, роли и known_at

- У 2152 из 2180 hero-bound карт есть метка патча провайдера; у дополнительных 28 в используемых frozen inputs её нет. У всех 1657 пригодных целей метка есть. Диагностически посчитано совпадение provider label с целевой картой: в позднем блоке медиана 2 игры, 450 из 1860 участник×цель имеют ноль таких записей.
- Канонический patch ID в этом снимке отсутствует у всех 2180 карт; same-canonical-patch count остаётся null. Provider label не подставляется в canonical patch и не доказывает hero eligibility или переносимость между патчами. При неизвестной метке цели same-provider-patch тоже null, а не совпадение двух unknown.
- Роли и их подтверждение не включены в используемый capture; role-conditioned history — null. Это ограничение **снимка**, а не вывод об отсутствии ролей во всём сервисе. Роль нельзя восстановить из порядка слотов, команды или героя.
- Исторические `known_at` героя и его назначения игроку не установлены. В позднем блоке есть 29 повторных использований прошлых карт, чьи receipts были получены раньше целевого cutoff; это не 29 независимых карт и не доказательство полной доступности всех фактов. `knownAsOfHistory` остаётся null. Event time не подменяет known/fetched time.

Нет весов, decay, patch-transfer policy или эффективного N: это отдельные сырые количества наблюдений. Включение их в будущую модель потребует явного контракта, временной валидации и проверки переносимости. Отдельные pub/ranked данные в эти pro-denominators не добавлены.

## Существующая аналитика и следующий срез

`packages/analytics/src/player-hero.ts` считает описательные метрики, а `packages/db/src/player-hero-report.ts` явно помечает их `retrospective_descriptive` и `RETROSPECTIVE_NOT_HISTORICAL_FEATURES`. Готовый UI-отчёт нельзя просто положить в старый обучающий пример: его snapshot/reference pool и фильтры не являются as-of feature contract. Эти модули и их пользовательское поведение не изменялись.

Предлагаемый следующий срез — отдельный pure feature contract для **объёма pro-практики**, с raw count, числом проверенных наблюдений и флагами неполноты. До реализации зафиксировать окно/преобразование, способ агрегации по сторонам и политику неизвестных patch/role/as-of полей. Не добавлять всё сразу, не выбирать по R1/R2 log loss, не превращать ноль наблюдений в оценку мастерства. Контракт не означает разрешение обучить или опубликовать новую модель; старый период остаётся исследовательским, независимый тест ещё предстоит зарегистрировать.
