# Параллельная работа агентов

Правила действуют для нескольких сессий на одном ПК и для работы на двух ПК. Задачи выбираются по плану проекта и решениям владельца. У каждой активной задачи один ответственный агент. Один агент может вести интеграцию нескольких задач.

## Где что записываем

| Что нужно узнать | Где смотреть |
| --- | --- |
| Что занято, кто работает, что передать другой сессии | [Журнал параллельной работы](PARALLEL_WORK_LOG.md) в общей ветке `origin/coordination/active-work` |
| Изменения кода и способ их проверить | Ветка задачи, коммит или PR, указанные в журнале |
| Исследовательский отчёт, выгрузка, снимок исключений | Приватный реестр с именем, SHA-256 и ревизиями в журнале. Инструкции подключения ведутся в `docs/SHARED_RESEARCH_REGISTRY.md` в ветке разработки. |
| Какой результат вошёл в проект | [Состояние проекта](PROJECT_STATE.md), [хронология](PROGRESS.md) и [план](IMPLEMENTATION_PLAN.md) в ветке интеграции |

## Перед началом задачи

1. Обновить сведения об удалённых ветках. Прочитать свежий журнал, план и состояние проекта на согласованной базе. Посмотреть `git status --short`, текущую ветку и SHA базы. Рабочая копия другого ПК может отставать.
2. Указать в журнале задачу, свой идентификатор сессии, ветку, исходный SHA, файлы или модули и общие ресурсы. Указать ожидаемый результат, зависимости и критерий готовности. В процессе добавлять новые затронутые пути до начала правок в них.
3. Сверить области и ресурсы с активными строками. После успешной отправки записи в общую ветку можно приступать к правкам. Для чтения, ревью и локальных проверок достаточно согласованного поручения ответственного агента, если проверка обходится без общих записей, квот и правок.
4. Для записи использовать отдельную ветку задачи. Если агенты на одном ПК, каждый работает в отдельном worktree или клоне. На разных ПК достаточно отдельных рабочих копий. Локальные тестовые БД и временные каталоги указывать явно. Если на одном ПК одновременно запускаются сервисы, развести порты и рабочие очереди.

### Если области пересекаются

| Ситуация | Действие |
| --- | --- |
| Два агента хотят изменить одни файлы, контракт API или одну миграцию | Назначить одного автора общей части. Второй продолжает на согласованном контракте, в своей области или в роли проверяющего. |
| Две разные задачи добавляют миграции или меняют зависимости | Согласовать порядок миграций, а для `package.json` и `pnpm-lock.yaml` определить одного автора итогового изменения. Применённые миграции остаются неизменяемыми. |
| Несколько веток готовы править `PROGRESS.md`, `PROJECT_STATE.md` или общий план | Каждый оставляет результат в журнале. Интегратор вносит записи в общие документы при включении изменений и сохраняет уже записанные результаты. |
| Пересечение обнаружено после начала работы | Сохранить свои изменения в своей ветке, зафиксировать пересечение в журнале и согласовать, какая реализация войдёт первой. После её включения перенести оставшуюся часть и повторить проверки на объединённом коде. |
| Запись давно не обновлялась или ПК недоступен | Проверить журнал, ветку и последний коммит. Передачу фиксирует текущий ответственный или владелец. Пока статус не уточнён, можно продолжать независимую работу и проверки на чтение. |

Изменение чужих незавершённых правок требует согласованной передачи. Для интеграции берите конкретные коммиты или PR. При конфликте прочитайте обе стороны и проверьте итоговое поведение. Отправку в репозиторий и развёртывание выполняйте в пределах разрешения владельца.

## Исследования, базы и API

- В журнале указывайте общие ресурсы явно. Например, `provider:pandascore/schedule`, `registry:exposure`, `registration:S3-04/dl30`, `migration-numbering`. Для провайдера фиксируйте операцию, набор ID или окно и использованную квоту, когда она известна. Сначала ищите сохранённые ответы. Повторный сбор одного и того же набора координирует один агент. Локальные счётчики на разных ПК сами по себе не отражают суммарный расход общего токена.
- Локальные анализы и проверки выполняйте на своей БД или в отдельных тестовых базах. Для записи в рабочую БД, запуска общего задания, импорта, регистрации эксперимента или активации модели укажите в журнале цель и ответственного. Перед запуском перепроверьте целевую среду и отсутствие уже запущенной или завершённой операции.
- Разные отчёты можно публиковать параллельно в приватное хранилище. В передаче укажите уникальное имя с задачей и ревизией или датой, полный SHA-256, версию кода, родительские ревизии и наличие исходных файлов. Скачивание по имени служит для поиска, а повтор расчёта привязывается к конкретному SHA.
- Перед добавлением общего снимка исключений перечитайте текущие ревизии и проверьте источники и раздельные ID карты, серии OpenDota и встречи PandaScore. В журнале укажите исходный и итоговый набор ревизий. Регистрация, оценка и активация проходят существующие проверки проекта и отдельные решения владельца. Для подготовки независимого теста записывайте границы данных и известные пересечения по целым сериям. [Допуск моделей](MODEL_VALIDATION.md)
- В Git и журнале указывайте ссылки, SHA и обезличенные результаты проверок. Храните ключи, пароли, `.env`, сырые приватные ответы и дампы в предназначенных для них локальных или приватных хранилищах.

## Передача и интеграция

Обновляйте запись при блокировке, передаче, готовности к интеграции или смене области. На передаче достаточно последнего проверенного коммита, выполненных проверок, известных ограничений и одной конкретной следующей операции. Если работа ещё в локальных изменениях и у принимающей сессии к ним нет доступа, укажите это и согласуйте способ передачи.

Статусы журнала отражают состояние работы.

- **В работе** — ответственный приступил, области перечислены в журнале.
- **Заблокирована** — указан блокер и явно сказано, какие области остаются занятыми.
- **Готова к интеграции** — есть доступная ветка или артефакт, записаны проверки и ограничения.
- **Закрыта** — результат включён в целевую ветку либо принят как исследовательский результат. Есть ссылка на коммит, PR или проверенный артефакт. Занятые области освобождены.
- **Снята** — работа прекращена или замещена. Указаны причина и задача-преемник, если она есть.

Принимающий агент проверяет доступность ветки, SHA и исходников, затем фиксирует смену ответственного. Интегратор обновляет состояние проекта и прогоняет проверки, на которые влияет объединение. Пункт плана закрывается только по его критериям готовности.

## Синхронизация журнала в Git

При первом запуске согласуйте коммит, в котором уже есть эта инструкция и начальный журнал, и опубликуйте `coordination/active-work` от него. До появления общей ветки записи ведёт один назначенный агент. После запуска каждый использует отдельный worktree для журнала. Команды выполняются в корне проекта. Путь к worktree можно выбрать другой, если предлагаемый уже занят.

```powershell
# Первый запуск с разрешения владельца. Заменить BASE_SHA на согласованный SHA.
git worktree add -b coordination/active-work ../dotaanalitic-coordination BASE_SHA
git -C ../dotaanalitic-coordination push -u origin coordination/active-work

# Подключение второй рабочей копии, если ветка уже опубликована.
git fetch origin
git worktree add -b coordination/active-work ../dotaanalitic-coordination origin/coordination/active-work
```

Из worktree журнала перед записью выполните `git pull --ff-only origin coordination/active-work`. Правьте `docs/PARALLEL_WORK_LOG.md`, создайте коммит только с этим файлом и отправьте обычным `git push origin HEAD:coordination/active-work`. Рабочие ветки продукта синхронизируются своим порядком.

Если push отклонён из-за обновления общей ветки, выполните `git fetch origin` и прочитайте `git show origin/coordination/active-work:docs/PARALLEL_WORK_LOG.md`. Сопоставьте свою запись со свежими задачами. Если области свободны, перенесите свой неопубликованный коммит через `git rebase origin/coordination/active-work`, проверьте итог журнала и повторите обычный push. Если одинаковый ресурс уже заявлен, согласуйте разделение и исправьте запись. Принудительная отправка и удаление общей истории журнала запрещены.

Например, агент на первом ПК ведёт S3-04 и проверяет принадлежность карт к сериям для Draft Lab, а на втором ПК агент ведёт S3-09 и оценивает модель победителя всей встречи. Оба могут анализировать свои артефакты параллельно. Если обеим задачам требуется дополнить один общий снимок исключений, один агент вносит подтверждённое дополнение, второй использует опубликованный SHA после проверки.
