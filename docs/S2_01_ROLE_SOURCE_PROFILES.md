# S2-01 — проверка источников ролей, 5 ноября 2026

Завершён срез `role-owner-check/source-profiles`. Общая причина трёх ошибок STRATZ у GamerLegion — ответ `proSteamAccount.teamId: 0`. Прежняя схема требовала положительный ID и отклоняла весь профиль. Теперь числовой ноль нормализуется в `null`: имя, account ID и позиция сохраняются, принадлежность команде остаётся неизвестной. Отрицательные, дробные, строковые и небезопасные числовые IDs по-прежнему отклоняются; совпадение запрошенного account ID обязательно.

Изменён контракт `packages/contracts/src/role-profiles.ts`; добавлены регрессии клиента, resolver и API/PG. Персональных исключений, миграций, изменений identity evidence и правил выбора ролей нет. Профиль с неизвестной командой не становится допустимой автоматической подсказкой даже при сохранённом team binding.

## Реальная проверка

Проверены сохранённые role bindings Yellow Submarine (2705) и GamerLegion (2706). Использован существующий `RoleProfileService` с действующими DB leases, квотами, таймаутами и cooldown. Составы и сопоставления не редактировались.

- Первый проход: 10 одиночных STRATZ запросов и одна общая заявка PandaScore турнира 22236. Все HTTP 200; три STRATZ ответа отклонены старым валидатором именно из-за нуля в teamId.
- PandaScore: все 10 выбранных игроков получили допустимые роли, совпадающие с подсказками локальной pro-истории. Устаревание прежней заявки было штатным истечением часового TTL, а не ошибкой источника.
- После исправления и окончания штатного cooldown: повторены только три ошибочных STRATZ запроса. Все три сохранены успешно с `providerTeamId:null`; SHA ответов совпали с ранее отклонёнными. Остальные профили и общая заявка взяты из кэша.
- Два из десяти STRATZ ответов не содержали профессионального профиля; это допустимый пустой результат. Остальные сообщали нулевые либо разные team IDs. Отсутствующая привязка STRATZ в обеих командах остаётся отдельным основанием `TEAM_BINDING_MISSING`; автоматически назначать один team ID всей пятёрке нельзя.
- Всего 14 исходящих provider requests: STRATZ 13, PandaScore 1. Повторные cache-only чтения не делали HTTP. Времена получения реальные; `eventAt/knownAt=null`.

После паузы между проверками TTL уже истёк: smoke работающего API в 18:49 UTC вернул сохранённые профили со статусом `stale`, без `source_schema_invalid`. Это ожидаемо; для текущих ролей нажмите «Обновить профили API». Проверка не обновляла данные повторно ради зелёного статуса. Сохранённые ручные позиции от обновления не меняются.

## Проверки и ограничения

Frozen offline install, root typecheck/build и 833 unit/CLI теста прошли. Две новые регрессии сначала воспроизвели ошибку, затем все 13 целевых unit-тестов прошли. API/PostgreSQL: 7 тестов прошли; первоначальный новый кейс попал под cooldown от предшествующего synthetic 503, порядок тестов исправлен без ослабления production лимитов.

Сверка 75 рабочих таблиц: изменились только `role_profile_cache`, `role_profile_stratz_quota`, `pandascore_request_quota`. Остальные 72, включая составы, identities, 340 карт, модели и журнал прогнозов, сохранены; очередь неизменна. Локальный API перезапущен с исправлением; health и два authenticated cache-only отчёта вернули 200, новых входов не было. Непосредственно после smoke auth session timestamp мог обновиться штатным authenticate.

Полные Node/PG/Python/Docker/Linux suites не повторялись. Доказательства и итог браузерных проверок — в [evidence](evidence/s2-01-role-source-profiles.json).
