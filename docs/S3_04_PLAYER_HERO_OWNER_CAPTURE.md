# S3-04 — серверный снимок выбранного драфта

Реализация `player-hero-owner-capture`, 14 ноября 2026. Это сохранение входных данных, не прогноз и не регистрация независимой выборки. Ручной выбор десяти героев допустим. H1/H2 не активируются, работающая pre-match модель не заменяется.

## Путь данных

`POST /api/v1/scenarios/:id/draft-captures` принимает `{ "expectedRevision": 1, "scheduleTargetRequestId": "UUID существующего назначения" }`; ссылка необязательна, если есть canonical series в сценарии или читается уже сохранённый снимок. Нужны сессия владельца, origin и CSRF. Сервер читает сохранённую ревизию, а не присланные клиентом аккаунты, часы, историю или вероятности.

В одной repeatable-read транзакции:

1. Блокируется сценарий и проверяются владелец/ревизия. Повтор возвращает тот же снимок, включая старый отказ. Два конкурентных запроса не создают две записи; serialization failure повторяется ограниченно.
2. Сервер получает `decisionCutoffAt` с шестью знаками долей секунды. Пользовательский `scenario.cutoffAt` сохраняется отдельно и не становится временем решения.
3. Роль внутри A/B связывает canonical player с выбранным героем. Текущие подтверждения Steam32 копируются вместе с observation IDs и исходными clocks. Несколько аккаунтов одной персоны, конфликт людей или явный rejection не разрешаются по нику. A/B не объявляются Radiant/Dire.
4. Копируется доступная локальная pro-история: строки карт/участников, receipts с исходной сохранённой проекцией, наблюдения фактов, идентичности, ссылки серий. Все bigint IDs в проекциях — строки. Срез выполняется строго до серверного cutoff, а не до будущего расписания.
5. Сохраняются неизменяемые JSON bytes/SHA и причины неполноты. PostgreSQL самостоятельно выставляет точный `recorded_at`; триггер запрещает UPDATE/DELETE, подмену ревизии, SHA и promotion в прогноз.

Чтение: `GET /api/v1/scenarios/:id/draft-captures/:revision`, только владелец. Повторное сохранение отредактированного сценария создаёт новую ревизию, для которой возможен новый снимок. Поздняя догрузка не исправляет старую запись.

## Ссылка на карту

Исходный `ScenarioInput` и его репозиторий сохранены без изменений: они входят в точный runtime manifest действующей V1. Новый capture изолирован в модуле API. Готовый `scheduleTargetRequestId` передаётся из существующего контекста встречи и сохраняется внутри самого неизменяемого снимка; нового ручного поля не требуется. После capture повтор без query-ссылки возвращает ту же запись. Попытка переназначить уже сохранённую ревизию другой встрече даёт409. До первого capture одна ссылка браузера не считается сохранённой привязкой.

При capture сервер читает принадлежащее владельцу immutable назначение PandaScore, проверяет направление команд, доступность observation по времени и допустимый ordinal при известном best-of. Ссылка имеет вид `pending / provider / providerSeriesId / mapNumber / actualMatchId:null`, с копией source evidence. Canonical series из контекста также может дать pending ссылку при известных provider IDs и тех же командах. Противоречивая или чужая ссылка не становится рабочей автоматически.

ID серии или PandaScore встречи **не используется** как Dota map ID. Финальная карта, фактическое начало и совпадение сыгравших аккаунтов/героев ещё не проверены. Позднее связывание потребует отдельной append-only записи; менять capture нельзя. Старый offline-контракт с обязательным `targetMatchId` не считается выполненным pending-снимком.

## Границы статуса

`status: captured` означает сохранение достаточно полного локального входа. Это не качество модели и не право публикации. Всегда `primaryEligible:false`, `scoringPerformed:false`, `deployable:false`.

`unavailable` сохраняет причины: неполные герои, неподтверждённые/неоднозначные аккаунты, отсутствие ссылки или истории, превышение бюджета. Отсутствие выбранного аккаунта в локальных pro-участниках — отдельная причина. Нулевой опыт на конкретном герое сам по себе не блокируется; порог Elo и вычисление признаков остаются в отдельном адаптере.

История — доказательный материал, а не готовая training-выборка. Receipts разных статусов и исходные известные/неизвестные clocks сохраняются; следующая проверка должна установить соответствие канонических строк receipts, допустимость каждого факта/исхода/identity и исключить целевую карту/серию. Значение `known_at:null` не заменяется временем начала старой карты. Identity, впервые увиденная сейчас, не становится исторической known-as-of.

Ограничения: до 5000 карт, 50000 участников, 10000 receipts, 200000 фактов, 50000 identity observations; история до 30 MiB, итоговая запись до 32 MiB. Превышение не превращается в усечённую успешную историю. SQL statement timeout 30 секунд, lock timeout 10 секунд. HTTP-провайдеры не вызываются. Полнота удалённой истории неизвестна.
