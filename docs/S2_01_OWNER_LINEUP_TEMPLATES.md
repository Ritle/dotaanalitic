# Шаблоны ожидаемых пятёрок и ролей под управлением владельца

Задача: `S2-01/owner-lineup-templates`, прямой выбор владельца 11 ноября 2026 года.

## Пользовательский порядок

1. Выберите будущую встречу, подготовьте пять игроков каждой стороны и проверьте роли под именами.
2. Нажмите **«Подтвердить пятёрки и роли»**. Владелец сохраняет новые числовые связи и ожидаемые назначения для повторного использования. Отдельное сохранение сценария для этого больше не требуется.
3. В карточках показаны автор, время подтверждения и редакция шаблона.
4. При следующем открытии той же команды и тех же пяти canonical player IDs роли подставляются из шаблона владельца. Порядок ответа источника не определяет назначения.
5. Измените роль и подтвердите выбор снова, чтобы сохранить новую редакцию. Повтор без изменения назначений не создаёт лишнюю запись.

Ручные правки приоритетнее позднего ответа сервера или подсказки источника.
Ожидаемые роли не гарантируют фактическое участие игроков в будущей встрече.
Подтверждение текущей страницы по-прежнему сбрасывается при переходе к другой
встрече; сохранённые назначения остаются и не требуют повторного ввода.

## Когда состав изменился

Шаблон применяется только к той же организации и точной пятёрке числовых
canonical IDs. Если отличается хотя бы один игрок, показано предупреждение;
старые роли не распределяются между новыми игроками. Владелец проверяет новый
состав и подтверждает новую редакцию. Последняя редакция представляет текущий
ожидаемый выбор; более старый вариант остаётся в аудите, но автоматически
не становится предпочтительным при возвращении прежней пятёрки.

Сохраняются player ID и rolePos. Отметка stand-in относится к конкретному матчу
и не переносится шаблоном: текущие карточки и их отметки при применении ролей
сохраняются. Шаблон не подтверждает историческую роль, членство в организации,
личность по нику или доступность состава до старта прошлой карты.

## Роль владельца

Только **owner** создаёт и изменяет общие шаблоны. Автор и время берутся на
сервере; переданный `confirmedByOwner:true` сам по себе не даёт полномочий.
Каждая запись проверяет активный account_role в БД, в том числе внутри транзакции.
Флаг роли из тела/URL/заголовка клиента не используется для авторизации.

`GET /api/v1/auth/access` сообщает доверенную роль сессии и возможность
редактировать составы. В интерфейсе владелец обозначен явно; в режиме
зарезервированного **user** назначения доступны для чтения, кнопки изменения
и подтверждения отсутствуют, выбор ролей заблокирован. Сервер по умолчанию
запрещает такому аккаунту non-GET операции, кроме выхода из сессии. Разрешения
для будущих POST-аналитик, расчётов, импорта и личных сценариев ещё не определены.

**Это основа разграничения, а не выпуск нескольких аккаунтов.** Сохранён прежний
уникальный single-account constraint и создание владельца только через CLI.
Создание user-аккаунтов, публичная регистрация, экран управления пользователями
и коммерческий SaaS не добавлены. Идея [BUG_REPORT №13](BUG_REPORT.md#13--типы-аккаунтов-владелец-и-пользователь)
в полном объёме остаётся будущей задачей.

## Конфликты и сбои

Записи append-only: старую редакцию нельзя обновить или удалить. `expectedRevision`
защищает от перезаписи из другой вкладки, requestId обеспечивает идемпотентный
повтор. При409 роли остаются в форме: «Перечитать шаблон A/B» → проверить →
«Подтвердить пятёрки и роли». Чтение само не подтверждает ручные назначения.

Сохранения разных сторон и числовых связей не являются одной общей транзакцией.
При частичной ошибке нет общего подтверждения, успешно сохранённые данные
остаются. Уход со страницы во время чтения не запускает позднюю запись шаблона.
Неоднозначный сетевой результат можно безопасно повторить с прежним requestId.

## Обновление существующей установки

Примените миграции `pnpm db:migrate`, затем `pnpm build` и перезапустите API.
Повторное применение миграций безопасно. Владелец сохраняет прежний аккаунт и
пароль; сброс или повторное создание аккаунта не нужны. После обновления API
обновите страницу браузера, чтобы загрузить права сессии.

## Техническая граница

SQL053 добавляет account_role с owner по умолчанию и отдельную таблицу
owner_lineup_templates. Исторические SQL001–052 не меняются. Шаблоны общие,
чтение не фильтруется по читателю; автор записи хранится отдельно. Контракты
этого addon находятся в feature-модуле API, чтобы не менять pinned shared barrel
действующего V1. V1 Elo и frozen prediction snapshots от шаблонов не меняются.

Интерфейс сохраняет роли в существующем scenario snapshot при создании сценария;
обновление шаблона не меняет уже созданные сценарии, отчёты или прогнозы.
Импорт профессиональной истории и provider HTTP этим действием не запускаются.

Проверки и ограничения записываются в [evidence](evidence/s2-01-owner-lineup-templates.json).
