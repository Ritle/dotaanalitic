# S3-04 — единый вход условной оценки H0/H1/H2

Реализован `conditional-future-evaluation-bundle`: локальная сборка проверенного перечня карт, признаков и отдельных исходов. Это подготовка входа для выбранной владельцем проверки B; численная оценка и регистрация окна этим срезом не выполняются.

## Что соединено

`tools/research/conditional-evaluation.mjs` повторно вызывает существующие source binder и enrollment verifier. Он не принимает готовые флаги пригодности от вызывающего кода. Проверяются совпадения окна, native event/map/series ID, состава серии, времени её завершения, перечня подготовленных карт и исключений. Связь исхода с картой проверяется по ID, cutoff, SHA receipt и ориентации Team A относительно Radiant/Dire.

Одна карта представлена один раз. H0, H1 raw/cal и H2 raw/cal используют общий `pairedMapIds`. Отсутствие входа или подтверждённого исхода исключает целую серию из сравнения; карта остаётся в журнале и знаменателе. Неполный перечень даёт `insufficient` и `pairedCoverage:null`. Превышение лимита 300 возможных целевых карт блокирует подготовку общей выборки.

Сохранённые выходы:

- `cohort.json` — окно/область, полный известный перечень, знаменатель, единое подмножество и причины исключения;
- `features.json` — только пригодные входы Elo/hero и фиксированный порядок H0/H1/H2, без целевых исходов и длительности карты;
- `labels.json` — отдельные подтверждённые исходы для того же подмножества, ориентация и source/time evidence;
- `audit.json` — fingerprints входов, повторных проверок и полного ранее подтверждённого списка исходов; source errors сохраняются;
- `manifest.json` — внешние SHA обоих родительских манифестов, политики, кандидата, списка исключений, кода и выходных файлов.

Исходные parent labels/features не переписываются. Если карта исключена, её исход остаётся в прежнем проверенном файле; отсутствие в новом парном файле не удаляет её из знаменателя. Реальные байты источника и весь исходный ledger доступны через цепочку манифестов.

## Воспроизводимость и границы доверия

`tools/research/conditional-evaluation-files.mjs` читает небольшой descriptor с двумя ссылками `{directory, manifestSha256}`: `source` и `enrollment`. До объединения выполняет оба прежних `verify`, сверяет общий SHA архива и заново вычисляет результат. Все входы/выходы находятся внутри `.tools`; проверяются размер и реальные пути. Создание исключительно в новом каталоге; повторная проверка требует внешний SHA манифеста.

```text
node tools/research/conditional-evaluation-files.mjs build SPEC SPEC_SHA OUTPUT_DIRECTORY
node tools/research/conditional-evaluation-files.mjs verify OUTPUT_DIRECTORY MANIFEST_SHA
```

Для реального архива CLI требует полный закреплённый exposure ledger: 5674 карты / 1768 серий. Удалять прежние исключения нельзя; дополнительные исключения допустимы только согласованно в обоих родительских входах. Источник ledger и его SHA берутся из неизменённой политики. Для явно синтетического архива используется его тестовый список, и результат остаётся synthetic.

Полнота перечня по-прежнему условна относительно проверенного **локального** реестра турнира. Манифест не превращает его в подпись провайдера или доказательство полноты API. Настоящие native IDs будущих основных выпусков и независимая область ещё не зарегистрированы.

Сохранены признаки неполноты hero history, нулевых наблюдаемых counts, месяц UTC, league и provider patch, если он присутствует в валидированном receipt. Provider patch не превращается в canonical patch. Эти поля описательные; они не меняют два численных признака. Смена целевого исхода проверена отдельным тестом: численные входы и членство выборки не меняются.

## Совместимость с оценкой

Старый `post_draft_independent_evaluate.py` требует prospective pre-start persistence и принимает только синтетический harness. Условный набор B **не подаётся в него под видом прогноза до старта**. Новый вход сохраняет `evaluationBasis: conditional_reconstructed`; отдельный conditional consumer — следующая задача. Прежние формулы, коэффициенты, температуры, пороги и отрицательный development result не изменены.

`prepared_local_inputs` означает готовность локальных данных к дальнейшей интеграции, не пройденный quality gate. В этом срезе `evaluationAllowed`, `registrationAllowed`, `collectionAllowed`, `scoringPerformed`, `independentTestCompleted`, `deployable` всегда false. Действующая V1 не менялась.

## Диагностика

Положительный пример построен только на синтетике. Реальный пример использует прежние две раскрытые карты: без страниц и итогового реестра он остаётся `insufficient`, знаменатель 2, пригодных 0, покрытие null. Никакие реальные вероятности или метрики не вычислялись.

У старых диагностических файлов были разные границы окна: микросекундный feature input и миллисекундный enrollment. Новая сборка отвергает такое несовпадение. Для сквозной проверки создана **новая явная ревизия** локальных входов с одинаковым окном и полным frozen exposure; прежние файлы сохранены. Это выравнивание технической диагностики, не изменение зарегистрированного окна — регистрации ещё нет.
