# S1-16 — имена в прогнозах и журнале

Задача №7: `S1-16/BUG_REPORT/readable-labels/prediction-flow`.

## Как пользоваться

В расчёте одной карты и форме сохранённой встречи выбранные команды и
пятёрки показаны с названиями и никами. Сохранённый результат показывает
имена для своего исходного состава, а не для поздней редакции сценария.
Стороны A/B и порядок игроков сохраняются. N личной истории по-прежнему
читается из результата; подпись не добавляет игр или ролей.

В журнале раскройте «Команды и ожидаемые составы A/B» в нужной строке.
Подписи и пятёрки появляются только для раскрытой попытки. На следующей
странице строки снова закрыты; раскрытие доступно клавишей Enter.
Идентификаторы команды/игрока и точная карточка доступны в «Данных записи».
Model UUID, ID карты/серии, receipt и SHA остаются в прежних сведениях.

Имена взяты из текущего локального каталога. Они не утверждают, что такой
ник или название были известны на дату прогноза. Время чтения metadata
показано отдельно. «Обновить подписи каталога» не пересчитывает прогноз,
не переписывает input, SHA, состав, исход, N или статистику журнала.
Если имя пустое, показано «Игрок без ника» / «Команда без названия»;
при отсутствующей записи — «Имя недоступно». Разные ID с одинаковым ником
не объединяются. Подписи не подтверждают личность или участие в игре.

## Загрузка и границы

Общий ForecastLineups использует существующие CatalogDisplayLabels и
ReportEntityLabel. Только прежний private local-only GET `/api/v1/catalog-labels`:
до2 команд и10 выбранных игроков одним запросом; null исключается,
повторяющиеся ключи удаляются. Базовые/ожидаемые составы сценария, герои
и неотображаемые сущности не запрашиваются. Роли в journal row не выдумываются:
там доступны только числовые личности ожидаемой пятёрки.

Существующий общий кэш5min обслуживает одинаковые наборы ID, включая
preview/результат и разные строки/страницы журнала. Закрытая страница50
попыток не делает50 запросов имён. Закрытие/повторное раскрытие не обновляет
свежий кэш; новая комбинация ключей требует своего ограниченного batch.
Нет запросов на каждого игрока, вызовов внешних провайдеров или увеличения
лимитов API. Нового endpoint, схемы, зависимости или shared export нет.

Ошибка metadata показана отдельно от результата; прежние подписи кэша
сохраняются. При холодном кэше остаются честные fallback и точные ID.
Ошибка чтения имён не блокирует сохранение расчёта. Кнопка обновления позволяет явно повторить чтение; автоматический retry
самого запроса выключен. Новый mount при отсутствующем/устаревшем кэше
может снова прочитать metadata.

Изменены четыре потребителя: ScenarioPredictionView, ScheduledForecastPanel,
PredictionResult и ForecastJournalView; добавлен один общий frontend-компонент.
Prediction input/requests, runtime inference, model registry, журнал исходов,
immutable snapshots, backend/SQL и зависимости не изменены.

## Проверки

[Результаты и сохранность](evidence/bug-report-prediction-labels.json).
Новые browser/PG проверки используют синтетический каталог и явно
синтетический положительный fixture журнала, не настоящие прогнозы.
Проверяются batch/cache/lazy50+1 pagination, дубли ников, blank/missing
имена, rename/503/retry, полный API-результат и текст сохранённого runtime
снимка, независимое сохранение при ошибке metadata, N/вероятность/статус.
Совместимость условных и назначенных расчётов, результатов и lifecycle
проверяется существующими наборами. Это изменение отображения, не новая
валидация точности модели или фактического участия игроков.
