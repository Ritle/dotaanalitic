# S3-07/V1 — отмена назначения карты и повторное открытие

Ручная отметка владельца относится к одному immutable назначению `opendota/providerSeriesId/map1`, а не к победителю серии. Все пересчёты этого назначения используют одну историю отмен. Исходные прогнозы, ожидаемые составы, результаты и старые отчёты не меняются.

## Правило учёта

- `cancelled` означает **отмену по сообщению владельца**, с обязательной ссылкой и причиной. Это не верифицированный факт провайдера и не training label.
- Первое событие — отмена; далее разрешено чередование `reopened` / `cancelled`. Повтор запроса с тем же UUID и содержимым возвращает прежнее событие. Новый запрос требует текущую `expectedRevision`; одновременные изменения не перезаписывают друг друга.
- `eventAt` — заявленное время события или null; `recordedAt` — фактическое серверное время записи/доступности отметки. Заднее число в `eventAt` не меняет прошлые отчёты. Будущая дата события отвергается. Сервис не загружает ссылку, поэтому отдельное время получения внешнего документа не выдумывается.
- Если у назначения когда-либо была подтверждённая связь с сыгранной картой, отметка отмены остаётся в аудите, но **не исключает карту из метрик**. Это действует и при последующем неподтверждённом исправлении источника: статус становится `unlinked`, а не отменённым.
- Пока связи нет, отменённые назначения остаются в таблице со статусом `cancelled`, без оценки правильности. Счётчик `cancelled` считает уникальные назначения среди строк после фильтров, а не пересчёты. Исходная недоступность расчёта и её причины сохраняются; `unavailable` — отдельный счётчик попыток и может пересекаться с отменами.
- Повторное открытие восстанавливает обычную классификацию: ожидание проверки, недоступность либо подтверждённый исход. Само по себе оно не создаёт результата.

## Хранение и совместимость

Forward-only SQL029 добавляет `v1_target_lifecycle`: owner/target/revision, request UUID/hash, exact event text/SHA и цепочку предыдущего SHA. SQL проверяет владельца, неизменное real-map назначение, переходы, время и цепочку; UPDATE/DELETE/TRUNCATE запрещены. SQL001–028 не изменены.

Новые отчёты используют `v1-journal-input-v2` / `v1-journal-report-v2` и policy `owner_reported_verified_binding_precedence_v1`. Полный снимок последних событий отмен фиксируется вместе с исходными наблюдениями. SQL требует точный текущий inventory, включая события повторного открытия. Создание отчёта и запись отмены сериализуются одним owner lock; результаты сохраняются в отдельном журнале.

Старые v1 input/report остаются читаемыми и воспроизводятся прежним pure builder. Их `cancelled:null` означает отсутствие учёта на момент создания. V2 вызывает прежний глобальный выбор primary до фильтрации, затем добавляет lifecycle-классификацию и считает метрики по отфильтрованным primary. Elo, feature builder и формулы метрик не менялись. Код замороженного release evaluator не пересобирается.

## Локальная команда владельца

После `pnpm db:migrate` и сборки:

```text
pnpm target:lifecycle history PREDICTION_REQUEST_ID
pnpm target:lifecycle append request.json SHA256
pnpm target:lifecycle history PREDICTION_REQUEST_ID BEFORE_REVISION
```

Пример **структуры** запроса; UUID нужно заменить существующим real-map request и новым UUID операции:

```json
{
  "requestId": "00000000-0000-4000-8000-000000000001",
  "predictionRequestId": "00000000-0000-4000-8000-000000000002",
  "expectedRevision": 0,
  "action": "cancelled",
  "eventAt": null,
  "sourceUrl": "https://example.test/cancellation-evidence",
  "reason": "Причина отмены и описание проверенного владельцем источника"
}
```

SHA256 относится к точным bytes request.json. Для повторного открытия: новый `requestId`, `action:"reopened"`, актуальная `expectedRevision`, ссылка и причина. При потерянном ответе повторить **тот же** файл/SHA. История возвращает до100 событий от новых к старым и exclusive `nextBeforeRevision`.

## Интерфейс и границы

Защищённые journal API принимают фильтр `status:"cancelled"`. Экран `/forecast-journal` показывает число отмен, тип отметки, причину, источник, время, revision/SHA и факт игнорирования отмены при наличии verified binding. Owner UUID не попадает в HTTP projection. Старый отчёт показывает неизвестное число отмен, новый — количество зарегистрированных отметок.

Запись отмены и повторное открытие пока доступны через owner CLI; новых HTTP mutation routes нет. Автоматическое подтверждение отмен, связывание расписания PandaScore с OpenDota series/map и удобный ввод real-map назначения в интерфейсе ещё не реализованы. Истёкшее расписание, отсутствие результата или отсутствие карты в API **не считаются отменой автоматически**.

Следующий точный срез: **S3-07/V1-schedule-target-adapter** — явная проверяемая связь выбранной встречи расписания с real-map назначением, сохранение source IDs и ручного разрешения неоднозначности; без вывода map1 из порядка найденных карт. UI действий владельца развивается в этом потоке. S3-07 и весь V1 release остаются открыты до оставшихся требований и независимой оценки модели.
