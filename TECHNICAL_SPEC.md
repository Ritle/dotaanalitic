# Dota 2 Pro Analytics — техническое задание Personal MVP 2.0

**Версия:** 2.0 (персональный MVP с прогнозированием)  
**Дата:** 27.10.2026  
**Статус:** согласованная новая граница MVP; прогнозные модели требуют исторической проверки  
**Язык продукта:** русский; архитектура допускает i18n

## 0. Первая прогнозная версия V1 — решение владельца от 02.11.2026

**Утверждено для реализации.** Эта редакция вместе с AGENTS v10 заменяет противоречащие требования полного MVP **только для первого прогнозного выпуска**. Остальной текст сохраняет целевую архитектуру и будущие возможности. Принятие требований не означает, что модель уже реализована или прошла проверку.

### 0.1. Пользовательский результат

Владелец выбирает будущую встречу или ручной сценарий, задаёт две пятёрки и получает после допуска модели оценку победы **на одной карте при этих составах, до драфта**. Состав можно взять с актуальной страницы команды/из API и исправить вручную. Пять отображённых игроков — достаточная основа ожидаемого состава; официальный анонс участия не обязателен. Если источник содержит больше пяти игроков или спорные ID, нужно выбрать пятёрку и разрешить идентификаторы, а не брать первые пять строк.

Источник состава, время получения, время выбора владельцем, статус «ожидаемый» и revision сохраняются. Редактирование создаёт новую ревизию; старый прогноз неизменяем. `scenario_lineup` — выбранные участники; существующий `scenario_expected_lineup` остаётся необязательной базой для сравнения замен, а не вторым обязательным составом. Автозаполнение — улучшение, ручной ввод уже допустим.

### 0.2. Минимальная модель и необходимые данные

| Область | Обязательно для V1 | Отложено, с сохранением возможности добавить |
|---|---|---|
| Цель | Победа Team A на одной pro-карте, условно на выбранные 5+5 | BO3/BO5 и between-map прогнозы вне V1 |
| Состав | 10 разных canonical игроков с проверенными numeric account IDs | Автоподбор состава, оценка вероятности участия |
| Сила | Хронологический Elo игроков; сравнение средних рейтингов двух пятёрок | Logistic regression, recent-form, cohesion, exact-five, churn |
| Организация | Название/ID для контекста; исторические ID для проверки исхода, где требует verifier | Organization rating как самостоятельный признак |
| Роли | Не входят в вектор и не блокируют V1 | Ручные роли и оценки STRATZ с отдельным provenance; role-aware модель |
| Патч | Не входит в вектор; отсутствие patch metadata не блокирует V1 | Patch weights, cold-start features, hero-impact registry |
| Сторона | Team A/B в сценарии; V1 не использует преимущество Radiant | Side-aware версия после отдельной проверки |
| Герои | Не требуются до драфта | Отдельная post-draft модель с 10 различными героями; bans/order/first-pick позже |
| Веса | Один заранее зафиксированный Elo update policy, без ручной смеси «силы» | Раздельные feature-specific decay policies после сравнения |

Начальный исследовательский кандидат использует уже записанные 1500/K32/scale400; это проверяемая гипотеза, не доказанные оптимальные параметры. Отдельные form/prior/штрафы за замену не добавлять без эксперимента. Неизвестная личность, конфликт аккаунтов и недостаточная история обрабатываются coverage-policy модели; фиксированный prior не выдаётся как запасной пользовательский прогноз.

История следует за тем же проверенным Steam account ID при смене организации или ника. Архивное подтверждение старого ника не требуется. Текущая numeric привязка может использоваться для ретроспективного связывания этого аккаунта, сохраняя настоящий `known_at`; объединение разных аккаунтов/спорных владельцев требует отдельного evidence. Будущие карты не входят в прошлые рейтинги.

### 0.3. Историческая проверка и живое использование

Три режима хранятся раздельно:

1. **Conditional retrospective:** фактические участники восстановлены из завершённой карты; оценивается модель «если эти десять игроков играют». Старые составы не объявляются известными до старта. Для раннего рейтинга доступны только карты, завершённые до cutoff; предположение event-time availability отмечается отдельно от действительно наблюдавшегося времени получения исхода.
2. **Verified as-of:** факты имеют доказанную доступность на исторический cutoff. Существующий строгий pipeline сохраняется как самостоятельный режим.
3. **Prospective expected lineup:** выбранный состав и прогноз действительно сохранены до старта будущей карты. При замене участника создаётся новый прогноз. Старый остаётся в журнале с отметкой несоответствия состава; его нельзя молча удалить из оценки рабочего процесса. Качество при совпавшем составе и качество всех предматчевых прогнозов показываются отдельно.

Conditional backtest может поддерживать **отдельный V1 conditional candidate**, прошедший зарегистрированный gate. Интерфейс должен сообщать: «Оценка при выбранных составах. Проверка модели выполнена на восстановленных составах; качество реальных предматчевых прогнозов ещё не установлено», пока prospective evidence отсутствует. Это не вероятность того, что состав действительно выйдет на карту. E0/E1 не становятся таким кандидатом автоматически.

Пятёрка целевой карты — единственное разрешённое здесь явно восстановленное условие. Нельзя добавлять её исход, duration, GPM, kills, будущие карты или поздно вычисленный глобальный рейтинг в признаки. Исторические native sides нужны для формирования пятёрок и меток; фактическая Radiant/Dire сторона будущей карты не нужна side-blind модели.

### 0.4. Допуск модели

- Pro-only verified outcomes; одна карта — один пример на dataset/stage; целые известные серии не пересекают временные folds; неизвестные серии обрабатываются явной консервативной policy.
- Для фиксированного Elo достаточно chronological warmup + untouched test. Подбор K/decay/feature set требует отдельной более ранней validation; обучаемый calibrator — отдельной calibration. Четыре непустых окна не обязательны для модели без таких операций.
- Brier, log loss, calibration/reliability, coverage, число карт **и серий**, диапазон дат и сравнение с заранее выбранным baseline обязательны. Для неопределённости учитывать зависимость карт внутри серии. Sample/coverage/metric thresholds и действия при нехватке N фиксируются до release test. Ориентир N=300 не универсальный gate и не разрешение на меньшую выборку без обоснования.
- Calibration assessment обязательна; `calibration.kind=none` допустим после проверки. Выбор или fitting коррекции не делается на финальном test. Уже просмотренные E0 результаты и данные не считаются новым нетронутым test.
- Проверять временную устойчивость/переносимость на свежие данные. Недоступный patch label — предупреждение и отдельный coverage bucket, не автоматический отказ patch-free Elo. Наличие labels позволяет дополнительные срезы; переносимость на любую будущую мету не заявляется.
- До прошедшего gate, registry activation и frozen snapshots ответ остаётся `unavailable`/вероятность `null`. Отсутствие необязательного признака не мешает V1, но отсутствие обязательного не запускает невалидированный fallback.
- Frozen E1 план/окно/параметры сохраняются. Для release candidate нужен собственный зарегистрированный gate и dataset/config/code/SHA; не переписывать ранее зафиксированный протокол ради успешного результата.

### 0.5. Как сохраняем будущие усиления

Не удалять nullable поля, provenance, patch/role/hero tables, существующие аналитические страницы или strict cohort. Новый набор признаков получает новый `feature_schema_version`, список зависимостей/правил пропусков, отдельные data/model gates и artifact version. Старый snapshot остаётся воспроизводимым по своей версии.

Порядок улучшений: (1) достаточный корпус и рабочий V1 Elo; (2) logistic/recent-form; (3) cohesion/roles/patch с абляциями; (4) отдельная post-draft модель; (5) draft order/first-pick и автоматизация. Порядок улучшений можно менять по результатам независимых экспериментов. Добавление признака требует доказанного улучшения или заранее заявленной цели без недопустимой деградации; нельзя переключать модель по случайному наличию поля в HTTP-запросе.

Provider patch label можно показывать как «патч по данным STRATZ/OpenDota» с источником и временем, отдельно от canonical release registry. Он не доказывает точное время развёртывания, историческую доступность героев или pre-known patch. Для такой разметки не требуется находить client-build mapping; для release-based правил прежняя строгость сохраняется.

### 0.6. Граница реализации на момент решения

Уже существуют ручные сценарии, описательная аналитика, отдельный offline research Elo и с2026-11-02 [отдельная подготовка V1 dataset](docs/S3_00_DATASET_BUILDER.md):232 real maps пригодны по data profile, без обязательных patch/roles/draft. **Не реализованы** production V1 feature builder/inference/activation и release evaluation gate. `dataset-builder.ts` продолжает требовать patch для strict профиля; `readiness.ts` сохраняет строгую проверку ролей, если они запрошены. Новый V1 профиль не меняет legacy strict semantics. Нет автоматического STRATZ/Dota2ProTracker roster importer.

Следующие срезы и приёмка записаны в [плане](docs/IMPLEMENTATION_PLAN.md). Выпуск V1 не означает готовность всего двухмодельного MVP.

Checkpoint2026-11-02: [V1 release policy зарегистрирована](docs/MODEL_VALIDATION.md) до независимого future test: explicit Tier 1 event scope, sample/coverage/Brier/log loss/calibration/uncertainty thresholds и неизменный порядок проверки. `release:plan` создаёт и воспроизводит этот контракт; это не реализация quality evaluator, успешная проверка или активация модели. S3-01/V1-evaluation остаётся открытым для collector/ledger; разработка feature builder/candidate не требует ждать окончания test window.

### 0.7. Уточнение владельца: Tier 1 в MVP, Tier 2 после MVP

Первые прогнозы и приёмка качества ориентированы на **будущие карты турниров Tier 1**. Поддержка прогнозов Tier 2 — дальнейшее развитие после MVP. Это область применения первой модели; tournament tier не добавляется в Elo как коэффициент, признак или произвольное усиление «важного турнира».

Для MVP достаточно небольшого управляемого списка конкретных турниров/сезонов/стадий: provider и numeric event IDs, отображаемое название, решение о включении, источник или отметка выбора владельцем, дата и revision. Такой список — рабочая область приложения, не заявление о единой официальной мировой классификации. Допускается ручной выбор владельцем без поиска архивных доказательств. Не переносить классификацию бренда автоматически на все годы, квалификации и соседние события. Не связывать разные provider IDs лишь по совпадению названия.

Сейчас OpenDota `professional`/`premium` используются только для is_pro; соответствие Tier 1/Tier 2 не реализовано. Upcoming API хранит ID/названия турниров, но не нормализованный tier. Неизвестный уровень нельзя автоматически называть Tier 1; событие сначала явно включается в список владельцем/по рассмотренному источнику. При реализации prediction endpoint проверять область применения активной версии; вне области — объяснимый unavailable, описательная аналитика остаётся доступной.

**Предыдущую профессиональную историю игроков сохраняем**, включая карты других уровней: смена уровня турнира не обнуляет карьеру и рейтинг. Отбор или веса истории — отдельная policy модели, проверяемая экспериментом; Tier 1-only training не является автоматическим требованием. В Elo сила соперника участвует в обновлении рейтинга, но это не моделирование турнирного давления, LAN или важности события.

Release evaluation должна отдельно подтвердить качество на выбранном Tier 1 domain. Список событий/правило отбора фиксируются до просмотра новых test outcomes; общие pro-метрики не выдаются за Tier 1-метрики. Текущий development corpus232 карт ещё не размечен таким списком и не объявляется Tier 1 benchmark. Frozen E0/E1/V1-data не переписывать; при необходимости сформировать новую версию selection/evaluation manifest.

Будущее расширение Tier 2 использует тот же механизм scope list и версионирование. Перед расширением применения проверить покрытие, calibration и качество на соответствующих турнирах. Добавление tier/stage/LAN как модельных признаков остаётся отдельным S5-02 улучшением с проверкой добавочной ценности.

**Статус на06.11.2026:** продуктовый scope согласован; отдельный reviewed release-event manifest, runtime targetScope check, [общий список событий владельца](docs/S3_07_TIER1_SCOPE_WORKFLOW.md) для повторного выбора и фильтр выбранной страницы расписания реализованы. Нормализованная автоматическая классификация всех турниров и универсальная Tier1-точность не заявляются; независимая release-оценка остаётся открытой. Назначение первой карты и расчёт через отдельный page-aware адаптер поддерживают дополнительные страницы; условия модели сохраняются. [Контракт](docs/S3_07_SCHEDULE_PAGE_TARGETS.md). [Текущая сверка требований](docs/V1_REQUIREMENTS_REVIEW_2026_11_06.md).

### 0.8. Практика игрока на героях в рейтинговых играх

Реализация дополнения2026-11-06: [STRATZ context](docs/S2_07_STRATZ_ENRICHMENT.md) по уже известным OpenDota ranked map IDs, до20 карт по ручному действию. Отдельная provenance/cache, exact identity/core-field agreement, estimated position/provider version и явное покрытие; без изменения cohort/N/WR, canonical patch mapping или V1 features. Самостоятельный STRATZ player-history cohort не считается проверенным этим путём.

Уточнение владельца2026-11-02: разрешить ranked-public историю проверенных игроков как **отдельный источник анализа практики героя**. Высокий WR на достаточной свежей выборке — кандидат на дополнительный сигнал, переносимость в pro-карты ещё нужно измерить. Низкий WR при малом N не доказывает слабость. Отсутствие доступных игр не доказывает отсутствие опыта: неизвестные аккаунты, закрытая/неполная история и недоступные тренировки остаются неизвестными.

Первое применение — необязательный блок игрок×герой «Рейтинговые игры» рядом с «Профессиональными матчами»: observed games/wins/raw WR, период, последняя доступная игра, source/fetchedAt, effective filters и coverage. N=0 → WR=null. Ошибка или отсутствие pub source не блокирует pro-аналитику и V1. Не объединять denominators в общий процент и не подставлять pub WR при нехватке pro-матчей.

Контекст: свежесть, patch label по доступному источнику, role с confirmed/estimated/unknown статусом, уровень лобби/оппонентов и solo/party при наличии. Не требовать всех этих полей или точного deployment registry для описательного блока; unknown показывать явно. Average lobby rank не считать точным личным MMR. Lifetime aggregate не выдавать за recent-ranked sample; фиксировать период, фильтры и полноту выдачи.

Только verified numeric account links; дополнительные аккаунты объединять после отдельной проверки, не по nickname. Ranked sample определяется проверенными provider mode/lobby fields: Turbo, unranked, custom и unknown не включать автоматически. Сохранять map IDs, source/time и дедупликацию между источниками; раздельные storage/query/contracts для pub/pro, без массового HTML scraping. API-агрегат пригоден для descriptive только при известной семантике фильтров и ограничений.

Для будущей модели — отдельная группа `ranked_hero_practice`; точный набор N/WR/recency/missingness после source audit. Связь с выбранным героем относится к hero-aware/post-draft модели. Pre-match hero-pool features — отдельный эксперимент, без подстановки фактического героя целевой карты заранее. **V1 player Elo и его обновления по pro-картам не меняются.**

История для признаков включает только завершённые и допустимые по объявленной availability policy pub-карты до target cutoff. Event/known/fetched раздельны; сегодняшний lifetime WR нельзя подставлять в старый прогноз. Retrospective допущения маркируются. Training target остаётся verified pro outcome: паблики не увеличивают число профессиональных обучающих примеров.

Пользу проверять сравнением моделей без/с pub features на одинаковом untouched temporal/series-aware pro holdout целевого Tier 1 domain: Brier/log loss/calibration/coverage. Не вводить фиксированный бонус за высокий WR или штраф за низкий WR/малое N. Smoothed estimate/prior показывать отдельно от raw WR; 50% не универсальная норма для каждого героя/роли/уровня.

**Статус:** описательный S2-07 реализован: [backend reader/cache](docs/S2_07_RANKED_PRACTICE_READER.md), [UI](docs/S2_07_RANKED_PRACTICE_UI.md), [raw hero summary](docs/S2_07_RANKED_HERO_SUMMARY.md). Immutable pub observations хранятся отдельно от pro. В карточке игрока есть ручная загрузка, период, coverage и отдельные games/wins/nullable WR/last-played по героям для проверенного OpenDota v2. [Live контроль](docs/S2_07_RANKED_COVERAGE_CONTROL.md) подтвердил197 ranked-карт Dendi/25 героев; summary сверен с сохранёнными картами без новых provider calls. Это bounded single-account sample, не полное покрытие всех игроков. STRATZ остаётся availability-only до непустой проверки, legacy v1 не включает показатели. Predictive effect не реализован и не измерен; pub features — последующий эксперимент. Отсутствие pub данных не добавляет blocker текущему V1-evaluation. Запрет подмены профессиональной статистики остаётся в силе.

### 0.9. Уточнение владельца: журнал и статистика собственных прогнозов входят в V1

Решение2026-11-02: базовый учёт собственных прогнозов обязателен **до приёмки первого выпуска**. S3-07/V1-journal включает сохранение, verified-result linking и простой экран статистики. Дополнительные графики/разрезы и scheduled monitoring остаются расширениями. Предмет — победа команды **на одной профессиональной карте**, не исход BO3/BO5.

Каждый выданный числовой forecast от прошедшей gate активной модели сохраняется до ответа пользователю: server-created timestamp, отдельный server `issued_at` успешного сохранения готового прогноза, cutoff, target одной карты, команды A/B, ожидаемые5v5, scenario/input/features/source snapshots, probability, model/artifact/policy revision и evidence активации на момент выдачи. Эти данные неизменяемы. Назначение «прогноз реальной карты» и single-map target фиксируются до issued_at; what-if нельзя задним числом превратить в prospective. Повторный расчёт и ручная замена игрока создают новые записи. Unavailable/failed остаются видимыми попытками с null probability и причиной, но не оцениваются как числовые прогнозы. Защита owner/session/CSRF распространяется на журнал и обновление результатов.

Прогноз связывается с фактическим canonical match_id только после проверки соответствия **конкретной карты**, команд и A/B mapping, времени и профессионального исхода через существующую verified-outcome границу. Scheduled series ID сам по себе не определяет map ID или map number; неизвестная связь получает статус «Не удалось связать», без угаданной привязки к первой карте серии. Результат хранится отдельно от prediction snapshot, с source/verification time и revision. Повторная проверка идемпотентна. Для V1 достаточно явного обновления результатов владельцем/обычной операции refresh; отдельный scheduled retraining/monitoring не требуется. Ручной выбор победителя не становится verified ground truth.

**Основная prospective статистика сервиса:** один primary forecast на одну фактическую карту. Правило `last_successful_pre_start_v1` задаётся до просмотра исходов: последний успешно сохранённый реальный forecast с server `created_at < actual_started_at`, **issued_at < actual_started_at** и допустимым cutoff не позже actual start, полученный от прошедшей gate модели, активной **на момент выдачи**. Одной даты создания фоновой задачи недостаточно: расчёт, завершённый после старта, не входит. Выбор — лексикографический максимум tuple(issued_at, created_at, prediction_run_id), timestamps сравниваются без потери точности БД, UUID — в canonical lowercase text order. Выбор зависит от времени/назначения прогноза, не от победителя, вероятности или ошибки модели. Общие показатели и фильтр версии используют одну и ту же primary выборку; смена версии не удваивает одну карту и не удаляет её прошлые прогнозы при деактивации. Все остальные recalculations доступны в архиве, но не увеличивают основной N. В audit сохраняется причина включения/исключения и revision primary policy/aggregate report. Обычный what-if сценарий без зафиксированного назначения реальной карте не считается prospective forecast.

Несовпавший фактический состав **не удаляет** корректно привязанный pre-start forecast из основной end-to-end статистики: пользователь получил прогноз на ожидаемую пятёрку. Сохранить `matched/mismatched/unknown` по составу и показать отдельный conditional срез совпавших пятёрок. При unknown actual roster не выдумывать совпадение; подтверждённый map outcome с корректными командами/временем всё ещё может оценивать сервисный прогноз. Роли/patch/draft, не используемые V1, не являются дополнительными veto. Подробные strict cohorts старших моделей могут требовать свои контексты; их нельзя смешивать с этой статистикой.

Минимальный экран: таблица «карта/команды → время → ожидаемые составы → вероятность и фаворит → версия → статус/фактический победитель → угадан ли исход», фильтры периода/версии/статуса, время последнего обновления, source и N. Счётчики расчётов и уникальных карт различимы; основные показатели — карты с прогнозом, проверенные, ожидающие результата, отменённые, не связанные/конфликтные, доля угаданных победителей. Отменённые/неразрешённые не считаются поражениями и показываются отдельно, не исчезают из журнала.

Фаворит A при pA>0.5, B при pA<0.5; при точном0.5 фаворит и correct=null. Такие настоящие модельные прогнозы входят в вероятностные метрики, но отдельно показаны и исключены из знаменателя accuracy, который явно виден. Accuracy — correct / число проверенных primary прогнозов с определённым фаворитом; при N=0 — null. Не округлять p до выбора фаворита. Brier/log loss и простая reliability table (вероятность/bins, N и observed WR) считаются по тем же verified primary прогнозам, включая p=0.5, с отдельным N и обозначенной metric policy. По версии виден размер выборки; historical backtest/research/what-if показываются отдельно. Нулевой sample не превращается в0% или обещанную точность.

Коррекция источника создаёт новую revision outcome association/aggregate report, сохраняя предыдущую и исходный forecast. Нельзя после исхода менять prediction time/состав/p, выбирать «удачный» recalculation или удалять ошибки из основной статистики. Прогнозы/оценки не являются training labels; один verified canonical map остаётся одним примером на stage/dataset version. Автопереобучение/автоактивация от нового результата не включаются этим требованием.

**Статус:** scope утверждён, backend/UI журнал и outcome linker ещё не реализованы; текущая задача разработки остаётся S3-01/V1-evaluation collector/ledger. S3-07/V1-journal следует за gate/snapshots и обязателен до S4/V1 acceptance. Frozen release validation protocol и research artifacts этой редакцией не меняются.

## 1. Назначение и границы

Персональное веб-приложение для анализа предстоящих **профессиональных** матчей Dota 2 и моделирования драфтов. В системе есть один личный аккаунт владельца с авторизацией; публичная регистрация, платежи и совместная работа отсутствуют. Пользователь выбирает две команды, проверяет предполагаемые составы, смотрит исторические матчи и создаёт виртуальный драфт с привязкой героя к конкретному игроку. Система рассчитывает статистику на завершённых pro-картах и два прогноза исхода одной карты: **до драфта** и **после полного драфта**. Период, патч, размер выборки, качество прогноза и неизвестные параметры отображаются явно.

**MVP включает собственный Prediction Engine.** Вероятности разрешено показывать **только** после обучения, калибровки и временного backtest на исторических pro-картах. При неготовой модели или недостаточных данных показывается сравнительная статистика со статусом «прогноз недоступен», а не придуманные 50/50 или произвольный скоринг. Не является советником для ставок.

### 1.1. В MVP

0. **Один аккаунт владельца:** вход/выход, защищённые cookie-сессии, страница настроек, закрытый доступ к личным сценариям. Пользователь создаётся через конфигурацию/CLI; публичной регистрации нет.
1. Справочник профессиональных команд, игроков, героев и патчей; поиск по имени и идентификатору.
2. Просмотр команды: текущий предполагаемый состав (с возможностью ручной корректировки), история карт, винрейт и форма, список героев, статистика Radiant/Dire, личные встречи.
3. Просмотр игрока: профессиональные матчи, выбранные герои, матчи/победы, KDA, GPM, XPM; фильтры по дате, патчу, команде, стороне и выбранному герою.
4. Создание сценария предстоящей карты из двух команд и двух пятёрок игроков (позиции 1–5 задаются/подтверждаются вручную).
5. Ручной выбор 0–10 героев, необязательные баны, сохранение и изменение виртуального драфта.
6. Анализ каждого назначения «игрок → герой», статистики героев в pro-сегменте, пар союзников и контрматчапов противников; подсчёт покрытия данными и предупреждения о малых выборках.
7. Хранение нормализованной истории, кэширование расчётов и фоновая загрузка/обновление данных.
8. Режим отсутствующих/неполных данных без ошибок и подмены нулём.
9. **Предматчевый прогноз:** оценка вероятности победы на одной карте по известным до драфта факторам команды, состава, формы и силы оппонентов.
10. **Прогноз после драфта:** отдельная оценка с учётом 10 назначенных героев и player-hero статистики; сравнение с предматчевой оценкой и объяснение отличий.
11. История прогнозов, версии моделей, воспроизводимые входные признаки, показатели backtest и прозрачные предупреждения о качестве.

### 1.2. Вне MVP

- Автоматическое расписание всех турниров и подтверждение официальных составов на конкретную карту.
- Live-драфты, real-time телеметрия, разбор реплеев своим парсером.
- Автоматические советы по пикам/банам, сложные нейросети, генеративные объяснения без статистического основания, гарантированные прогнозы исхода серии.
- Массовый сбор Dotabuff HTML, обход ограничений сайтов и API.
- Публичная регистрация, платные подписки, командные пространства, многопользовательские права, мобильные приложения.
- Публичные матчи как составная часть профессионального win rate (при желании позже отдельно).

## 2. Источники данных и ограничения

| Источник | Роль | Стратегия |
|---|---|---|
| **OpenDota REST** | Основной: команды, pro-матчи, составы, игроки, герои, подробные карты | Серверный HTTP-клиент, ограничитель запросов, нормализация |
| **dotaconstants** | Названия, идентификаторы, версии игровых данных/патчей | Версионированный справочник; даты патчей валидировать |
| **STRATZ GraphQL** | Резерв/обогащение, если прошла проверка доступа и условий | Отдельный ProviderAdapter; выключен по умолчанию |
| **Dotabuff** | Референс пользовательского опыта | Не парсить в MVP; отдельно анализировать разрешения |

Базовый URL: `https://api.opendota.com/api`.

Запросы для импорта:

| Endpoint | Для чего |
|---|---|
| `GET /teams` | Справочник команд |
| `GET /teams/{team_id}` | Карточка команды |
| `GET /teams/{team_id}/players` | Известные игроки, флаг `is_current_team_member` (не гарантия состава будущей карты) |
| `GET /teams/{team_id}/matches` | История pro-карт команды |
| `GET /teams/{team_id}/heroes` | Вспомогательные агрегаты (период необходимо проверять) |
| `GET /proMatches?less_than_match_id=...` | Последние pro-карты, проход в прошлое по ID |
| `GET /matches/{match_id}` | Участники, герои, KDA/GPM/XPM, стороны, `picks_bans` при наличии |
| `GET /players/{account_id}` | Профиль и Steam32 ID |
| `GET /players/{account_id}/matches` | История игрока, но **не считать автоматически pro-only** |
| `GET /players/{account_id}/heroes` | Агрегаты по героям, но **не считать автоматически pro-only** |
| `GET /heroes` | Справочник героев |
| `GET /heroStats`, `GET /heroes/{id}/matchups` | Контрольные/справочные показатели; результат этих эндпоинтов не считать текущей профессиональной метой без доказанного совпадения фильтров |

**Правило источника истины:** профессиональные метрики проекта считаются только по `matches.is_pro=true` и нормализованным `match_players`. Никакие «общие по аккаунту» показатели `/players/{id}/heroes` нельзя смешивать с pro-only данными. `is_pro=true` устанавливается по подтверждённому профессиональному источнику (`/proMatches`, pro-история команды/лиги), не по наличию десяти игроков в матче.

**Лимиты:** согласно опубликованной документации OpenDota — 50 000 бесплатных запросов в месяц и 60 запросов/мин. В коде лимиты конфигурируемые; использовать запас, кэш и единый серверный rate limiter. Нельзя полагаться на стабильную полноту истории, наличие реплейного парсинга или актуальность состава.

**ID:** ID команд и матчей хранить как `BIGINT`; `account_id` OpenDota — Steam32 и отличается от Steam64; ID героев — числовые значения Dota. `player_slot` OpenDota для Radiant обычно 0–4, Dire 128–132; сторона игрока определяется по этому полю, а не по расположению в массиве.

## 3. Пользовательские сценарии и функциональные требования

Формат: `FR-XX` — приоритет P0 (обязателен) / P1 (улучшение MVP).

### FR-00. Личный аккаунт и авторизация [P0]

- Единственный владелец системы; пользователь создаётся через защищённую CLI-команду или переменные первоначальной инициализации, не через открытый endpoint.
- Вход по логину/паролю, Argon2id-хэш, cookie `HttpOnly; Secure; SameSite=Lax/Strict`; сессионный токен хранится на сервере в виде хэша; logout удаляет сессию.
- Все личные сценарии, отчёты и прогнозы доступны только авторизованному владельцу; запросы неавторизованного клиента дают `401`.
- Настройки: предпочитаемый патч/окно/количество карт, часовой пояс отображения; история сценариев на главном экране.
- В MVP нет регистрации, восстановления пароля по email, OAuth/Steam login, тарификации. Сброс пароля — локальная CLI-команда.
- В БД у сценария есть `owner_user_id`, чтобы в дальнейшем поддержать нескольких владельцев без переезда схемы.

### FR-01. Поиск и выбор команд [P0]

- Поле поиска с подсказками по имени/тегу, отображение логотипа (если источник разрешает использование), ID, последнего обновления.
- Нельзя выбрать одну и ту же команду с двух сторон.
- При выборе команды отображается предполагаемый состав из API; статус «предполагаемый, уточните перед матчем».
- Кнопка «Обновить данные» инициирует фоновую задачу и не блокирует интерфейс.
- При совпадающих именах поиск различает команды по ID/тегу.

### FR-02. Обзор профессиональных карт команды [P0]

- Фильтры: последняя 10/20/50/100 карт, 30/90/180 дней, патч, турнир, сторона Radiant/Dire.
- Показатели: карты, победы, поражения, win rate, доля сыгранных сторон, серия последних результатов, средняя длительность, число игр с полными данными.
- Таблица карт: дата, турнир, противник, сторона, счёт, победа/поражение, герои, ссылка на подробности.
- Только матчи до момента анализа (`cutoff_at`, включать `started_at < cutoff_at`).
- Видно, когда и каким источником обновлены результаты.

### FR-03. Состав команды [P0]

- Известные актуальные участники из OpenDota; проверка отсутствующих и бывших игроков.
- Сохранение ручного «состава для сценария» из пяти игроков, каждой персоне назначается роль 1–5.
- Роли `Carry/Mid/Offlane/Soft Support/Hard Support` не выводятся как достоверные только по флагу членства; автоматическая оценка допустима лишь со статусом inferred и уверенностью.
- Stand-in разрешён, но явно помечается.
- История сыгранности: количество pro-карт точным составом из этих 5 аккаунтов; отдельная метрика команды как организации.

### FR-03a. Roster continuity и замены [P0]

- **Организация != игровая пятёрка**. Не использовать общий win rate Team Liquid как непосредственную оценку новой пятёрки; историю старого состава показывать отдельно.
- Использовать реальных 5 игроков каждой карты (`match_players`) и отдельную **пожизненную pro-историю игрока**, включая любые прошлые команды. Если игроки прежде вместе выступали за другую организацию, их совместные карты учитываются при анализе сыгранности.
- Для текущей пятёрки считать: `exact_five_maps`, 10 независимых попарных co-play выборок, свежесть, последние смены состава/churn, сохранение ролей и покрытие идентификаторами; отображать N и период.
- Разрешить сохранить **базовую предполагаемую пятёрку** (`scenario_expected_lineup`) и сравнить с **выбранной для сценария** (`scenario_lineup`); замены 1–5 участников, stand-in, переходы и перестановки ролей.
- При замене одного игрока сохраняются 4 общих игрока и 6 из 10 структурных связей, **но это не фиксированный штраф в 40%**. Не устанавливать вероятность победы/потерю силы по ручной формуле без temporal backtest.
- Если исходный состав неизвестен, статус замены неизвестен; ручной `is_standin` не эквивалентен доказанному снижению силы. Подтверждение пользователя относится к сценарию, а не гарантирует реальный состав.
- `docs/ROSTER_CONTINUITY.md` — обязательный технический контракт (фильтры, feature engineering, UX, миграция, тесты).

### FR-04. Профиль профессионального игрока [P0]

- Имя, известный Steam32 ID, команда, позиция в сценарии.
- Статистика по pro-картам: games, wins, win rate, KDA (сумма K+A / max(1, сумма D)), средний K/D/A за карту, GPM, XPM, последние 20 карт.
- Пул героев: количество игр/побед, свежесть игры, показатели на герое.
- График формы по последним картам; выбор периода и патча.
- Результаты с подменой игроков помечаются; не делать выводов на основании неидентифицированных аккаунтов.

### FR-05. Сравнение двух команд [P0]

- Сравнительная таблица: win rate последних карт, win rate на текущем патче, состав/сыгранность, Radiant/Dire, противники за период, личные встречи.
- «Личные встречи» — только реальные карты между ID этих двух команд и до `cutoff_at`.
- По умолчанию показывать две выборки: весь доступный состав команды и «точно эта пятёрка»; если вторую невозможно рассчитать, выводить `недостаточно данных`.
- Количество игр рядом с любым процентом обязательно.

### FR-06. Создание сценария анализа [P0]

- Пользователь выбирает команды A и B, необязательный турнир, ожидаемое время начала, формат серии (BO1/BO2/BO3/BO5).
- Пользователь подтверждает пятёрки и роли; стороны Radiant/Dire **не фиксируются заранее**, если ещё неизвестны. Необязательный переключатель карты позволяет назначить сторону.
- Анализ драфта относится к **одной карте** серии, а не ко всей серии. В сценарии BO3 можно позже создать отдельные драфты для карт №1–3, но это P1.
- `cutoff_at` по умолчанию — момент анализа; для исторического backtest явно задаётся время до начала карты. Будущие данные не попадают в расчёт.
- Сценарий сохраняется, имеет собственный UUID и может быть изменён.

### FR-07. Конструктор драфта [P0]

- Две колонки, по 5 слотов на сторону; каждый слот имеет игрока, позицию и выбранного героя.
- Героев можно добавлять, менять и удалять; бан — опциональное действие в журнале драфта.
- У каждой карты не более 10 выбранных героев; один и тот же герой не может быть выбран обеими сторонами, повторно выбран или одновременно выбран и забанен.
- Показывать статистику уже после частичного драфта (например 3 против 2).
- Если выбран герой, а игрок для слота неизвестен, рассчитывать только общую и командную часть; персональную часть не подменять средним.
- Текущая последовательность `pick/ban` хранится в порядке; при редактировании она атомарно пересохраняется с повторной проверкой ограничений. Отдельный аудит всех версий драфта — вне MVP.

### FR-08. Аналитика выбранного героя и игрока [P0]

- Для каждого слота: `pro games on hero`, `pro wins`, win rate, усреднённые K/D/A и GPM/XPM, дата последней профессиональной игры на герое.
- Показывать частоту выбора героя игроком: количество pro-карт с героем / число всех его pro-карт в том же периоде.
- По умолчанию текущий патч и окно 90 дней; при малой выборке отдельно показывать предыдущее окно/другие патчи, но не смешивать их незаметно.
- Если нет матчей: «нет подтверждённых профессиональных игр на герое за выбранный период».

### FR-09. Синергия союзных героев [P0]

- Для каждой пары выбранных союзников считать количество pro-карт, где оба героя выступали на одной стороне, победы и win rate по этой стороне.
- Пара безразлична к порядку: A+B = B+A. Одна реальная карта входит в статистику пары один раз.
- Показать минимальное количество наблюдений и сравнительную базу (винрейт героев на сопоставимом наборе карт), а не категоричное «лучшая связка».
- Опционально в P1 учитывать конкретную пару игроков на конкретной паре героев.
- Не трактовать корреляцию как причинность.

### FR-10. Матчапы героев [P0]

- Для каждой пары `свой герой vs противник` считать pro-карты, где герои выступали на разных сторонах, и долю побед *относительно своего героя*.
- Показать матрицу максимум 5×5 по заполненным слотам; направление A→B принципиально: победы A противоположны победам B.
- Не путать общедоступный `/heroes/{id}/matchups` с профессиональной и актуальной по патчу выборкой; показатель для MVP выводится из локальной pro-базы.
- При малом n показывать бейдж «малая выборка» вместо жёсткой оценки.

### FR-11. Отчёт драфта [P0]

- Блок «Индивидуальный опыт»: таблица из 10 слотов, доступных данных, истории игрока на герое.
- Блок «Союзные пары»: до 10 пар на полную сторону, n и win rate.
- Блок «Против героев соперника»: матрица до 25 матчапов, n и win rate.
- Блок «Ограничения данных»: дата обновления, патч, окно, источники, покрытие, отсутствующие поля.
- Отчёт дополняется **проверенным прогнозом** с указанной моделью/качеством, либо состоянием «прогноз недоступен»; не вычислять вероятность непосредственно из сырых процентов win rate.

### FR-12. Источники, качество и синхронизация [P0]

- При загрузке сопоставить ID, сохранить время запроса и статусы `pending/partial/complete/unavailable`.
- Повторные загрузки идемпотентны (`UPSERT`); `null` неизвестного значения не равен `0`.
- Ограничение запросов единое для всех фоновых задач; реакция на 429 через `Retry-After` (если есть), затем exponential backoff + jitter.
- Отчёт отображает `n`, границы периода, патч, полноту игроков/пиков и `computed_at`.
- Для временной недоступности API использовать последние сохранённые данные с явной датой обновления и предупреждением.

### FR-13. Предматчевая модель [P0]

- На карточке сравнения две команды и подтверждённые/предполагаемые составы; вызов прогноза `pre_match` до ввода героев.
- Выход: вероятность победы Team A и Team B на **одной карте**, дата среза, модель/версия, размер train/test набора, качество калибровки, важные признаки и предупреждения.
- Признаки известны до игры: историческая сила команд (например, Elo), форма с поправкой на силу соперников, стабильность состава, опыт выбранной пятёрки, сторона если известна, применимый патч; не включать поля, появляющиеся после начала матча.
- Если Radiant/Dire неизвестны, использовать специально обученный «unknown side» сценарий или усреднение **отдельно рассчитанных** гипотез сторон; это должно быть объяснено в результате.
- Нельзя запускать предматчевое обучение и прогноз на текущих/будущих результатах относительно `cutoff_at`.

### FR-14. Прогноз после полного драфта [P0]

- Требует 10 **разных** назначенных героев и сопоставленных слотов двух команд; отсутствие личного player ID допускается только с явно пониженным качеством данных.
- Использует ту же фиксированную предматчевую информацию и дополнительные признаки: hero strength в сопоставимом pro-пуле и патче, конкретный player × hero, союзные пары, 5×5 матчапы, подтверждённые роли и Radiant/Dire.
- Результат: вероятность победы на карте, разница с прогнозом до драфта в процентных пунктах, факторы изменения, покрытие и список самых ненадёжных факторов.
- Частичный драфт 0–9 героев **сохраняет описательную аналитику**, но не показывает численный `post_draft` прогноз в MVP.
- После любого изменения lineup, hero, стороны, cutoff или фильтров новый прогноз создаётся с новым снимком входов. Старый прогноз в истории не изменяется.
- Если обучение/валидация модели недостаточны, показывать аналитический отчёт без вероятности и объяснять причину.

### FR-15. История прогнозов и качество [P0]

- Сохранять: тип `pre_match|post_draft`, версию сценария, `cutoff_at`, данные моделей/feature-снимок, входные команды/игроков/героев, вероятность или `NULL`, `computed_at`, предупреждения и покрытие.
- Предоставить экран сравнения «до/после», а также историю пересчётов одного сценария.
- Версия модели фиксирует алгоритм, время обучения, объём и временные границы train/test, Brier score, log loss и калибровку на независимом временном отрезке.
- При недостаточных/устаревших данных или провале критериев публикации модель не должна утверждать высокую точность или отдавать проценты.
- Подробные правила — раздел 15.

### FR-16. Patch-Aware Analytics (P0, сквозное)

- Матчи точно сопоставляются с версией игры на момент старта; версию патча и релизную дату берём из подтверждённых метаданных, при неизвестности оставляем `NULL` и выводим coverage warning.
- Описательные метрики «на текущем патче» **строго** относятся только к указанному патчу. Отдельные взвешенные модельные оценки могут использовать предыдущие патчи, но маркируются и показывают raw N, effective N, состав по патчам и версию алгоритма.
- Предматчевые признаки силы команды/игрока и post-draft признаки героев/связок/контрпиков используют **разные** функции затухания и проверки релевантности. Старые (например, трёхлетние) карты имеют малый вклад в актуальную мету, но могут нести слабый сигнал длительного опыта.
- Сильно меняющиеся герои (rework) имеют дополнительный вес/ограничение переноса старых hero-метрик на новый патч. Нельзя делать вид, что отсутствие метаданных означает отсутствие изменений.
- При выходе нового патча флаг cold-start и пересчёт/инвалидация кэшей обязательны; без релевантного валидационного quality gate числовой post-draft прогноз недоступен.
- Параметры времени, штрафы переходов патчей и hero-change корректировки — обучаемые/подбираемые на прошедших хронологических отрезках, сравниваются с моделью без весов. Детали и тесты в `docs/PATCH_AWARE_ANALYTICS.md`.

## 5. Метрики: точные определения

**Единица наблюдения:** одна завершённая профессиональная **карта** (`match_id`), не BO3/BO5-серия. Все вычисления используют `started_at < cutoff_at`, `is_pro=true`, допустимый период, выбранный патч и только полноту полей, требуемую конкретной метрикой.

Обозначения: `n` — число допустимых карт; `w` — число побед наблюдаемой стороны.

| Метрика | Расчёт |
|---|---|
| Team WR | `w / n * 100%` в pro-картах команды |
| Exact-lineup WR | То же, но 5 известных аккаунтов одной стороны точно равны выбранной пятёрке |
| Player-hero WR | `wins(player, hero) / games(player, hero) * 100%` в pro-картах |
| Player hero pick rate | `games(player, hero) / games(player) * 100%` в одной pro-выборке |
| KDA | `SUM(kills + assists) / GREATEST(1, SUM(deaths))`; средние K/D/A за игру показываются отдельно |
| Mean GPM/XPM | `AVG(gpm/xpm)` по строкам, где поле не null; показывать размер фактической выборки |
| Hero pair WR | `wins(side with H1 and H2) / maps(side with H1 and H2)` |
| Counter WR | `wins(side playing A against B) / maps(A versus B)` |
| Pro hero pick rate | `maps with hero / all eligible pro maps`, если охват всего набора достаточен |
| Head-to-head | `wins(team A versus B) / maps(A versus B)` |

**Нулевые выборки:** `n = 0 => value = null`, а не 0%. Для малых n используется категориальная отметка (настройки: `n < 10` — недостаточно, `10 ≤ n < 30` — низкая устойчивость, `n ≥ 30` — достаточнее для описательного сравнения). Это **продуктовые пороги**, не статистическая гарантия.

**Патч и окно:** основной режим — текущий игровой патч с верхним ограничением 90 дней и `cutoff_at`. Для командной формы дополнительно показывается «последние 20 pro-карт» независимо от 90 дней (как отдельная метрика). Если на текущем патче данных нет, не подмешивать другой патч в тот же показатель.

**Сглаживание (P1):** для отображения относительно средних можно использовать `p_smooth = (w + k·p0)/(n+k)` с заранее заданным `k` и `p0` от сопоставимой профессиональной выборки. Для MVP хранить сырые `wins/n`, не скрывать реальное n и не создавать композитный win score.

**Неоднозначные роли:** роли игрока в сценарии задаёт пользователь; «игра в своей роли» в исторических картах показывается только при достоверных role-labels, иначе не фильтровать по предположениям.

### 5.1. Правила для вероятностного прогноза

Исторические описательные метрики — **входные признаки**, а не готовые вероятности победы. Модели обучаются с бинарной меткой реальной победы Team A. `P(B) = 1 - P(A)` только если исход не предполагает ничьей в одной карте. Обязательна калибровка на хронологически более поздних матчах. Без прохождения проверок `win_probability = NULL`, а не формально рассчитанный процент.

## 6. Логическая модель и схема данных

**Связи:** User → AuthSession; User → Scenario; Team ↔ TeamRosterPeriod ↔ Player; League → Match; Series → Match; Match → MatchPlayer → (Player, Hero); Match → MatchDraftAction → Hero; Scenario → ScenarioLineup → (Player, Hero); Scenario → ScenarioDraftAction; Scenario → AnalysisRun; Scenario → PredictionRun → PredictionModelVersion.

**См. сопровождаемый SQL-файл `SCHEMA.sql`** — исполняемые таблицы, CHECK/FK, индексы.

| Таблица | Назначение и ключевые поля |
|---|---|
| `teams` | PK `id`; `opendota_team_id` unique; `name`, `tag`, `logo_url`, `synced_at` |
| `players` | PK `id`; `opendota_account_id` (Steam32) unique nullable; `steam64_id` text; `nickname`, `synced_at` |
| `heroes` | PK `id` (официальный герой); name, localized_name, metadata |
| `patches` | PK `id`; `label`, `released_at`, source |
| `leagues` | PK `id`; внешний `opendota_league_id`, name |
| `series` | PK UUID; pair teams, scheduled_at, best_of, state; не путать с картой |
| `team_roster_periods` | Team–Player; role, valid_from/to, source, confidence/verified |
| `matches` | PK `id` = `match_id` BIGINT; teams by Radiant/Dire; patch, league, series, timestamp, winner, import quality |
| `match_players` | PK `(match_id, player_slot)`; player (может отсутствовать), hero, side, stats, role confidence |
| `match_draft_actions` | Историческая последовательность picks/bans из матча |
| `scenarios` | PK UUID; команды A/B, hypothetical radiant side, `cutoff_at`, scheduled_at |
| `scenario_lineup` | PK `(scenario_id, team_slot, role)`; выбранные игроки и герои 1–5 |
| `scenario_draft_actions` | Упорядоченная последовательность действий текущего пользовательского драфта (не журнал редакций) |
| `analysis_runs` | История расчётов: input_hash, version, filters, result JSONB, quality, timestamps |
| `app_users` | Владелец, уникальный логин, хэш пароля, настройки и статус |
| `auth_sessions` | Серверные авторизованные сессии с хэшами токенов и сроком действия |
| `prediction_model_versions` | Тип модели, версия, артефакт, training cutoff, backtest-метрики, флаг активности |
| `prediction_runs` | Неизменяемый снимок прогноза с типом, вероятностью/NULL, версией модели, признаками и объяснениями |
| `sync_jobs` | Очередь задач импорта с retry/ошибками |

Особенности:
- Личные сценарии привязаны к `app_users.id`; предметные данные pro-карт глобальны, чтобы не дублировать их при будущей поддержке нескольких аккаунтов.
- `prediction_runs` хранит **снимок** входного состояния, а не только ссылку на редактируемый драфт; неизменность поддерживается сервисным слоем.
- `team_a/team_b` — обозначение на экране, не Radiant/Dire. Radiant/Dire задаётся для реальных карт отдельно.
- Принадлежность pro-игрока к команде не хранится только одним `current_team_id`: нужны изменения состава/подмены во времени.
- Исторический участник карты может не иметь известного `player_id`; строка допустима с null и участвует в общекомандных метриках, но не в exact-lineup.
- Данные без `picks_bans` участвуют в статистике по сыгранным героям, но **не** участвуют в ban/pick rate.
- API-ключи в БД предметных сущностей не сохраняются; только в серверных secrets/env.

## 7. Архитектура приложения

```text
apps/web (Vue 3 / TS / Pinia / Router / ECharts)
       |
       | HTTP JSON
       v
apps/api (Fastify / TS / Zod)
  ├─ TeamsController / PlayersController / ScenariosController
  ├─ AuthService (единственный аккаунт, безопасные cookie-сессии)
  ├─ AnalyticsService (чистые функции и SQL-агрегаты)
  ├─ PredictionService (pre_match, post_draft; inference + quality gate)
  ├─ OfflineTrainAndBacktest (CLI; обучение, калибровка и артефакты моделей)
  ├─ SourceAdapters
  │    ├─ OpenDotaProvider (основной)
  │    └─ StratzProvider (неактивен в MVP)
  └─ JobsService (периодическая загрузка, повторные попытки)
       |
       +--- PostgreSQL (Prisma/Drizzle + migrations)
       +--- PostgreSQL job queue или BullMQ/Redis позднее
```

**Пакеты монорепозитория:**
- `apps/web` — SPA и состояние сценариев;
- `apps/api` — REST, доменные сервисы, провайдеры;
- `packages/contracts` — Zod/TypeScript DTO;
- `packages/analytics` — формулы и правила выборок, unit-тесты;
- `packages/prediction` — feature engineering, offline training, calibration, inference, backtesting;
- `packages/db` — миграции и репозитории.

Рекомендуемый MVP: **Drizzle ORM + PostgreSQL** и простая очередь задач в PostgreSQL; Redis и отдельный worker-процесс можно вынести после измерений нагрузки. Важнее иметь централизованный rate limiter для OpenDota, чем вводить много микросервисов.

## 8. Контракты собственного REST API

Префикс `/api/v1`. Ответы с аналитикой включают `filters`, `sampleSize`, `computedAt`, `dataUpdatedAt`, `source`, `coverage`, `warnings`. Даты — ISO-8601 UTC.

| Метод и путь | Назначение | Примечание |

## 9. Схема импорта данных

### 9.1. Первичное наполнение

1. Импортировать справочники `/heroes`, `/teams`, patch metadata; проверить внешние ID.
2. Для выбранной команды получить `/teams/{id}/players` и `/teams/{id}/matches`.
3. Собрать уникальные `match_id` последних 100 pro-карт каждой из двух команд, плюс доступные pro-карты для фоновой базы меты (общий поток `/proMatches`).
4. Для каждого `match_id` вызвать `/matches/{id}` и атомарно импортировать `matches`, участников, picks/bans. Проверить «ровно 10 слотов» для статуса `complete`.
5. Сопоставить аккаунты, даты, героев, лиги, патч; неизвестные оставить null и создать `warning`.
6. Удалить дубли по ID; при обновлении повторить UPSERT.
7. Рассчитать показатели из БД и сохранить отчёт с точным cutoff и версией алгоритмов.

### 9.2. Фоновое обновление

- Герои/патчи: раз в сутки и после обновления игры (интервал настраиваемый).
- Команды/составы: не реже 1 раза в 6 часов для выбранных команд, плюс ручная команда «обновить» с ограничением частоты.
- История pro-карт: инкрементально, например раз в 30 минут для избранных команд; не считать полноту API гарантированной.
- Импорт карточки карты: один раз после появления, повтор если `partial`/нет детальных полей.
- Кэш аналитики: инвалидировать при изменениях сценария, данных источника, версии расчётов или параметров фильтрации.

**Рабочий бюджет:** не более 45 запросов/мин (настраиваемый консервативный лимит); ниже опубликованного 60/мин; не превышать месячную квоту. HTTP 429/5xx → backoff; 404/неполная запись → статус и повтор по заданной политике, а не бесконечный retry.

### 9.3. Проверка покрытия

При недостаточном объёме импортированных карт не выводить утверждение «этот герой имеет WR X% во всём профессиональном пуле». Формулировка должна быть «в загруженной выборке N карт». Мета требует широкого независимого покрытия pro-матчей, а не только карт двух выбранных команд. Для MVP можно показывать одновременно `scope=selected_teams` и `scope=imported_pro_sample`; они маркируются раздельно.

## 10. Качество данных, безопасность и нефункциональные требования

**Доступ к личным данным:**
- Все routes `/api/v1/*` кроме входа и health-check закрыты сессией владельца; CORS по явному allowlist.
- Логин rate-limited, сессии серверные, токен доступен только cookie; все изменяющие запросы защищены от CSRF.
- Никакие открытые endpoint регистрации, платежей, тарифов и управления другими пользователями не существуют.

**Функциональная корректность:**
- Повторная загрузка одного match_id не создаёт дублей.
- `is_pro`, принадлежность команде, герой и победа определяются из подтверждённых полей.
- Временной срез предотвращает попадание матчей, стартовавших после `cutoff_at`.
- Обучение, калибровка и inference прогнозов исключают признаки из будущего; разделение по времени и серии исключает повторные карты серии между train и validation.
- Прогноз после драфта недоступен без десяти уникальных героев; состояние частичного драфта остаётся анализируемым описательно.
- При недостаточном качестве модели вероятность всегда `null`, с явной причиной отказа.
- Смена патча не меняет историю ранее рассчитанных «as of» отчётов.
- При неполных данных расчёты выполняются по доступным полям или выводится `null` + причина.

**Эксплуатация:**
- API-ключи только на сервере, `.env` исключён из Git; логирование без секретов.
- Адаптеры источников с timeout, retry, нормализацией ошибок и общим request budget.
- Защитить `/admin/*` от публичного доступа, даже если MVP однопользовательский.
- Основные индексы в `SCHEMA.sql`; хранение timestamps в UTC.
- Сценарии и аналитика восстанавливаются после перезапуска контейнеров.
- Интерфейс не должен замерзать во время длительной загрузки.

**Целевые показатели (проверяются на пилоте):** cached API-ответы p95 < 1,5 сек; отчёт по уже импортированным картам p95 < 5 сек; первый импорт проходит асинхронно; база не допускает потери уникальности `match_id`.

**Тесты:** unit-тесты формул; интеграционные тесты PostgreSQL и нормализации OpenDota; контрактные тесты на сохранённых примерах ответов; e2e-сценарии авторизации, сравнения двух команд, полного драфта и двух типов прогнозов. Отдельные offline-тесты: temporal leakage, калибровка, Brier/log loss, правильный состав feature snapshot, детерминированная загрузка артефакта модели.

## 11. Критерии приёмки MVP

1. Поиск находит две разные профессиональные команды по имени; пользователь видит время последнего обновления.
2. Можно создать сценарий с двумя разными командами и вручную подтвердить ровно пять игроков/ролей на каждой стороне.
3. Импортируются как минимум доступные последние 20 pro-карт каждой выбранной команды, либо показывается честное состояние «доступно меньше N» с причиной.
4. Можно открыть карточку карты и увидеть десять героев и результат, если детальная запись полная.
5. В отчёте команды рассчитываются карта-в-карту win rate, выбранный период, стороны и очные встречи.
6. У игрока отображаются только подтверждённые pro-матчи; ранговая/публичная статистика не загрязняет результат.
7. Можно построить и сохранить частичный драфт, заполнить все 10 героев, изменить назначение игрока и героя.
8. Невозможно назначить одного героя двум героям-слотам, использовать забаненного героя или продублировать игрока в составе одного сценария.
9. Система выводит исторические `player + hero`, синергию и матрицу контрпиков для известных слотов, с размером выборки и фильтрами.
10. `n=0` выводит «нет данных», а не «0% WR»; малые выборки помечаются.
11. Два одинаковых запуска анализа при неизменной базе и фильтрах дают одинаковый результат; обновление данных приводит к пересчёту.
12. API OpenDota временно недоступен → интерфейс остаётся рабочим, показывает кэш/ошибку и не подставляет фиктивные значения.
13. Единый provider limiter предотвращает превышение заданного RPM; 429 приводит к retry с задержкой.
14. Есть `docker compose up` для локальной разработки, миграции БД, seed справочников и команды тестов.
15. На наборе тестовых карт корректно вычисляются Radiant/Dire, исход победы, 1 подсчёт пары за карту и исключение карт после cutoff.

16. Личный аккаунт создаётся через CLI; до авторизации пользователь видит только страницу входа, после выхода нет доступа к сохранённым сценариям.
17. Для подтверждённых команд можно запросить предматчевый прогноз или получить явное «модель/данные недостаточны» без фиктивного процента.
18. При 10 героях доступен post-draft прогноз, до этого числовой post-draft прогноз не отображается.
19. После изменения драфта новый прогноз сохраняется как отдельная запись; старый остаётся воспроизводимым по снимку.
20. Backtest объединяет карты одной серии в один хронологический блок, исключает post-match признаки и публикует метрики двух моделей.
21. API не возвращает опубликованную вероятность от модели, не прошедшей quality gate; интерфейс сообщает причину и показывает доступную статистику.

## 15. Prediction Engine: техническая спецификация

### 15.1. Объект и этапы прогноза

**Одна карта (map), не серия**. Выход `p_team_a` относится к победе команды A в её предстоящей карте. Это оценка модели, а не гарантированная вероятность реального исхода и не рекомендация ставок.

| Стадия | Когда считается | Допустимые признаки | Требования |
|---|---|---|---|
| `pre_match` | До выбора героев | Сила команд по истории, форма, сила противников, roster stability, роль/опыт, патч, сторона если известна | Команды и идентифицированные составы или явное предупреждение о неизвестных игроках |
| `post_draft` | После выбора 10 героев | Всё из `pre_match` + герои, player×hero familiarity, пары, 5×5 матчапы, мета по патчу, состав/роль | 10 разных героев, обе стороны/слоты определены; сторона Radiant может оставаться unknown только если это поддерживает модель |

Нельзя показывать `post_draft` процент для 0–9 героев. Для частичных драфтов остаются доступными таблицы, сравнения и описательные метрики.

### 15.2. Алгоритмы первой версии

1. **Baseline:** исторический Elo команды/состава (вес матчей по давности, при наличии — поправка на силу соперников); зафиксировать правило обновления рейтинга и его версию. Чистый Elo — простой контрольный прогноз, а не результат исследований draft.
2. **Pre-match v1:** регуляризованная логистическая регрессия по признакам, вычисленным строго на момент `cutoff_at`, с Elo-разницей как сильным базовым признаком. Возможны разные группы признаков, но не «всё подряд»; сохранить коэффициенты и масштабирование.
3. **Post-draft v1:** отдельная регуляризованная логистическая регрессия, использующая `logit(p_pre)` и признаковые агрегаты по 10 героям, игрокам, парам и матчапам. Обучать так, чтобы `p_pre` исторических тренировочных примеров был рассчитан без доступа к их исходу и будущим играм.
4. **Калибровка:** Platt / isotonic только на отдельном временном сегменте. Без проверки калибровки нельзя маркировать score как точный win probability.
5. **Позже, вне базового MVP:** CatBoost/LightGBM, sequence models, embeddings драфтов, прогноз серии, контрфактические советы по банам.

Форма выходного расчёта для объяснения различий: `delta_pp = 100 × (p_post - p_pre)`. Допускается пояснять вклад признаков в **скор модели**, но не приписывать им причинное изменение реальных шансов на победу.

### 15.3. Признаки и антиутечка

Только данные, которые могли быть известны на момент прогноза. Для матча с датой `T` каждый исторический запрос использует `history.started_at < T`, а не дату импорта записи. Данные об опыте игрока, патче, команде и мета-статистике тоже должны быть построены по состоянию на `T`.

**Разрешены до матча:** rolling Elo, wins последних N про-карт, сила соперников, состав, количество карт данной пятёрки, патч, Radiant/Dire при известности, отдых/свежесть при качественных timestamp.

**Разрешены только после полного драфта:** 10 hero IDs, подтверждённое назначение герой/игрок, player-hero experience, pro pick/ban/synergy/counter, роль героя с подтверждённой разметкой.

**Строго запрещены:** kills, deaths, net worth, GPM/XPM, duration, first blood, tower outcomes, финальный счёт текущей карты; любые факты об исходе, которые появились после стартового `T`. Нельзя использовать агрегаты OpenDota `/heroStats` как исторические признаки, если они рассчитаны по всей текущей базе с будущими играми. Пересчитывать из `matches`/`match_players` на нужном срезе.

**Патч:** при обучении требуется patch metadata, существовавшая к `T`; ранние данные другого патча допускаются только как **отдельные** затухающие признаки, которые модель учится интерпретировать. Для отображаемых обычных WR используем заявленный патч и не смешиваем выборки.

### 15.4. Исторические данные и алгоритм обучения

- Учебная строка — pro-карта с известными командами, датой, победителем. Для `post_draft` дополнительно должны быть полностью известны десять героев; player×hero признаки могут быть missing + флаг missing.
- Для каждой строки последовательно восстановить `as_of` features **до** старта карты (без учёта текущей карты); при одной и той же дате придерживаться стабильного тайм-брейка.
- Делить dataset хронологически по дате матчей и **группам серий** (все карты одной BO-серии в одном fold). Train → calibration → test, без случайного перемешивания карт разных времён.
- Убирать зеркальную зависимость от порядка teamA/teamB с помощью нормализации ориентации и теста симметрии `p(A,B) ≈ 1 - p(B,A)` при одинаковых вводах.
- Артефакт включает веса, scaler, порядок признаков, схему подготовки, версию и оценку качества; feature builder один для offline и online, иначе возникнет training-serving skew.
- Обучение запускается вручную/по расписанию как offline CLI-job, **не** внутри API-запроса пользователя. Результаты локально воспроизводимы на сохранённом наборе match IDs.

### 15.5. Контроль качества и публикация модели

Обязательно хранить на независимом хронологическом тесте: `n_test`, baseline Elo, Brier score (ниже лучше), log loss (ниже лучше), calibration curve / ECE, accuracy на пороге 0.5 как вторичную метрику. Отдельно сравнивать результаты `pre_match` и `post_draft` на **одном и том же пересечении** полного draft-test, иначе сравнение некорректно.

**Предлагаемый стартовый quality gate:** независимый тест не менее 300 pro-карт по каждой модели; корректный temporal split; отклонение калибровки не хуже согласованного порога (уточняется после эксперимента); Brier и log loss не хуже простого baseline на том же наборе. Число 300 — рабочая проектная гипотеза для проверки, не научная гарантия точности. Если gate не пройден, `status=unavailable` и `teamAWinProbability=null`; descriptive analytics остаётся рабочей.

Недостаточное покрытие состава, неизвестная сторона, устаревший патч или сильная смена состава — предупреждения. Нельзя утверждать «65% точности» без сохранённой метрики для сопоставимой тестовой выборки и указания периода.

### 15.7. Практический критерий завершения Predictor MVP

Предматчевый и последрафтовый endpoints вызываются в личном кабинете, оба фиксируют модель и as-of features, корректно ведут историю, блокируют неполный драфт и могут честно отказаться от процента. На заранее выбранном историческом тестовом наборе выводятся quality-метрики, позволяющие сравнить модели с baseline, а в UI виден охват данных и разница прогноза до/после драфта.

## 16. Решения, оставленные на будущее

- Приватные рабочие пространства для других пользователей, регистрация, email, подписки, роли, публичные API-ключи — **не реализовывать**.
- В структуре данных сохраняем `owner_user_id`, отдельный аналитический пакет и versioned model registry, чтобы не переписывать фундамент позже.
- Онлайн-модель драфта во время турнира, live-betting, советы по ставкам и гарантии прибыли не являются задачей проекта.

## Уточнение: приоритет текущего состава и сыгранности (MVP 2.1)

Статистика команды-организации, конкретной пятёрки и игроков по всей карьере обязана рассчитываться раздельно. Для обеих моделей учитываются состав и его изменения: новый игрок может улучшить индивидуальную силу, но снизить сыгранность; **автоматически считать такую замену ухудшением запрещено**. Нужны две сравнимые исторические конфигурации — baseline и candidate — и временная валидация признаков состава. Спецификация: `docs/ROSTER_CONTINUITY.md`.

## 17. Уточнение архитектуры и плана (Personal MVP 2.2 — 27.10.2026)

Требования ниже **уточняют**, не расширяя MVP до публичного SaaS. Полный чеклист, dependency order и точные acceptance gates — `docs/IMPLEMENTATION_PLAN.md` (v3, IDs `S0-..S5-..`). Схема обновляется forward-only через `004_context_identity_provenance.sql`.

**Обязательные P0:** противник и его сила *на дату карты*, а не только raw WR; организация отдельно от игроков и exact-five; verified аккаунты/переименования и историю смены ролей; различие между событием, доступностью сведений и синхронизацией; карта отдельно от серии, история pre-map score, независимые Team A/B–Radiant/Dire–first pick; патч и подтверждённые правила доступности героев; shrinkage малых выборок и honest coverage; неподменяемые снимки и model gate. Предматчевый прогноз не видит драфта, post-draft учитывает назначение всех десяти героев конкретным игрокам. Старые матчи за прошлую организацию не исчезают из player/pair statistics; замена не получает фиксированный штраф.

**P1 после рабочего P0:** LAN/online и уровень/стадия турнира как проверяемые признаки, полный исторический порядок пиков/банов, Model Performance с фактическими результатами, What-if сценарии, compare pre/post при идентичном snapshot, интерфейс review неоднозначной идентичности/провайдеров.

**P2:** прогноз результата всей BO-серии и между картами; структурные признаки драфта/стиля команды. Хранение базовых полей BO и parent scenario в миграции 004 — архитектурная подготовка, а НЕ обязательство реализовать P2 в MVP.

Нормативные контракты: `docs/POINT_IN_TIME_AND_MATCH_CONTEXT.md`, `docs/IDENTITY_AND_DATA_QUALITY.md`, `docs/MODEL_EVALUATION_AND_SCENARIOS.md`. Все ключевые метрики должны указывать источник, дату среза, объём, тип (raw/smoothed), model version/качество, а при неизвестном контексте оставаться nullable.

## 18. Continuous Learning Architecture (v4, 27.10.2026)

**P0 архитектурно:** результаты новых *проверенных профессиональных карт* могут включаться в **следующую** версию обучающего датасета (одна карта → один sample per dataset/stage). Сохранённые прогнозы, guesses пользователя и неподтверждённые What-if сценарии не используются как истинные метки. Полностью отделять реальные labels от замороженных as-of features, версионировать dataset/code/patch/feature/policy и source evidence. После ручного offline train кандидата валидировать на отдельной временной тестовой выборке, только после прохождения quality gate проводить атомарное включение; все изменения логировать. Старые прогнозы и датасеты не перезаписывать.

**P1 после MVP:** регулярное пакетное переобучение по расписанию/накоплению pro-карт/смене патча, challenger vs champion, реальные prospective метрики с подтверждённым исходом и настройка opt-in автоматической публикации (по умолчанию **отключена**). Не обучаться после каждого прогноза и не превращать количество пользовательских прогнозов в статистический вес.

Обязательные документы: `docs/CONTINUOUS_LEARNING_PIPELINE.md`, `docs/IMPLEMENTATION_PLAN.md`, `docs/PREDICTION_ENGINE.md`; миграция `005_training_pipeline.sql`.

## Дополнение v9 — обязательные требования к исходным драфтам и селекции матчей

Нормативно: [docs/DRAFT_DATA_INTEGRITY.md](docs/DRAFT_DATA_INTEGRITY.md). Реальные пользовательские результаты OpenDota выявили 0/11/12 raw pick events при 10 сыгранных героях, неполные ID организаций и неизвестные ID серий. Эти поля независимо валидируются и хранятся; Data Collector не должен «исправлять» источник удалением событий или исключать карту из всей статистики. Подтверждённые финальные герои могут использоваться для hero-only пост-драфтовых сценариев без validated timeline, но историческая доступность до начала карты требует отдельного доказательства. Полная хронология — отдельный валидатор, учитывающий режим и патч; итоговый training gate stage-specific. SQL `006_draft_data_quality.sql` применяется только после 001–005.
