# Dota 2 Pro Analytics — Personal MVP / Codex Engineering Kit v9

**Текущий этап — S4, приёмка V1:** [требования, доказательства и открытые условия выпуска](docs/S4_V1_ACCEPTANCE_AUDIT.md). Доступны расписание, ручные 5v5, сохранение расчётов, сопоставление результата, отмена/открытие встречи и журнал. Активной проверенной модели пока нет; расчёт сохраняет `unavailable` с объяснением и пустой вероятностью.

[Проверка на рабочих данных](docs/S4_V1_LOCAL_OWNER_SMOKE.md) пройдена: вход, история команды/игрока, сравнение, расписание, архивный журнал и выход. Приложение доступно после запуска по `http://localhost:5173`; это должен быть тот же origin, что в `.env`. В расписании доступен [фильтр турнира по ID PandaScore](docs/S4_V1_SCHEDULE_EVENT_FILTER.md): он работает по сохранённой странице до20 записей и не определяет Tier1 автоматически. При смене фильтра выбранная встреча и несохранённая форма сбрасываются.

На главной доступен [актуальный статус реестра модели](docs/S4_V1_MODEL_READINESS_STATUS.md) и кнопка повторной проверки. Недоступность модели отличается от ошибки соединения; время проверки указано в UTC. Даже допуск реестра требует отдельной проверки состава, истории и турнира при расчёте.

## Локальный запуск

**Быстрое сравнение:** выберите встречу → проверьте автоматически подставленные сохранённые пятёрки → подтвердите игроков → выберите период → **«Сравнить выбранные пятёрки»**. Для Angry Birds — Spirit Academy выберите «Последний год». Сохранять сценарий для сравнения не нужно. Ручные исправления доступны через «Изменить игроков и роли», технические подробности раскрываются отдельно. [Краткая инструкция](docs/S1_16_COMPARISON_UX.md).

Если пригодных сохранённых пятёрок ещё нет, аккаунты **подготавливаются автоматически**. Проверенные общие связи переиспользуются сразу; новые соответствия видны в карточке и подтверждаются кнопкой **«Подтвердить аккаунты и выбрать пятёрку A/B»**. При шести участниках отметьте нужных пятерых. Причины незаполненных мест показаны рядом с именами; расширенный поиск открывается через «Уточнить аккаунты A/B». [Автоматическая подготовка](docs/S2_01_AUTOMATIC_ROSTER_PREPARATION.md), [ручной порядок и исправления](docs/S2_01_UNIFIED_PLAYER_CATALOGUE.md).

В редакторе сценария и форме будущей встречи доступны [роли из PandaScore/STRATZ и pro-истории](docs/S2_01_ROLE_PROFILES.md). В «Сопоставление источников» один раз свяжите команду и записи игроков, затем нажмите «Обновить профили API». Редактор расставляет выбранную пятёрку по одной однозначной подсказке на игрока: PandaScore → STRATZ → pro-история. Источник и расхождения видны; неизвестные/повторяющиеся роли остаются для ручного уточнения. Ручная правка сама выключает авто, сохранённый состав открывается с выключенным авто. Герой/замена следуют за игроком. Роли не входят в V1 Elo.

В форме будущей встречи доступна [личная pro-история пятёрки](docs/S2_01_PLAYER_HISTORY.md): выберите игроков → «Загрузить историю игроков». OpenDota ID организации не нужен. Доступен выбор 90–730 дней и 10/25/50 карт на пятёрку; по умолчанию год и 25 карт. Нужен обработчик очереди, описанный в инструкции.

В карточке игрока под профессиональной статистикой героев раскройте [«Рейтинговая практика»](docs/S2_07_RANKED_HERO_SUMMARY.md): для OpenDota v2 доступны игры, победы, наблюдаемый WR и последняя игра по героям. Показаны период, источник и покрытие; раскрытие читает сохранённые данные, внешний запрос запускается кнопкой загрузки/обновления. Малое число игр не доказывает силу на герое, пустой источник не означает нулевой опыт. STRATZ пока показывает доступность истории без геройских показателей. [Backend](docs/S2_07_RANKED_PRACTICE_READER.md) включается флагом RANKED_PRACTICE_ENABLED (default=false, локально включён). Рейтинговые карты не обновляют V1 Elo.

Проверенный непустой пример — [Dendi](http://localhost:5173/players/61), OpenDota:197 ranked-карт/25 героев в ограниченной30-дневной выборке. Исправлен общий дефект OpenDota project; [adapter v2](docs/S2_07_RANKED_COVERAGE_CONTROL.md) запрашивает героя/длительность явно. Old observations сохранены, v1 cache обновляется вручную без ожидания прежнего TTL. STRATZ для этого аккаунта ranked-историю не предоставил; источники не объединяются автоматически.

[Дополнение STRATZ](docs/S2_07_STRATZ_ENRICHMENT.md) подключено: в рейтинговой практике OpenDota раскройте **«Дополнительные данные STRATZ»** → **«Дополнить данные STRATZ»**. До20 последних известных карт получают оценку позиции и код версии игры, с проверкой совпадений и кэшем. У Dendi20/20 карт совпали, позиция доступна19/20. Повторная загрузка использует кэш; N/WR основной выборки сохраняются.

После загрузки сервис [подготавливает аккаунты остальных участников и серии](docs/S2_01_HISTORY_ENRICHMENT.md). В отчёте отдельно показаны raw N и допустимая история Elo, ограничения источников и время проверки. Частичный результат не означает готовность прогноза; модель требует независимой проверки и активации.

[Проверка owner API](docs/S4_01_V1_SECURITY_REVIEW.md) исправила отражение URL в ранних ошибках и raw path в логах. [Сверка очереди](docs/S4_01_V1_QUEUE_COVERAGE.md) также исправлена: native backup/restore проверяет pg-boss и сохранность queued data. [Проверка сбоев источников](docs/S4_01_V1_PROVIDER_RESILIENCE.md) исправила сохранение Retry-After OpenDota для всех 5xx между клиентами; сбой обновления сохраняет прежнее расписание с пометкой stale. [Проверка конфликтов](docs/S4_01_V1_PROVIDER_CONFLICTS.md) подтверждает сохранение исходных фактов и исключение спорных данных. S4-01 завершён для localhost V1. [Историческая регрессия](docs/S4_02_V1_HISTORICAL_REGRESSION.md) сверила232 frozen development карты с прежними признаками и runtime; доступна offline-команда `pnpm regression:v1`. [Полный browser suite](docs/S4_02_V1_FULL_OWNER_E2E.md)57/57 прошёл на изолированных данных, включая compiled API restart/CLI flow. S4-02 завершён для localhost V1. [Production preflight](docs/S4_03_V1_DEPLOYMENT_PREFLIGHT.md) исправлен, но контейнерная проверка пока blocked: нет Docker и .env.production. Проверка native БД проходит. Общая приёмка модели/release и production deployment остаются открытыми.

Нужны Node.js >=22.12, pnpm 10.19.0 и PostgreSQL 16. На этой Windows-машине уже настроен нативный PostgreSQL; команды его запуска и локальные pnpm shims описаны в [bootstrap](docs/S0_00_VERIFICATION.md). При использовании Docker запустите PostgreSQL командой `pnpm db:up`.

Выполняйте команды из каталога `dotaanalitic`:

```powershell
corepack pnpm install --frozen-lockfile
# Только при первой настройке, если .env ещё нет:
if (-not (Test-Path -LiteralPath '.env')) { Copy-Item -LiteralPath '.env.example' -Destination '.env' }
# Укажите локальный DATABASE_URL в .env, затем:
corepack pnpm db:migrate
corepack pnpm preflight:strict --require-db
corepack pnpm typecheck
corepack pnpm build
# Только если владелец ещё не создан: задайте логин и скрытый пароль в терминале.
corepack pnpm owner:create
corepack pnpm dev
```

Откройте `http://localhost:5173` (точно как `WEB_ORIGIN` в `.env`). В другом терминале `corepack pnpm smoke` проверяет API. После обновления примените все текущие миграции командой `pnpm db:migrate` и запустите приложение; существующего владельца повторно создавать не нужно. Ключ PandaScore нужен для обновления расписания, а ключи источников хранятся только в серверном `.env`. Без ключа и без данных интерфейс показывает причину недоступности.

Путь владельца: «Предстоящие матчи» → выбрать встречу → «Зафиксировать назначение первой карты» → сопоставить две локальные организации → сохранить назначение → подготовить сценарий → выбрать десять игроков → подтвердить и сохранить → вернуться к назначению → рассчитать. [Сверка сыгранной карты](docs/S3_07_V1_SCHEDULED_BINDING_OWNER_FLOW.md) доступна у сохранённого расчёта; [отмена и открытие](docs/S3_07_V1_SCHEDULED_TARGET_LIFECYCLE.md) — на странице назначения. Для статистики создайте отдельный сохранённый отчёт в «Журнале прогнозов».

Перед новым назначением и прогнозом сведения именно об этой встрече должны быть моложе 5 минут. В блоке «Свежесть расписания» используйте «Обновить расписание перед прогнозом»; при ошибке или задержке повторов показана причина. Старые записи доступны для просмотра и точного повтора запроса. [Правило и ограничения](docs/S4_V1_SCHEDULE_FRESHNESS.md).

## Проверки

```powershell
corepack pnpm test
corepack pnpm test:fixtures
corepack pnpm verify:migrations
corepack pnpm verify:docs
# Полный API/БД набор: PostgreSQL 16 с CREATEDB, pg_dump и pg_restore 16:
corepack pnpm test:postgres
# Дополнительно требуется установленный Chromium:
corepack pnpm test:e2e
```

E2E создают отдельные временные базы, синтетического владельца и данные. Команда `pnpm test:e2e` сама собирает API с зависимостями. Новый `v1-acceptance.spec.ts` запускает собранные API/CLI и перезапускает API с сохранением той же тестовой базы; при прямом вызове Playwright CLI предварительно выполните `pnpm build`. Проверки отдельных функций и прежние результаты приведены ниже как история разработки; номера миграций в этих записях относятся к соответствующему этапу.

`pnpm test:postgres` собирает API/worker и автоматически включает все `*.integration.test.ts` из их тестов и пакетов db/ingestion, а также базовую проверку миграций. Каждый набор использует временную БД. Для restore-тестов задайте `PG_BIN` — каталог PostgreSQL 16 с `pg_dump`/`pg_restore`; на этом Windows-ПК используется `.tools/pgsql/bin`. `pnpm test:integration` отдельно проверяет миграции и ограничения в собственной временной БД, не заполняя рабочую базу тестовыми строками. Список полного набора: `node scripts/test-postgres.mjs --list`.

## Проверка резервной копии — S4

Общая локальная регрессия и исправления средств проверки: [S4-02](docs/S4_02_V1_FULL_REGRESSION.md).

`pnpm backup:verify --pg-bin .tools/pgsql/bin --bundle .tools/v1-frozen-runtime` создаёт локальный backup и проверяет его восстановление в новую временную PostgreSQL16 БД. Проверяются fingerprints таблиц, snapshots и модельные файлы; сессии отзываются только в восстановленной копии. Тестовая база удаляется, архив остаётся в игнорируемой `.tools/backups`. [Процедура, файлы и ограничения](docs/S4_V1_BACKUP_RESTORE.md).

## История разработки

### S3-00 — подготовка датасетов

После `pnpm db:migrate` (текущая019) используйте `pnpm dataset:prepare preview config.json`, затем `build config.json`. Strict as-of context и проверенный исход сохраняются отдельно; неизвестные составы/патчи/серии исключаются. Пустая выборка даёт unavailable без новых записей. Повтор одинакового build использует прежний frozen ID; `export <dataset-uuid> output.json` проверяет SHA и сохраняет точные bytes без перезаписи файла. Это prepared-context-v1, ещё без numeric features/training; прогнозы недоступны. Проверки: `pnpm test:dataset-builder`. [Config, gates и ограничения](docs/S3_00_DATASET_BUILDER.md), [свежий live audit](docs/S3_00_SOURCE_AUDIT.md).

## Предстоящие матчи — S1-10

После `pnpm db:migrate` (019) и запуска `pnpm dev` войдите владельцем и откройте «Предстоящие матчи» (`/upcoming`). Ключ `PANDASCORE_API_TOKEN` остаётся только в серверном `.env`. Обновите расписание, выберите встречу и загрузите заявки. Время матча показано в МСК; время получения источника — отдельно. Server cache5мин и общая PostgreSQL quota защищают источник.

В раскрывающемся блоке найдите две организации и10 разных игроков по имени или ID, явно выберите записи из локального справочника, подтвердите роли и создайте обычный manual scenario. ID PandaScore не подставляются как canonical IDs. Если источник недоступен, последнее расписание сохраняется с предупреждением. Проверки: `pnpm test:upcoming`, `pnpm test:e2e`. [Поведение, API и ограничения](docs/S1_10_UPCOMING_UI.md).

Тёзки различаются по ID, повторный игрок недоступен, правка выбора снимает подтверждение состава. Пустая выдача требует уточнения запроса или пополнения локального каталога. [Поведение и проверки](docs/S1_11_CATALOG_PICKER.md).

На страницах организаций и игроков доступны описательные отчёты с N/source/filters: по5 карт у Spirit/Yandex и десяти основных игроков, DM0/null. `pnpm provider:audit --teams ... --capture ...` и `pnpm history:current preview/apply ...` позволяют обновлять ограниченную выборку через сохранённый source capture и проверенный импорт; повтор сохраняет число карт и ревизии. [Команды, покрытие и ограничения](docs/S1_13_CURRENT_HISTORY.md).

S1-14: на странице организации выберите **«Загрузить последние pro-карты»**. Запуск идёт через durable очередь; состояние, объём, время источника и частичный результат видны на странице, статистика перечитывается после завершения. Повторные клики используют прежний run; cooldown5мин после завершения. API/worker защищают source quota и idempotency. Проверки: `pnpm test:history-refresh`, `pnpm test:e2e`. [Запуск worker, API и ограничения](docs/S1_14_HISTORY_REFRESH.md).

S1-15: в ручной форме `/upcoming` явно выберите организации из локального справочника. Под выбором появятся N, наблюдаемый win rate, даты, источник и покрытие последних 20 локальных pro-карт; здесь же можно обновить историю и открыть полные отчёты/сравнение организаций. Игроки и роли выбираются отдельно. [Поведение и ограничения](docs/S1_15_UPCOMING_SUMMARY.md).

S1-16/17: выберите десять разных игроков, подтвердите роли и нажмите **«Сравнить выбранные пятёрки»**. Показаны отдельно история организаций, точных пятёрок,10 пар и игроков с N/датами/coverage. По умолчанию последние90 дней; доступны даты UTC и ID патча/лиги. Изменение фильтров сохраняет состав/подтверждение, скрывает прежний результат до нового запуска. Enter в фильтре выполняет только сравнение; сценарий не сохраняется. [Сравнение](docs/S1_16_UPCOMING_LINEUPS.md), [фильтры и QA](docs/S1_17_UPCOMING_FILTERS.md).

Период сравнения не переносится в сохраняемый сценарий: его срез фиксируется при сохранении, начало периода отчёта выбирается отдельно. Сохранённая версия отчёта не меняется после обновления истории; новый расчёт создаёт новую версию. [Сквозная проверка S1-18](docs/S1_18_UPCOMING_WORKFLOW_QA.md).

После выбора строки расписания экран и фокус клавиатуры переходят к карточке ожидаемых составов. Это помогает на телефоне и при длинном списке встреч. [Приёмка реальных данных и S1-20](docs/S1_20_OWNER_ACCEPTANCE.md).

После успешного обновления расписания или заявки API автоматически сохраняет неизменяемый снимок источника и серверное время в `upcoming_source_observations` (миграция021). Для этого не нужен отдельный запуск Codex. Снимок подтверждает только доступность объявления на момент записи; связь с фактической картой, игроками и драфтом проверяется отдельно. На16 текущих pro-картах strict dataset preview дал0 пригодных для обучения примеров, поэтому прогнозы пока недоступны. [Evidence и ограничения](docs/S1_08_PROSPECTIVE_SOURCE_EVIDENCE.md).


Продолжение подготовки личной истории: после завершённой загрузки откройте «Изменить игроков и роли» → «Личная pro-история» → **«Продолжить проверку загруженных карт»**. Проверяются недостающие числовые аккаунты, серии и пригодность для Elo; поиск и скачивание карт не повторяются. Кнопка учитывает cooldown, создаёт отдельный отчёт и сохраняет исходную загрузку. Наличие истории не активирует модель. [Подробно](docs/S2_01_HISTORY_ENRICHMENT_RESUME.md).


Подготовка независимой проверки V1: [проверенное состояние и команды сбора](docs/S3_01_V1_EVALUATION_READINESS.md). Источники собираются до фиксированного снимка2 декабря2026 03:00МСК; оценка запускается не раньше него. Автоматический сбор турнира сейчас не включён. Дата сама по себе не активирует прогнозы.


Сбор данных для первой независимой проверки: [управляемый CLI](docs/S3_01_V1_COLLECTION.md). Команды status/collect/recover/merge сохраняют все попытки; повтор номера не вызывает повторный API-запрос. Фоновое расписание не включено, настоящий сбор ограничен зарегистрированным окном.

Пакеты деталей для проверки модели: [details-init/status/capture/recover/export](docs/S3_01_V1_COLLECTION.md#детали-карт-полный-набор-пакетов). Все карты и ошибки сохраняются в учёте; повтор пакета не делает новых API-запросов. Экспорт источников ещё не означает готовность прогнозов.

Импорт собранных пакетов и общий отчёт: [import-batch/recover/reconcile/export](docs/S3_01_V1_IMPORT_COLLECTION.md). Повтор номера не записывает карты заново; явная новая попытка сохраняет предыдущие результаты. Сверка использует все пакеты и один снимок БД, а экспорт готовит отдельную конфигурацию проверки модели.

Проверка составов и ролей: [живые кейсы и ручное редактирование](docs/S2_01_ROLE_UI_ACCEPTANCE.md). После замены игрока повторно подтвердите состав перед сравнением; неподтверждённые новые аккаунты требуют проверки владельца.
